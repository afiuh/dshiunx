## 怎么做

### 1. Effect —— 副作用怎么撤销？

**问题**：组件卸载时，它写过的文件、注册的监听器、分配的定时器，怎么全部撤掉？

**解法**（§3.1）：

- 把副作用从 `f : X ⇝ Y` 改写成 `f : Γ × X → Γ × Y`
- 每次执行**当场交出逆函数**：`f(γ) → (δ, g)`，`g` 把 `δ` 恢复成 `γ`
- 运行时把 `g` 攒成栈，卸载时 **LIFO** 依次执行
- 组合规则：`(f1,g1) ∘ (f2,g2) = (f1∘f2, g2∘g1)`——逆按相反顺序累积

**为什么是起点**：撤销是"可组合"的第一硬要求。装很容易，卸干净才难。后面的每个机制都建立在"能撤销"之上。

**缺了它**：组件只能装不能卸，卸载留下幽灵副作用（定时器还在跑、监听器还在响）。

**边界**：
- 内核只负责"攒和倒序执行"，**不理解副作用是什么**
- 逆函数由写代码的人提供（只有他知道怎么撤销）
- 只要求左逆（`g∘f = id`），不要求右逆

---

### 2. Coeffect —— 组件怎么声明依赖？

**问题**：组件要等 `ctx.fs` 就绪才能启动，系统怎么知道"什么时候能启动它"？

**解法**（§3.2）：

- 依赖建模为部分函数 `Σ ≔ (k : K) ⇀ 𝒱k`
- 关键：`set(k, v)` 的返回类型是 `𝔈Σ*`——**依赖注册本身就是 effect**，所以天然可撤销
- 组件声明依赖集合 `d ⊆ K`
- 满足谓词 `σ ⊧ d`；每次 context 变化按满足性分类：
  - **activating**（不满足 → 满足）→ 执行组件的 effect 链
  - **deactivating**（满足 → 不满足）→ 应用 accumulator 恢复
  - **neutral** → 不动

**为什么建立在 Effect 上**：如果依赖注册不可撤销，组件卸载后依赖还挂在表里 → 依赖泄漏、同名注册冲突。

**缺了它**：组件只能硬编码 import，或者自己轮询依赖状态。

**边界**：不预设依赖类型（字符串 key + 类型族），不做版本仲裁。

---

### 3. Context —— 两者怎么共处？

**问题**：effect 改 `Γ`、coeffect 读 `Σ`，怎么一起撤销？隔离和拦截是独立机制吗？

**解法**（§3.3 / §3.2.3）：

- 把 effect 上下文和 coeffect 上下文统一成 `Γ∞`
- **隔离（isolate）/ 拦截（intercept）是派生 context**：
  - 派生新 context，不改共享表
  - **逆是 identity**——恢复时直接丢弃派生 context，不需要追踪
- 这就是为什么隔离和拦截"不需要清理"——它们从不修改原 context

**缺了它**：两套状态各管各的，撤销不完整；隔离要额外追踪。

**边界**：内核不预设隔离语义（label 是什么由调用方定）。

---

### 4. Fiber —— 撤销的边界在哪？

**问题**：撤销哪些？谁持有这条 effect 链？

**解法**（论文 Table 2）：

```
fiber = ⟨d 依赖声明, p provide, e effect 链, 状态机, uid⟩
```

状态机：`pending`（依赖没齐）→ `loading` → `active` → `unloading` → `disposed`

**缺了它**：没有"组件"这个单位，不知道撤销什么。

**边界**：fiber 不承载业务状态（业务状态是插件自己的事）。

---

### 5. Loader —— 组件从哪来？

**问题**：配置怎么变成 fiber？改一个字段要不要重建整棵树？

**解法**（§5.2.1）：

- **Entry** 是 fiber 的声明式规格：`id` / `url` / `isolate` / `intercept` / `config` / `disabled`
- **增量协调（reconciliation）**——按变化字段分派最小操作：

| 变化字段 | 操作 |
|---|---|
| `id` / `url` | 重建 entry |
| `isolate` | 重分配 realm |
| `intercept` | 原地更新（读时咨询，无需重载） |
| `config` | 交给组件决定（通常 diff，实质变化才重载） |
| `disabled` | 置位卸载，清除重载 |

**缺了它**：只能整体重建，改配置 = 重启。

**边界**：loader 不决定组件内容，只管装载顺序和协调。

**子节点**：配置校验（Schema）——`config` 是任意 JSON，装载前要验证。论文没提，是工程配套。

---

### 6. HMR —— 怎么替换？

**问题**：改了一个模块，哪些要重载？怎么保证不进入半重载状态？

**解法**（§5.2.2）——**因为 fiber 已经界定了组件的所有 effect 和 coeffect，所以不需要开发者标注 acceptance boundary**：

1. **模块分类**：从变化模块出发，沿 import 图固定点迭代 → `accepted` / `declined`
2. **stale entry 检测**：entry 的依赖树与 `accepted` 相交 → 该 entry 是 stale
3. **事务性重载**：失效缓存 + 备份 → dispose 每个 stale entry → 装新 fiber → 任一失败就恢复备份

**缺了它**：替换必须重启，或者留下半旧半新（旧代码的副作用还在，新代码又加一遍）。

**边界**：只做替换，不做版本回滚（回滚是 git 的事）。

---

### 7. Event —— 怎么通信？

**问题**：组件之间怎么解耦通信？

**解法**（§5）：五种分发模式

| 模式 | 语义 |
|---|---|
| `emit` | 同步通知，不 await |
| `waterfall` | 环绕中间件，每个监听器可改写参数/结果 |
| `parallel` | 并发扇出，等全部完成 |
| `serial` | 顺序执行，任一返回非空即停 |
| `bail` | 顺序执行，遇到第一个 bail 值即停 |

**缺了它**：组件只能直接 import。

**边界**：**旁支**——不参与可组合性。发个通知，撤销它没有意义。

---

### 8. Logger —— 组件怎么报告状态和错误？

**问题**：组件运行中要告诉人/日志系统“我在干什么、出错了”，怎么做？

**解法**（`logger.ts`）：

- **分级**：`LoggerLevel`（ERROR / WARN / INFO / DEBUG）
- **按 fiber 自动命名**：日志能追溯到哪个插件
- **exporter**：控制台、文件、自定义输出目标
- **拦截配置**：通过 `Service.metadata` 控制某个插件的 `level` / `name`

**缺了它**：每个插件自己 `console.log`，无法统一过滤、无法按插件路由、无法关闭。

**边界**：
- 内核只提供“往哪写”，不决定“写什么”
- 日志**不是事件**（不走 `emit`）——它不改变系统状态，也不参与可组合性
- 日志不是“可观测性”的全部——插件树、事件、状态查询属于插件模块（P7 显式控制）

---

如果把 1+2 合成「效果与共效应」、3+4 合成「上下文与组件」，会变成 5 个，但会丢掉一条关键因果：

> **Coeffect 的 `set` 返回的是 effect function** —— 依赖注册可撤销，是因为它本身就是 effect。

合成一个大节点，这条“两个机制是同一套数学”的推导就藏起来了。分开放，每个节点自己回答自己的问题，因果链才显式。

而第 7、8 个（Event / Logger）是**旁支**，不参与可组合性，但也不能省——它们是内核提供的两种“输出”能力。

### 8.1 内核更新导致插件被迫跟进

**性质**：待讨论的问题 ｜ **状态**：**未定方案**

**现象**：官方内核一更新，插件被迫跟进才能正常使用。

**已查明的根源**：问题出在 **Coeffect** 和 **Context** 两个节点——它们把**内部表示**（符号名、属性名、方法形状）当作公共 API 暴露：

```
Coeffect  → symbols.config / Service.config    （符号名）
Context   → ctx.root                            （属性名）
```

对比：Effect / Event / Logger 是**行为抽象**（`ctx.effect(cb)`、`ctx.on(name, h)`），所以稳定；而 Coeffect / Context 的这两处是**内部表示直接暴露**，所以内核一改形状，插件就断。

**待讨论**（都还没结论）：

- 语义和符号表示该怎么解耦？
- 需不需要一张可跟随内核变化的 API 表？如果需要，表里放什么、名字怎么定？
- TypeScript 的类型声明需要编译期符号，运行时查表解决不了——这个矛盾怎么处理？
- 或者有别的路子（门面 / 适配层 / 版本化契约 / 其他）？

**当前结论：无。**

### 8.2 语义与符号表示的解耦

**性质**：待讨论的设计原则 ｜ **候选位置**：内核模块总则（不入具体节点）

**已观察到的现象**：稳定的 API 都是**行为抽象**，不稳定的都是**内部表示**。

| 类型 | 例子 | 变过吗 |
|---|---|---|
| **行为抽象** | `ctx.effect(cb)`、`ctx.inject(deps, cb)`、`ctx.on(name, h)` | ❌ 从论文到实现没变 |
| **内部表示** | `symbols.config`、`ctx.root`、`Service.metadata` | ✅ rc.11 → rc.12 全变了 |

**为什么 `ctx.effect` 稳定**：它不暴露逆函数存在哪个栈里、栈怎么组织、LIFO 怎么实现。插件只需知道“返回清理函数”。

**待讨论**：

- 是否要把“只用行为抽象作公共 API”定为一条硬规则？
- 内部表示（符号、属性名、静态槽位）该完全藏起来，还是留一条受控的出口？
- 这条规则如果成立，它会约束到哪几个节点（看起来是 Coeffect + Context）？

**当前结论：无。**

### 8.3 内核更新的类型学

**性质**：观察结果 ｜ **候选位置**：内核模块总则 / DSH 更新跟进

分析 rc.11 → rc.12 的实际改动，可分四层（**这只是观察，不是定论**）：

| 层 | 内容 | 例子 | 插件要不要跟 |
|---|---|---|---|
| **结构层** | 8 个机制本身 | 无（本次零改动） | 几乎不动 |
| **语义层** | 机制的确切行为 | `isolate` 不回退、`inject` 优先级 | ✅ 要跟（行为变了） |
| **表达层** | API 名字、签名、符号 | `config`→`metadata`、`root` symbol 化 | ✅ 要跟（编译失败） |
| **工程层** | 性能、诊断、跨副本 | `locate()` 抽出、`ValidationError.is()` | ⚠️ 可选 |

**观察**：拿到一个新版本，可以先分个类，再决定跟不跟、怎么跟。但分类本身还不成熟。

### 8.4 构造性完备 ≠ API 冻结

**性质**：观察与推论 ｜ **候选位置**：内核模块总则

疑问：结构这么简洁，为什么内核还在不断更新？按理说应该构造性完备了。

**一种解释**（待验证）：构造性完备保证的是「能构造出任何东西」，不是「构造的零件永远不变」。

类比：λ 演算是图灵完备的，但编程语言还在更新（语法糖、类型系统、标准库）。

**如果这个解释成立**，内核的“完备”是结构完备，不是功能完备：
- 能构造：任何插件组合、任何依赖关系、任何生命周期
- 构造不出：语义（插件做什么）、跨进程性能、沙箱安全

**推论**：不要期待内核冻结；但要盯住“结构层是否被塞进新东西”——那才是边界失守。

### 8.6 Logger 的定位

**性质**：已定 ｜ **候选位置**：第 8 个节点（旁支）

按内核准入三条（所有插件都依赖 / 与具体能力无关 / 足够稳定）：

- 所有插件都依赖？❌ 不一定（有些插件不记日志）

- 足够稳定？✅ 是

**两条满足，一条不满足** → “可选的内核能力”。
但它确实在 cordis 里，且所有插件都能用 `ctx.logger` 而不用自己装。

**定位**：与 Event 并列的**旁支**——不参与可组合性。

### 8.8 内核固定出口 + 基础插件（**方向已定**，细节待定）

**性质**：架构方向 ｜ **状态**：**方向已拍板**，实现细节后续讨论

##### 要做什么

三层架构，每层只依赖下一层的**功能契约**，不依赖实现：

```
业务插件
  │  只认「标准接口」（语义：isActive / root / effect）
  ▼
基础插件（生成器，可选）
  │  读「固定出口」，生成标准接口文件
  ▼
固定出口（8+N 个功能槽位，只增不减）
  │  内核内部随便改
  ▼
内核（cordis 8 个机制）
```

##### 为什么要做

DSH 的内核一更新，插件被迫跟进（符号名、属性名、静态槽位都在变）。根源：**内部表示直接当公共 API**。

我们要的是：**插件永不跟内核版本**。

##### 怎么做

**① 内核提供固定出口**

按**功能**分槽位（不是按位置、不是按名字）：

| 槽位 | 功能 | 插件读 | 插件提交 |
|---|---|---|---|
| `effect` | 撤销副作用 | — | `register()` |
| `coeffect` | 依赖 | `get()` | `provide()` / `inject()` |
| `context` | 上下文 | `root()` | `isolate()` / `intercept()` |
| `fiber` | 组件单元 | `of()` / `isActive()` | — |
| `loader` | 装载 | `entries()` | `load()` |
| `hmr` | 演化 | — | `reload()` |
| `events` | 通信 | — | `on()` / `emit()` |
| `logger` | 日志 | — | `log()` |

**纪律（照搬 Linux）**：
- 槽位可以**增加**（只增不减）
- 已分配的功能**不删、不改语义**
- 名字可以改（因为基础插件按功能理解，不按名字）

**② 基础插件是生成器（不是运行时服务）**

```
内核启动 → 基础插件跑一次 → 读固定出口 → 生成 standard-api.d.ts
```

这是 protobuf / GraphQL codegen / Prisma 的模式——**编译期生成类型**。

**③ 业务插件 import 生成的文件**

```ts
import { KernelAPI } from '@dshiunx/standard-api'
```

内核更新 → 重新生成 → 插件**重新编译**，代码不改。

##### 读写分离

| 方向 | 操作 | 性质 |
|---|---|---|
| **插件 → 内核** | 读（`root()` / `services()` / `fiberOf()`） | 查询 |
| **插件 → 内核** | 提交（`provide()` / `inject()` / `effect()` / `on()` / `emit()` / `log()`） | **请求，内核决定** |
| **内核 → 插件** | 读（`depsOf()` / `providesOf()` / `effectsOf()`） | 内核特权 |
| **内核 → 插件** | 写（`activate()` / `deactivate()` / `dispose()`） | 内核特权 |

**插件可写不了内核**——它只能提交请求，内核有最终决定权（这也是为什么 `provide` 返回 `Disposable`，而不是让插件直接改 store）。

##### 基础插件是可选的

| | 有基础插件 | 没有基础插件 |
|---|---|---|
| 插件 import | `standard-api.d.ts`（生成物） | `@deepseek-ai/cordis`（内核内部） |
| 内核改 API | **插件重新编译，代码不改** | **插件改代码** |
| 插件作者负担 | 零 | 每次都改 |

**没有它也能用**，只是会变成 DSH 那样“一更新就麻烦”。

##### 为什么选「代码生成」而不是「运行时接口」

之前讨论过运行时查表（`ctx.kernel.at('root')`），最后选了代码生成。对比：

| | 运行时接口 | **代码生成** |
|---|---|---|
| 类型安全 | ❌ 需要手动断言 | ✅ 编译期检查 |
| 插件写法 | 运行时查表，字符串 key | 静态 import，类型推导 |
| 内核更新 | 重新查表 | 重新生成 + 编译 |
| **错误时机** | **运行时** | **编译期** |
| 稳定性来源 | 运行时的表结构 | **生成文件的类型** |

**代码生成更稳定，因为错误从运行时提前到了编译期。**

##### 待定细节（后续讨论）

| 点 | 选项 |
|---|---|
| **生成时机** | 内核启动时 / 构建时（`npm run codegen`）/ 安装时 |
| **生成文件放哪** | `packages/standard-api/generated/` ？进不进 git？ |
| **槽位描述格式** | 生成器的输入——内核要维护一份“接口描述”（类似 `.proto` / `.graphql`） |
| **生成器怎么写** | 读 `ctx.kernelInfo` 运行时元信息？还是读一份静态描述文件？ |
| **业务插件迁移** | 76 个包：渐进 or 一次性 |
| **D2 的正式废弃表述** | 内核自主设计，业务插件继续复刻 |
| **元入口是否也进出口** | `get` / `inject` / `effect` / `on` 是自举入口，可能不进槽位 |

### 8.9 这次讨论产生的其他结论

| 结论 | 性质 |
|---|---|
| 内核需要的信息 = 四表 + 一栈 + 一状态机，全部是 `key → value` | 分析 |
| 存储分散正常，**入口分散才是问题**（Linux 也是存储分散、入口集中） | 分析 |
| DSH 是“能做但没做”——因为它的优先级是“快速演进”，不是“接口稳定” | 判断 |
| 没有现成方案同时满足“同进程 + 类型安全 + 接口稳定” | 调研 |
| Linux 的两层：用户态走 syscall（稳定）/ 内核模块直接链接（不稳定） | 调研 |
| 三条铁律：编号永不回收 / 名字稳定 / 废弃返回明确错误 | 调研 |

## 如何验证自己做对了

- 八个节点每个都能用一句话说出「它回答什么问题」
- 每个节点都能回答「缺了它，插件会怎样」
- 节点之间是**因果链**（主链 6 个），不是并列清单——顺序不能换
- 没有「因为代码里有个包」而存在的节点
- 人能一次读完八个问题，并说出「内核到底管什么」

### 越界判据

一条决策里出现 `session`、`tool`、`llm`、`ui` → 它属于插件模块，不属于内核模块。
