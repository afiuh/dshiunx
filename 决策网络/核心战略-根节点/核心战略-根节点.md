# 核心战略-根节点

**父级**：无

## 为什么要做

### DSH 的理念对，但实现被产品稀释

| DSH 的理念 | DSH 的实现偏差 |
|---|---|
| 一切皆插件，智能体本身也只是插件 | 框架里塞了产品假设（Web UI、账户、遥测、插件市场、多客户端适配） |
| 核心是框架，不是某个具体功能 | 框架与产品耦合，为普适性做取舍 |
| 插件机制是创造工具 | 插件系统为产品功能服务，而不是为"创造"服务 |

**结论**：不是推翻 DSH，是**把它的理念实现得更彻底**——去掉产品包袱，让内核回到"最小、干净、可组合"。

我们要更好地实现他这个理念，最初的框架应该就像 Arch Linux 系统最初的模样一样简洁干净，其他的一切都可以插件化，这种理念实行起来，其实就和Linux系统一切皆文件的理念是同构的，在这个框架上加的所有东西都能进行精确管理控制优化还能随意创造，再加上自进化机制，这样做出来的才是能更好地实现一切皆插件的本意

### 为什么"干净"不是审美偏好

**内核脏了，插件就没法任意组合。**

内核里塞了产品假设、特殊路径、隐式依赖，每加一个插件都要考虑"会不会和内核里的某个假设冲突"。更麻烦的是版本的破坏性更新，如果内核更新插件因为版本问题就不能用了，那会非常麻烦，就很难的做到插件的规模效益，毕竟不是所有插件都会一直跟进的，如果我花了很大的成本好不容易给自己搞出来了一套最适合自己的插件组一更新好多插件都不能用了，那也太沮丧了，只有内核足够小、足够纯，有且只有一个要求那就是插件的能力，插件才能像乐高一样随便拼，AI 才能放心地写新插件，系统才能真的"一切皆插件"。

所以"像 Arch 初始安装一样干净"不是怀旧，是**为了让上面能长出的任何东西都能没有后顾之优**。



## 要做什么

### 一句话

**做一个与操作系统同构的 AI 程序：内核像 Arch 初始安装一样干净，一切皆插件（包括 TUI 和 Agent 循环），系统能在运行中替换和创造自己的器官。**

### 不是真的做一个操作系统

dshiunx 本身仍是**一个运行在现有系统上的程序**；它与操作系统**同构**的结构是从理念推导出的架构（内核/进程/文件系统/窗口管理器/应用），要实现这样的理念就需要这样的架构，而不是实现一个 OS 去和 Windows/Linux 竞争。

DSH 的存在已经证明：**不需要新 OS，也能实现"一切皆插件"**。

> 用户（2026-10-22，纠正"同构"）：
> "我们不是说真的做一个操作系统啊，我们做的这个它不是说深入到计算机内核的操作系统，它本身还是一个程序的，只不过这个程序的理念跟架构，它跟操作系统是同构的，这也是DSH想实现的事嘛，它的存在已经证明了，想要做成这种，不一定说非得做一个全新的操作系统再去和Windows和Linux竞争"

### Arch 的起点：一切都要自己配

Arch 装完只有**内核 + bash + pacman**——没有桌面、没有快捷键、没有输入法、没有浏览器。然后用户自己配了 Hyprland、waybar、fcitx5-vinput、快捷键、代理、编辑器……

这些**没有一个是 Arch 的固有部分**。它们可以随时换掉、删掉、重配。系统仍然是 Arch，因为内核和包管理还在。

dshiunx 的对应起点不是"内核 + TUI + agent 循环"，而是：

```
内核（cordis：DI / 生命周期 / 服务 / 事件）
加载器（loader：配置树 / 嵌套 / HMR）
```

**TUI、agent loop、llm、session、工具、模型、角色、布局——全是插件。**

> 用户（2026-10-22，纠正 AI 的理解）：
> "不不不，TUI和Agent的循环本身也只是插件而已，做出来之后，这些本身也可以在运行中实现自进化，你想想Arch Linux系统在最开始长什么样？是不是所有的都是我们现配的，包括我们现在的桌面管理、快捷键，以及各种软件、程序、工具，都是我们配的"
### 实现的第一阶段-内核打磨
做出可以支持我们理念的内核
1.最小内核

2.一切皆插件，除了内核没有特殊插件

3.在2的基础上实现除了内核一切皆可自进化

4.拒绝垃圾的代码架构，在我们的dshiunx里的插件要做到最大程度的插件解耦化

5.做到插件无限嵌套和随意联动，用简单插件的先进组合实现复杂功能而不是做一个架构垃圾的大插件

### 实现的第二阶段-插件的丰富
由于我们的内核只看功能所以当我们的内核做出来之后所有有功能的程序都可以作为我们的插件，这一阶段我们主要是要配置出最适合我们自己的dshiunx,也是后面可以作为运行damo去宣传我们的项目了


### 实现的第三阶段-应对不同需求
当我们有了名气有了使用者可以根据不同使用者的需求做针对性的发行版，但是发行版不是固定的框架，只是提前组合了相关插件用户还是可以随便拆，这意味着任何人都可以把自己配置出来的dshiunx作为发行版分享出来





### 发行版模式

同一内核 + 不同插件组合 = 不同形态。

Arch 本身最小，但 Manjaro / EndeavourOS / Garuda 提供不同预装组合；dshiunx 的不同 profile 也能精确特化到不同人、不同需求。

> 用户（2026-10-22，审查"非目标"时）：
> "你不能确定自己永远不会做这些，你就别在核心战略里提了，而且你看，按我们的战略展开，所有的好处都能兼顾的，因为插件本身是很自由的，你可以选择运行，也可以选择不运行，就像 Arch Linux 一样，也有很多整合后的发行版，按照我们的战略实现之后，不同的人、不同的需求都能通过不同的插件来精确特化实现"

**原则**：内核保持中立，不替用户做产品选择；选择权在插件组合。

## 怎么做

### P1 · 最小内核

内核只做**不可插件化**的事：

- 依赖注入（`ctx.inject` / `provide` / `get`，见 `registry.ts` / `reflect.ts`）
- 生命周期（`fiber.ts`，effect、dispose）
- 服务注册与查找（`service.ts`）
- 事件分发（`events.ts`：emit / waterfall / parallel / serial / bail，5 种）
- 插件加载（`cordis-plugin-loader`）

**内核准入判据（三条必须同时满足）**：

1. 所有插件都依赖它（不是某类插件）
2. 与具体能力无关（不知道"文件""工具""界面"是什么）
3. 足够稳定（不能频繁变化，否则插件生态无法建立）

**明确不进内核**：TUI、Agent 循环、工具、模型适配器、会话存储、布局、角色、预设。

### P2 · 一切皆插件（包括 TUI 和 Agent 循环）

工具、界面、循环、记忆、装配、角色——全部是插件。**不存在"系统固有功能"**。

关键：**TUI 和 agent loop 也不是固有部分**，只是"初始 profile 里的一套默认选择"——可以换、可以删、可以被 AI 重写。

| 层 | 例子 | 自进化意味着 |
|---|---|---|
| 工具 | `tool-fs`、`tool-bash` | AI 写新工具 |
| 界面 | TUI、LayoutTree、Web renderer | AI 改自己的界面 |
| 循环 | agent-loop（怎么思考、怎么调工具） | AI 改自己的思考方式 |
| 记忆 | session、compaction、storage | AI 改自己怎么记、怎么忘 |
| 装配 | `entries.yml` / profile | AI 改自己的结构 |

因为这些都是插件，都在同一套生命周期/服务/事件里，都能 HMR 热加载——**所以"改自己"和"装一个插件"是同一个动作**。

### P3 · 无限嵌套

插件套插件，深度不设限；**第 N 层子插件和顶层插件拥有同样的 ctx 能力**。

代码已验证：`Context.extend()` / `isolate()` / `intercept()` 创建子上下文；`isolate` 让同名服务在不同 scope 有不同实现。

**硬契约（D40）**：子 scope 必须继承 root 的 isolate，否则子树看不到宿主服务——`owner = ctx.root` 是架构修复，不是权宜之计。

示例：

```
科研工作流（插件）
├── 文献检索（子插件）
├── 实验记录（子插件）
│   ├── 记录纸生成（孙插件）
│   └── 数据拟合（孙插件）
├── 数据分析（子插件）
└── 报告生成（子插件）
```

系统不需要知道它内部有多少层——就像 Linux 不需要知道一个目录里还有多少层目录。

### P4 · 与操作系统同构（设计范式）

**核心映射**：一切皆文件 ↔ 一切皆插件/服务。

| Linux | dshiunx | 代码位置 |
|---|---|---|
| 内核（调度/决策） | AI（agent-loop） | `dsh-agent-loop` |
| 进程 | session | `dsh-session` |
| 文件系统 | storage + entries.yml | `dsh-session-persistence-jsonl` + `bundle-arch/entries.yml` |
| 一切皆文件 | 一切皆插件/服务 | `packages/dsh-*` |
| 内核态 / 用户态 | 内核 / 插件 | `cordis` / `dsh-*` |
| 窗口 | ViewEvent | 未实现（TUI 封存） |
| 窗口管理器 | LayoutTree（平铺） | 未实现 |
| 应用 | plugin | `dsh-*` |
| 包管理 | 插件加载器 | `cordis-plugin-loader` |
| shell | TUI / 命令 | 已封存 |

> "同构"是**设计语言**，不是实现目标：借用操作系统的分层、边界、可组合性来组织 AI 程序，而不是写一个 OS。

### P5 · 可管理、可控制、可优化、可创造

| 能力 | 机制 |
|---|---|
| **管理** | 每个插件有 manifest、依赖、生命周期、配置 schema（schemastery）、隔离边界（isolate） |
| **控制** | 启停、替换、裁剪（按需加载）、权限 |
| **优化** | 可观测（事件/日志/指标）、可热替换（HMR 保留状态） |
| **创造** | AI 能在运行时写插件、注册、热加载——自进化的入口 |

**"一切皆文件"真正值钱的地方**：统一接口带来统一的管理能力。

- **看**：任何时刻能问"现在有哪些插件、依赖什么、状态如何、谁在调用谁"
- **改**：插件树就是 `entries.yml`，配置就是文件，改文件 = 改系统
- **查**：会话是 append-only log，事件是流，所有行为可追溯
- **回滚**：git 管一切——插件代码、配置、决策，出问题 `git revert`
- **替换**：改一个插件，HMR 热更新，会话不断、状态保留
- **裁剪**：不要的能力直接删，内核不依赖任何具体插件，删完照样启动

### P6 · 自进化

**不是"AI 帮你写代码"，是"AI 是系统的一部分，能改造自己"。**

因为：
1. AI 是内核（agent-loop），不是应用——它能看到整个插件树
2. 插件可以被运行时创建/注册（loader 支持）
3. 改动能热加载且保留状态（HMR）
4. 所有变更可 git 回滚（安全网）

闭环：

```
AI 发现缺一个能力
  → 写一个插件（代码 + manifest）
  → 注册进插件树
  → HMR 热加载
  → 会话不中断，立刻可用
  → 不好用？git revert，回到上一版
```

这不是"AI 辅助开发"，是**系统在运行时扩展自己的器官**。而且因为插件是隔离的、可观测的、可回滚的，这种扩展是可控的——**不需要审批弹窗，靠架构本身的安全网**。

### 三层架构（依赖只能向下）

```
L0  内核        cordis：DI / 生命周期 / 服务 / 事件
L1  加载层      loader：配置树 / 嵌套 / isolate / HMR
L2  运行时插件  agent-loop / llm / session / tools / storage
L3  界面插件    LayoutTree / TUI renderer / Web renderer
L4  用户插件    第三方 / AI 生成
```

**硬规则**：L0 不知道 L1 存在；L1 不知道 L2 存在；内核不得依赖任何具体插件。

### 结构性边界（不是风险，是设计前提）

1. **内核不可自进化**：内核必须稳定到能加载下一个插件。这和 Linux 一样——用户态什么都能换，内核不能热替换自己。
2. **内核不知道"插件"之外的概念**：不知道 session、tool、model、ui。
3. **内核不做策略**：审批、沙箱、重试、压缩——都是插件。

### 风险与插件化解法

> **评估视角：按本系统（Arch Linux）评估，不按大众产品评估。**
> 本系统的优势：无权限弹窗 / 无注册表 / 用户本来就习惯"自己配置一切" / git 是日常工具。
> 因此"范围太大""没有审批""用户不会配置"这类大众产品风险，在这里不成立或可忽略。

**核心判断：没有架构上的结构矛盾。** 剩下的风险都是工程性的，而工程性风险可以用插件解决——这正是"一切皆插件"的元优势。

| 风险 | 性质 | 插件化解法 |
|---|---|---|
| 内核边界失守 | 工程性 | `boundary-check` 插件：依赖图审计、内核准入检查 |
| LayoutTree 方向错 | 工程性 | 多 LayoutTree 实现并行（TUI/Web），按需切换 |
| 自进化不可恢复 | 工程性 | `checkpoint` 插件：git 快照 + 状态回滚 |
| Node 单进程瓶颈 | 工程性 | `worker` 插件：重活下沉子进程/worker |
| 内核 vendor 漂移 | 工程性 | `upstream-diff` 插件：定期 diff 上游 |

### 与 DSH 的取舍（战略级）

| 维度 | DSH | dshiunx |
|---|---|---|
| 产品化 | Web/账户/遥测/市场 | **全砍**，只留运行时 |
| 框架与产品 | 耦合 | **内核纯净**，产品能力全插件 |
| 插件系统 | 为产品服务 | **为创造服务**（AI 可写） |
| 预设模式 | 内置 | **配置/插件** |
| 客户端 | 多客户端适配 | **TUI 优先**，Web 后做（同一 LayoutTree） |
| 审批 | 内置审批链 | **不弹审批**（pi 机制） |

## 如何验证自己做对了

### 成功判据（可验证，不是口号）

1. **内核上限**：内核代码量/依赖数有明确上限（如 < 10k 行、零产品依赖）
2. **可删除性**：删掉任意插件，系统仍能启动（内核不依赖具体插件）
3. **可替换性**：任意插件可热替换且保留状态
4. **可创造性**：AI 能在运行时创建/注册/热加载插件
5. **可观测性**：所有插件的事件、状态、依赖可查
6. **干净性**：无账户、无遥测、无插件市场、无客户端假设

### 具体验证

- **welcome**：删掉所有可选插件，`dx` 仍能完成一次完整对话
- **anything**：任意插件可叠加/移除，不影响最小窗口
- **无产品假设**：默认界面里没有审批弹窗、市场入口、账户
- **可替换**：TUI、Agent 循环、模型适配器都能换成别的实现，内核不动
- **内核干净**：`grep -r "session\|tool\|llm\|ui" packages/cordis/src` 为空
- **无限嵌套**：建一个三层嵌套的插件组，子插件能看到宿主服务
- **热替换**：改一个插件文件，进程不重启，行为变化且会话不丢
- 人看：像不像 Arch——黑屏 + login，但登录后能用；不是桌面环境
