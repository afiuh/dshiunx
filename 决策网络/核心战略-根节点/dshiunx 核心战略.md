## 为什么要做

### DSH 的理念对，但实现被产品稀释

| DSH 的理念 | DSH 的实现偏差 |
|---|---|
| 一切皆插件，智能体本身也只是插件 | 框架里塞了产品假设（Web UI、账户、遥测、插件市场、多客户端适配） |
| 核心是框架，不是某个具体功能 | 框架与产品耦合，为普适性做取舍 |
| 插件机制是创造工具 | 插件系统为产品功能服务，而不是为"创造"服务 |

**结论**：不是推翻 DSH，是**把它的理念实现得更彻底**——去掉产品包袱，让内核回到"最小、干净、可组合"。

我们要更好地实现他这个理念，最初的框架应该就像 Arch Linux 系统最初的模样一样简洁干净，其他的一切都可以插件化，这种理念实行起来，其实就和Linux系统一切皆文件的理念是同构的，在这个框架上加的所有东西都能进行精确管理控制优化还能随意创造，再加上自进化机制，这样做出来的才是能更好地实现一切皆插件的本意

### 为什么"干净"不是审美偏好

**内核脏了，插件就没法任意组合。**

内核里塞了产品假设、特殊路径、隐式依赖，每加一个插件都要考虑"会不会和内核里的某个假设冲突"。更麻烦的是版本的破坏性更新，如果内核更新插件因为版本问题就不能用了，那会非常麻烦，就很难的做到插件的规模效益，毕竟不是所有插件都会一直跟进的，如果我花了很大的成本好不容易给自己搞出来了一套最适合自己的插件组一更新好多插件都不能用了，那也太沮丧了，只有内核足够小、足够纯，有且只有一个要求那就是插件的能力，插件才能像乐高一样随便拼，AI 才能放心地写新插件，系统才能真的"一切皆插件"。

所以"像 Arch 初始安装一样干净"不是怀旧，是**为了让上面能长出的任何东西都能没有后顾之忧**。

## 要做什么

### 一句话

**做一个与操作系统同构的 AI 程序：内核像 Arch 初始安装一样干净，一切皆插件（包括 TUI 和 Agent 循环），系统能在运行中替换和创造自己的器官。**

### 不是真的做一个操作系统

dshiunx 本身仍是**一个运行在现有系统上的程序**；它与操作系统**同构**的结构是从理念推导出的架构（内核/进程/文件系统/窗口管理器/应用），要实现这样的理念就需要这样的架构，而不是实现一个 OS 去和 Windows/Linux 竞争。

DSH 的存在已经证明：**不需要新 OS，也能实现"一切皆插件"**。

### Arch 的起点：一切都要自己配

Arch 装完只有**内核 + bash + pacman**——没有桌面、没有快捷键、没有输入法、没有浏览器。然后用户自己配了 Hyprland、waybar、fcitx5-vinput、快捷键、代理、编辑器……

这些**没有一个是 Arch 的固有部分**。它们可以随时换掉、删掉、重配。系统仍然是 Arch，因为内核和包管理还在。

dshiunx 的对应起点不是"内核 + TUI + agent 循环"，而是**内核 + 加载器**。TUI、agent loop、llm、session、工具、模型、角色、布局——全是插件。

### 实现的第一阶段-内核打磨

做出可以支持我们理念的内核：

1. 最小内核
2. 一切皆插件，除了内核没有特殊插件
3. 在 2 的基础上实现除了内核一切皆可自进化
4. 拒绝垃圾的代码架构，在我们的 dshiunx 里的插件要做到最大程度的插件解耦化
5. 做到插件无限嵌套和随意联动，用简单插件的先进组合实现复杂功能而不是做一个架构垃圾的大插件
6. 显式控制和充分信息，尽最大可能拓展使用者的控制范围，不把使用者当巨婴，不做防白痴设计

### 实现的第二阶段-插件的丰富

由于我们的内核只看功能，所以当我们的内核做出来之后所有有功能的程序都可以作为我们的插件。这一阶段我们主要是要配置出最适合我们自己的 dshiunx，也是后面可以作为运行 demo 去宣传我们的项目了。

### 实现的第三阶段-应对不同需求

当我们有了名气有了使用者，可以根据不同使用者的需求做针对性的发行版。但是发行版不是固定的框架，只是提前组合了相关插件，用户还是可以随便拆，这意味着任何人都可以把自己配置出来的 dshiunx 作为发行版分享出来。

### 发行版模式

同一内核 + 不同插件组合 = 不同形态。

Arch 本身最小，但 Manjaro / EndeavourOS / Garuda 提供不同预装组合；dshiunx 的不同 profile 也能精确特化到不同人、不同需求。

**原则**：内核保持中立，不替用户做产品选择；选择权在插件组合。

## 怎么做

### 七条原则

每条按「是什么 / 为什么 / 判据 / 边界 / 反面」展开——只讲战略，不落到代码。

---

**P1 最小内核**

- **是什么**：只保留不可插件化的机制——依赖注入、生命周期、服务注册、事件分发、插件加载。其余一切能力都从内核里赶出去。
- **为什么**：内核每多一个能力，就多一条“必须兼容”的约束。内核越大，插件生态越难建立。
- **判据**：所有插件都依赖它（不是某类插件）；与具体能力无关（不知道“文件”“工具”“界面”是什么）；足够稳定（不频繁变化）。
- **边界**：TUI、Agent 循环、工具、模型适配器、会话存储、布局、角色、预设——全部不进内核。
- **反面**：为某个产品功能开特例；给某类插件留“内置”路径；在内核里写平台判断。

---

**P2 一切皆插件**

- **是什么**：工具、界面、循环、记忆、装配、角色——全部是插件，**包括 TUI 和 Agent 循环**。不存在“系统固有功能”。
- **为什么**：只有全部插件化，才能全部可替换、可裁剪、可自进化。任何“例外”都会变成不可替换的黑洞。
- **判据**：删掉任何一个插件，系统仍能启动；换掉任何一个插件，内核不用改。
- **边界**：内核本身不是插件（它是加载器）；插件可以无限多，但内核不知道它们叫什么。
- **反面**：把 TUI / agent-loop 做成“内置”；给某些插件专属注册路径、专属生命周期、专属 UI 位置。

---

**P3 无限嵌套**

- **是什么**：插件套插件，深度不设限；第 N 层子插件和顶层插件拥有**同样的能力**。
- **为什么**：复杂功能要靠组合，不能靠大插件。嵌套是“用简单插件实现复杂功能”的唯一手段。
- **判据**：三层嵌套的子插件能看到宿主服务；删掉中间层，子层仍能独立工作；新加一层不需要改内核。
- **边界**：不预设嵌套语义（内核不知道“组”是什么）；嵌套不改变插件性质（不因此获得特权）。
- **反面**：大插件（一个插件干十件事）；层级特权（深层插件能力打折）；预设“最多三层”之类的限制。

---

**P4 与操作系统同构**

- **是什么**：一切皆文件 ↔ 一切皆插件/服务。借用操作系统的分层、边界、可组合性来组织 AI 程序。
- **为什么**：OS 的架构经过几十年验证；同构能直接借用它的管理心智（权限、进程、文件、包）。
- **判据**：能用同一套工具看/改/查/回滚/替换/裁剪所有插件；新概念能对应到 OS 里的某个既有概念。
- **边界**：这是设计范式，不是实现目标——不写 OS，不和 Windows/Linux 竞争。
- **反面**：发明一套与 OS 无关的新概念；每个东西都要特殊管理；把“同构”理解成“做一个操作系统”。

---

**P5 可管理、可控制、可优化、可创造**

- **是什么**：所有东西都是同一种东西（插件/服务/文件），所以能用同一套工具处理。
- **为什么**：统一接口带来统一能力——不是靠一个管理界面，是靠“所有东西同构”。
- **判据**：**看**（插件树、依赖、状态、谁在调用谁）、**改**（配置文件即系统结构）、**查**（会话是追加日志，事件是流）、**回滚**（git 管一切）、**替换**（热更新保留状态）、**裁剪**（删掉不用的能力，系统照样启动）。
- **边界**：不依赖 GUI 管理界面；不把管理能力做成特权（人和 AI 用同一套）。
- **反面**：黑盒；只读；不可观测；管理靠“专门的管理模块”而不是靠结构本身。

---

**P6 自进化**

- **是什么**：AI 是系统的一部分，不是应用——它能写插件、注册、热加载，在运行时扩展自己的器官。
- **为什么**：这是一切皆插件的必然结果，不是附加功能。AI 能改的不只是工具，还包括界面、循环、记忆、装配。
- **判据**：AI 能在运行时创建/注册/热加载插件；改坏了能 git 回滚；改的过程中会话不中断。
- **边界**：**内核不可自进化**（必须稳定到能加载下一个插件）；自进化靠隔离、可观测、git 回滚这些架构安全网，不靠审批弹窗。
- **反面**：把 AI 当应用（只能调工具不能改结构）；用审批弹窗代替安全网；改坏了没有回滚点。

---

**P7 显式控制和充分信息**

- **是什么**：尽最大可能拓展使用者的控制范围，**不把使用者当巨婴，不做防白痴设计**。
- **为什么**：使用者是系统的主人，不是产品的用户。隐藏信息和控制权 = 剥夺能力。产品的“安全默认”往往是把人当成会犯错的小孩，代价是让所有人失去能力。
- **判据**：所有插件对人和模型都可见；所有行为可观测；所有选择可配置；不预设“安全默认”；不隐藏高级选项；出错时说清楚发生了什么，而不是拦住不让做。
- **边界**：不是“没有安全机制”——安全靠隔离、可回滚、可观测，而不是靠“不让你做”。
- **反面**：隐藏高级选项；默认限制；“你确定吗”式确认；防白痴提示；把能力藏在“专业模式”里。

---

### 三条结构性前提（不是风险，是设计前提）

1. **内核不可自进化**：内核必须稳定到能加载下一个插件。用户态什么都能换，内核不能热替换自己。
2. **内核不知道"插件"之外的概念**：不知道 session、tool、model、ui。
3. **内核不做策略**：审批、沙箱、重试、压缩——都是插件。

## 如何验证自己做对了

### 六条判据

1. **内核上限**：内核代码量/依赖数有明确上限
2. **可删除性**：删掉任意插件，系统仍能启动
3. **可替换性**：任意插件可热替换且保留状态
4. **可创造性**：AI 能在运行时创建/注册/热加载插件
5. **可观测性**：所有插件的事件、状态、依赖可查
6. **干净性**：无账户、无遥测、无插件市场、无客户端假设

## 下一级的决策节点

> 核心战略只给方向；下面两层负责「具体怎么做」和「做成什么样」。
> 划分依据：**内核模块只管「内核提供什么机制」，插件模块只管「插件怎么组织」**，两者都不越界到对方。

### 内核模块

**负责什么**

1. **职责边界**：哪些机制必须在内核里（依赖注入、生命周期、服务注册、事件分发、插件加载），哪些明确不进。每一条都要能回答「为什么它不能是插件」。
2. **准入判据的具体化**：三条判据（所有插件都依赖 / 与具体能力无关 / 足够稳定）怎么落到每个候选机制上，怎么审计。
3. **稳定性契约**：内核的 API 面有多大、什么能改、什么不能改、上游更新怎么跟、本地修改怎么记。
4. **内核的实现验证**：怎么证明「内核不知道插件之外的概念」——能删掉所有插件、能换掉任何实现、能无限嵌套而不改内核。
5. **内核内部的子机制**：依赖注入与生命周期、事件与服务、插件加载与嵌套、嵌套组、配置包含与校验、热更新、定时器、通用工具——每一个都要有独立节点。

**不负责什么**

- 不决定插件长什么样（那是插件模块）
- 不决定装配与 profile（那是计划与经验 / 装配）
- 不决定产品形态（那是核心战略的七条原则）
- 不讨论具体工具的用法（那是插件模块的工具子节点）

**判断自己越界了没有**：如果一条决策里出现了「session」「tool」「llm」「ui」这类词，它就属于插件模块，不属于内核模块。

---

### 插件模块

**负责什么**

1. **插件机制**：什么样的东西算插件、插件怎么注册、怎么被加载、怎么被替换、怎么被裁剪。机制本身要在内核里，但「怎么用这套机制」是插件模块的事。
2. **插件类型与边界**：工具、Agent 循环、上下文管理、会话与持久化、模型层、终端与沙箱——各自负责什么、不负责什么、之间怎么交互。
3. **插件指导理念**：同质（除内核外所有插件是同一性质的对象）、显式（对人和模型都可见）、可热启动（任何插件都能热重载）。
4. **组合规则**：无限嵌套怎么用、什么时候该拆成多个小插件、什么算「大插件」（一个插件干十件事 = 架构垃圾）。
5. **可观测性**：怎么让每个插件对人和模型都可见——这是 P7「显式控制和充分信息」在插件层的落地。
6. **工具家族的具体决策**：Bash、文件、搜索、LSP、技能、待办、目标、子代理、工作目录、工具注册表、超时策略、重复调用提醒——每一个都要有独立节点。

**不负责什么**

- 不决定内核机制（那是内核模块）
- 不决定战略方向（那是核心战略）
- 不决定装配（那是计划与经验 / 装配）
- 不替用户做产品选择（那是发行版 / profile）

**判断自己越界了没有**：如果一条决策需要改内核代码才能实现，它要么是内核模块的错，要么是插件机制不够——先回头查 P1 和 P3。
