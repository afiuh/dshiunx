## 1. 问题：DSH 的理念对，实现被产品稀释

### 1.1 DSH 的理念

- 一切皆插件，智能体本身也只是插件
- 核心是框架，不是某个具体功能
- 插件机制是创造工具，不是功能菜单

### 1.2 DSH 的偏差

1. **产品包袱**：Web UI、账户、遥测、插件市场、多客户端适配
2. **为普适性做取舍**：框架里塞入了产品假设（默认界面、默认流程、平台集成）
3. **框架与产品耦合**：插件系统为产品功能服务，而不是为“创造”服务

### 1.3 结论

不推翻 DSH，而是**把它的理念实现得更彻底**：去掉产品包袱，让内核回到最小、干净、可组合的状态。

## 2. 战略目标

### 2.1 一句话

**做一个与操作系统同构的 AI 程序：内核像 Arch 初始安装一样干净，一切皆插件（包括 TUI 和 Agent 循环），系统能在运行中替换和创造自己的器官。**

> 注意：**不是真的做一个操作系统**。dshiunx 本身仍是一个运行在现有系统上的程序；它与操作系统**同构**的是理念与架构（内核/进程/文件系统/窗口管理器/应用），不是实现一个 OS 去和 Windows/Linux 竞争。DSH 的存在已经证明：不需要新 OS，也能实现“一切皆插件”。

### 2.2 三个层次

| 层次 | 目标 |
|---|---|
| 内核 | 只保留不可插件化的机制：DI、生命周期、服务、事件、插件加载 |
| 插件 | 工具、界面、Agent 循环、记忆、装配——全部是插件，可替换、可创造 |
| 演化 | AI 是内核的一部分，能在运行时改造系统；内核是唯一不能自进化的部分 |

## 3. 核心原则

### P1 · 最小内核

**判据**：如果一个能力可以被插件实现，它就不进内核。

**内核准入条件**（必须全部满足）：
1. 是所有插件都依赖的机制（不是某类插件）
2. 与具体能力无关（不知道“文件”“工具”“界面”是什么）
3. 足够稳定（不能频繁变化，否则插件生态无法建立）

**内核职责清单**（穷举）：
- 依赖注入（`ctx.inject` / `provide` / `get`）
- 生命周期（fiber、effect、dispose）
- 服务注册与查找
- 事件分发（waterfall / parallel / serial / bail）
- 插件加载（由 loader 提供，loader 属于最小内核的一部分）

**明确不进内核**：TUI、Agent 循环、工具、模型适配器、会话存储、布局、角色、预设。

### P2 · 一切皆插件

包括但不限于：

| 类别 | 例子 | 是否插件 |
|---|---|---|
| 工具 | fs / bash / web / 生图 / 剪视频 | ✅ |
| 界面 | TUI / LayoutTree / Web renderer | ✅ |
| 循环 | agent-loop（怎么思考、怎么调工具） | ✅ |
| 记忆 | session / compaction / storage | ✅ |
| 装配 | entries.yml / profile / preset | ✅ |
| 角色 | persona / system prompt 片段 | ✅ |

**推论**：不存在“系统固有功能”。初始 `profiles/default` 只是一套默认装配，不是系统本身。

### P3 · 无限嵌套

- 插件可以套插件（group → group → …），深度不设限
- 嵌套的硬契约：**子 scope 必须继承 root**（`owner = ctx.root`），否则子树看不到宿主服务
- 嵌套不是语法糖，是“能力组合”的基本方式：一个“科研工作流”插件内部可以是一棵子树

### P4 · 与操作系统同构（设计范式）

**核心映射**：一切皆文件 ↔ 一切皆插件/服务。

> “同构”是**设计语言**，不是实现目标：借用操作系统的分层、边界、可组合性来组织 AI 程序，而不是写一个 OS。

| Linux | dshiunx | 本质 |
|---|---|---|
| 内核（调度/决策） | AI（agent-loop） | 系统的决策中心 |
| 进程 | session | 独立运行单元 |
| 文件系统 | storage + 配置树（entries.yml） | 状态的持久化与组织 |
| 一切皆文件 | 一切皆插件/服务 | 统一抽象 |
| 内核态 / 用户态 | 内核 / 插件 | 权限与稳定性边界 |
| 窗口 | ViewEvent | 可呈现的数据单元 |
| 窗口管理器 | LayoutTree（平铺） | 布局与组织 |
| 应用 | plugin | 能力单元 |
| shell | TUI / 命令 | 人机接口 |
| 包管理 | 插件加载器（loader） | 能力的安装与装配 |

### P5 · 可管理、可控制、可优化、可创造

统一抽象带来统一工具：

| 能力 | 具体含义 |
|---|---|
| 管理 | 每个插件有 manifest、依赖、生命周期、配置 schema、隔离边界 |
| 控制 | 启停、替换、裁剪（按需加载）、权限 |
| 优化 | 可观测（事件/日志/指标）、可热替换（HMR 保留状态） |
| 创造 | 用户和 AI 都能写插件、注册、热加载 |

### P6 · 自进化

**定义**：不是“AI 帮你写代码”，而是 **AI 作为内核的一部分，能在运行时改造系统**。

**可进化的层**：
- 能力（工具）
- 界面（TUI / LayoutTree / Web）
- 循环（agent-loop）
- 记忆（session / compaction / storage）
- 装配（entries.yml / profile）

**不可进化的层**：
- 内核（cordis）：必须稳定到能加载下一个插件
- 加载器（loader）：同上

**安全网**（不靠审批）：
- 隔离：插件边界
- 可观测：事件、日志、依赖图
- 可回滚：git 管代码、配置、决策

## 4. 架构边界

### 4.1 分层

```
L0  内核        cordis：DI / 生命周期 / 服务 / 事件
L1  加载器      loader：配置树 / 嵌套 / isolate / HMR
L2  系统插件    agent-loop / llm / session / storage / tools
L3  界面插件    LayoutTree / TUI renderer / Web renderer
L4  用户插件    第三方 / AI 生成
```

### 4.2 依赖规则

1. 只能向下依赖（L4 → L3 → L2 → L1 → L0）
2. 内核不知道任何具体插件的存在
3. 删掉任意插件，系统仍能启动
4. 内核不得依赖产品假设（账户、遥测、市场、客户端）

### 4.3 内核准入判据（操作化）

新增一个东西到内核前，必须回答：

1. 它可以被插件实现吗？→ 能，就不进内核
2. 所有插件都依赖它吗？→ 否，就不进内核
3. 它与具体能力无关吗？→ 有关，就不进内核
4. 它稳定吗？→ 不稳定，就不进内核

## 5. 成功判据（可验证）

| # | 判据 | 验证方式 |
|---|---|---|
| 1 | 内核上限 | 内核代码量、依赖数有明确上限，并纳入检查 |
| 2 | 可删除性 | 删掉任意插件，`dx` 仍能启动 |
| 3 | 可替换性 | 任意插件热替换，会话状态保留 |
| 4 | 可创造性 | AI 能在运行时创建、注册、热加载插件 |
| 5 | 可观测性 | 插件的事件、状态、依赖可查询 |
| 6 | 干净性 | 无账户、无遥测、无插件市场、无客户端假设 |

## 6. 内核中立性：产品形态由插件组合决定

内核不预设任何产品形态。下列能力**不是内核的一部分**，但都可以作为插件存在——装不装、默认开不开，由插件组合决定：

| 能力 | 在内核里？ | 作为插件？ |
|---|---|---|
| Web UI | ❌ | ✅ Web renderer 插件 |
| 插件市场 | ❌ | ✅ market 插件 |
| 账户 / 遥测 / 云同步 | ❌ | ✅ 对应插件 |
| 审批弹窗 | ❌ | ✅ approval 插件（默认不装） |
| 开箱即用体验 | ❌ | ✅ 发行版 profile（预装组合） |
| 内核实现方式 | vendor（当前） | 未来可由宿主插件承担 |

**发行版模式**：同一内核 + 不同插件组合 = 不同形态。就像 Arch 本身最小，但 Manjaro / EndeavourOS / Garuda 提供不同预装组合；dshiunx 的不同 profile 也可以精确特化到不同人、不同需求。

**原则**：内核保持中立，不替用户做产品选择；选择权在插件组合。

## 7. 当前阶段与差距

### 已完成

- L0/L1 vendor 完成（cordis / loader / group / include / hmr / timer / cosmokit / schemastery）
- 96 entries 加载，嵌套 group 跑通
- HMR 跑通：任意插件层热替换，保留进程
- TUI 插件化骨架（core / commands / overlays / keyboard）
- 自有代码类型错误 0，测试 5 个通过

### 进行中

- 去产品化（砍 arch bundle、去审批、去 Web 产品假设）
- 内核边界审计（什么还塞在内核/宿主里）

### 缺失

- **LayoutTree**（唯一缺的核心构件）
- **自进化闭环**（AI 写插件 → 注册 → 热加载 → 回滚）
- 内核边界的代码化检查（依赖规则尚未强制）
- 包管理策略的最终定论（D33 与显式 dependencies 冲突）

### 待定

- 包管理：纯 tsconfig paths，还是显式声明 dependencies（可审计），或内核零外部依赖

## 8. 风险

| 风险 | 描述 | 缓解 |
|---|---|---|
| 范围膨胀 | 系统同构的范围太大，什么都想做 | 先做 LayoutTree + TUI 平铺，验证抽象 |
| 过早抽象 | LayoutTree 还没被真实需求验证 | 先用 TUI 跑通，再抽 Web |
| 自进化安全 | AI 改坏自己的循环/界面 | 隔离 + 可观测 + git 回滚 |
| 内核边界失守 | 产品假设重新渗入内核 | 内核准入判据 + 依赖检查 |
| 性能 | 插件树过深、事件过多 | 按需加载、隔离、可观测 |
