# 决策文件执行过程（我的工作方式）

**父级**：[方法](./方法.md) · **配套**：[AI行为约束](../经验/AI行为约束.md)
**性质**：这不是给别人看的模板，是**我每个文件实际怎么走**的流程
**前提**：项目源码是 vendored 的 DSH，历史信息分散在 git / 归档 / 历史讨论里——所以流程必须按情报量分级，不能一刀切

---

## 0. 情报版图（先知道去哪找）

| 情报源 | 位置 | 能回答什么 |
|---|---|---|
| **本项目源码** | `packages/<pkg>/src/` | 实际行为（流程/分支/边界） |
| **DSH vendored 副本** | `node_modules/@deepseek-ai/<pkg>/src/` | 与本项目**逐字节一致**（diff 已验证），行为核对用这个即可 |
| **DSH 上游完整仓库** | `/mnt/data/AI自由工作区/AI参考源码/deepseek-harness/` | **设计意图**：docs/、README、示例、为什么这样设计 |
| **DSH TUI 版** | `/mnt/data/AI自由工作区/dsh-TUI/` | TUI 相关（本轮不做） |
| **git 历史** | `git log -- decisions/<路径>` / `git log -S<关键词>` | 这个决策改过几次、为什么改、踩过什么坑 |
| **归档** | `~/.pi/agent/workdir/archives/<会话>/NN_*.md` | 当时的讨论链、被否决的方案、用户原话 |
| **历史讨论** | `decisions/历史讨论/` | 早期设计讨论（框架来源/架构分层/Agent模式/TUI/运行时能力） |
| **检查记录** | `decisions/内核模块/检查计划.md` | 哪些文件查过、发现过什么错 |

**已验证的事实**（2026-10-24）：插件基础设施 / 智能体 / 工具相关包，`packages/` 与 `node_modules/@deepseek-ai/` **diff 无差异**；例外：`cordis-plugin-logger-console`（DSH 无对应包）、`bundle-arch`（本项目自建，`@dshiunx/arch`）。所以：
- 核对行为 → 看本项目源码即可（等同 DSH）
- 找"为什么这么设计" → 去**上游仓库**的 docs/README，不是看代码

## 1. 开工前：判定情报级别（决定走哪条路）

每个文件先跑三条判定，得出 L1/L2/L3：

```bash
# ① 历史热度
git log --oneline -- decisions/<文件或目录> | wc -l
# ② DSH 上游是否有对应包
ls node_modules/@deepseek-ai/<pkg> 2>/dev/null
# ③ 历史讨论/归档是否提过
grep -rl "<模块关键词>" decisions/历史讨论/ ~/.pi/agent/workdir/archives/<会话>/ 2>/dev/null | head
```

| 级别 | 触发条件 | 走法 |
|---|---|---|
| **L1 轻** | git 提交 ≤2 且 DSH 无对应包 且 无历史讨论 | 读本项目源码 → 写 → 两层验证（跳过 DSH 对照，标注"无 DSH 对应"） |
| **L2 中** | DSH 有对应包（默认情况） | L1 + 读 DSH 上游 docs/README 找设计意图 + 标注"与 DSH 一致" |
| **L3 重** | git 提交 >3 或有 fix/教训提交 / 历史讨论提过 / 归档有争议 | L2 + 读 git 提交正文 + 归档检索 + 历史讨论，把"被否决的方案"写进决策 |

**判定结果写进文件头**（一行）：`> 情报级别：L3（git 12 次提交 / 历史讨论有"第三方插件适配" / DSH 有对应包）`

## 2. 通读：按"问题清单"读，不是按文件顺序读

### 2.1 列出通读范围

```bash
# 本项目：这个决策涉及的所有源文件（不是只看入口）
find packages/<pkg>/src -name "*.ts" | xargs wc -l
```

写进文件头的通读清单（读一个勾一个）：

```markdown
> 通读清单：index.ts(939) ✅ / operations.ts(641) ✅ / install-spec.ts(123) ✅ ...
```

### 2.2 带着四类问题读（这是"灵活"的核心——问题驱动，不填格子）

| 问题类 | 读的时候找什么 | 找不到怎么办 |
|---|---|---|
| **主流程** | 输入从哪来 → 经过哪些步骤 → 输出到哪 | 说明模块边界没看清，重读入口 |
| **分支** | 每个 `if/switch/early return` 的条件与后果 | 分支太多就说明该拆文件 |
| **边界** | 默认值、空值、异常、并发、超时、重试 | 没有边界是危险信号，回头找错误处理 |
| **差异** | 与 DSH 上游设计是否一致；不一致是有意还是遗漏 | 查 git log / 决策记录，确认后写原因 |

**读的过程中只记草稿**（一行一条：`问题 → 源码位置 → 现象`），不直接写决策文件。

### 2.3 DSH 上游怎么用（L2/L3）

- **不重复读代码**（vendored 一致）
- 读 `AI参考源码/deepseek-harness/docs/` 里对应主题、包 README、示例
- 目的：拿到"设计者为什么这样拆"——这是源码里读不出来的
- 找不到文档 → 在决策里标"DSH 无文档说明，按实现推断"，不编

## 3. 组织：按问题写，不按模板填

### 3.1 文件结构的唯一硬要求

读者读完必须能回答三个问题：

1. **为什么需要这个模块**（从上层拆下来的动机）
2. **它怎么工作**（主流程 + 关键分支 + 边界）
3. **凭什么这么设计**（依据：源码/DSH 文档/历史讨论；被否决的方案）

**结构可以变**：简单的模块可以只有"动机 + 决策列表"；复杂的模块才需要框图、差异表、时序图。

### 3.2 每条决策的信息项（不是格式，是必须能回答）

| 信息项 | 说明 | 允许省略的情况 |
|---|---|---|
| 行为 | 谁在什么条件下做什么、产出什么 | 不能省 |
| 依据 | 源码 `文件:行号` / DSH docs / 历史讨论 / git 提交 | 不能省（规划项写"规划，无源码"） |
| 为什么 | 设计理由 | 不能省 |
| 不选 | 备选方案 + 否决理由 | 确实没有备选时写"无" |
| 边界 | 默认值/空值/异常/并发/超时 | 该模块确实无边界时写"无特殊边界" |

### 3.3 灵活性的边界（什么时候必须拆文件）

- 单文件对应源码 > 2,000 行 → 拆
- 通读时发现"两个独立的主流程" → 拆
- 决策条目超过 15 条且主题分散 → 拆
- **不允许**为了"看起来完整"把不相关内容塞进一个文件

## 4. 验证：三层，顺序不能换

| 层 | 只看什么 | 检查什么 | 失败信号 |
|---|---|---|---|
| **① 自洽** | 只读决策文件 | 条目间有无矛盾/重复/缺口；每条能否独立判断对错 | 两条讲同一件事（Isolate 反例） |
| **② 行为** | 只读本项目源码 | 逐条对照流程/分支/边界/默认值 | 只能对上名字，对不上行为 |
| **③ 差异** | 只读 DSH 上游（L2/L3） | 差异是有意还是遗漏；有无未登记修改 | 发现未登记的修改 |

每层单独一轮，不合并命令。第 ③ 层对 L1 文件跳过并标注。

---

## 5. 收敛判据（什么时候算完）

- [ ] 通读清单全部打勾（每个文件都从头读到尾）
- [ ] 四类问题都有对应条目，或明确写"本模块无此类"
- [ ] 每条决策的信息项齐全（依据/为什么不能缺）
- [ ] 三层验证无 ❌
- [ ] 文件头写了情报级别与依据
- [ ] 提交（commit body 写：情报级别、通读范围、发现的问题、修正内容）

**任何一项未满足 → 不算完成，不进入下一个文件。**

## 6. 不同文件的走法示例（证明"灵活"）

| 文件类型 | 例子 | 走法 |
|---|---|---|
| **纯机制、DSH 有文档** | `插件规范/形态与隔离.md` | L2：读 manager+loader 源码 → 读 DSH docs 里插件形态说明 → 写决策（形态分级 + 隔离语义 + 边界） |
| **有历史争议** | `插件演化/安装流程.md` | L3：先读 git log（安装相关提交 10+）→ 归档里找"安装审批"讨论 → 通读 index 939 + operations 641 → 写决策（含被否决的方案） |
| **纯配置/数据** | `插件分类/分类维度.md` | L1：读 `gen-catalog.mjs` + `catalog.yml` + `entries.yml` → 写（分类靠正则、6 类含义、新增包的归类规则）→ 无需 DSH |
| **生成物** | `工具具体/运行时检视工具.md` | L1：读 `tool-cordis/index.ts`(74) + 确认 `api-catalog.ts` 是生成物 → 写（工具能力 + 生成机制）→ 不分析 8,974 行数据 |
| **跨包协作** | `智能体/preset.md` | L3：读 preset + registry + mount + app-boot 的 profile 解析 → 读 DSH docs 里 preset 设计 → 画调用链 → 写 |

## 7. 我自己的检查点（写文件过程中随时问）

1. **"我现在是在读，还是在猜？"** —— 猜就停下，回去读
2. **"这条决策的依据是什么？"** —— 说不出 `文件:行号` 或文档出处 = 没依据
3. **"这个分支我写了吗？"** —— 通读时记的分支清单，逐条核对
4. **"这个文件该拆吗？"** —— 源码 >2,000 行 / 两个主流程 / 条目 >15 且分散
5. **"我是不是想快点写完？"** —— 想快 = 危险，回头补通读
