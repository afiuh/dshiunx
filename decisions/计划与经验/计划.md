# 第 2 步：决策指导代码优化

#
## 目标

按第 1 步定稿的决策改代码；用改代码得到的经验反过来修正决策。

## 子步

| 子步 | 做什么 | 验收 |
|---|---|---|
| **2.1 列缺口** | 按模块列"决策 → 代码缺口"：决策说要、代码没有；或代码做了、决策没写 | 清单每条可定位（决策路径 + 源码路径） |
| **2.2 逐模块改** | 每模块一提交，commit 引用决策路径 | 测试通过；`strict` 0 错误；依赖边界 0 违规 |
| **2.3 实践反馈** | 代码暴露的决策错误 → 立即改决策（同一提交或紧邻提交） | 决策与代码同步 |
| **2.4 字段可删性测试** | 全部改完后，测试 `dependencies` / `version` 能否删除（前提决定 1） | 可删 → 按 D33 删；不可删 → 记录原因，定新策略 |

## 执行规则

1. **不发明决策**：代码要加的东西，必须先在决策里有依据；没有就先补决策
2. **不留冲突**：决策与代码冲突时，当场改一边，不攒着
3. **每模块可回滚**：一模块一提交，出问题 `git revert`
4. **测试先行**：改之前先确认现有测试能跑（基线），改完对比

## 顺序建议（按依赖与风险）

| 序 | 模块 | 理由 |
|---|---|---|
| 1 | 内核模块（cordis 无变更，只验证） | 地基，且 rc.3 无变化，风险最低 |
| 2 | 工具机制（执行器插件化等） | 变化最大，影响面最广，先做 |
| 3 | 插件基础设施（规范/分类/装配/演化/启动） | 依赖工具机制的服务接口 |
| 4 | 具体插件（智能体 / 工具） | 上层，最后 |
| — | TUI | 不在本步范围 |

# 第 3 步：TUI 模块

#
## 为什么放最后

| 理由 | 说明 |
|---|---|
| **不是 DSH 代码** | TUI 是项目自研/借鉴其他来源，没有"上游可对照"这个基准 |
| **代码水平差** | 用户判断：比 DSH 模块差不少，直接沿用现有实现会继承问题 |
| **需要专门方法** | 不能用"对照上游 → 吸收"的流程，要先研究"参考策略"：借鉴什么、重写什么、废弃什么 |
| **不是主线** | 核心战略里界面只是插件之一（P2），不影响内核/插件体系的完备性 |

## 子步

| 子步 | 做什么 | 产出 |
|---|---|---|
| **3.1 研究参考策略** | 梳理 TUI 现状（代码量/结构/问题）、可参考的外部实现、重写 vs 修补的边界 | `计划/第3步/参考策略.md` |
| **3.2 写 TUI 决策** | 按参考策略写决策（可能整体重写 `具体插件/TUI插件/`） | 更新的决策文件 |
| **3.3 按决策实现** | 逐模块实现，每模块一提交 | 可运行的 TUI |

## 边界

- 本步启动前，TUI 相关代码**不改、不删、不重构**
- TUI 决策文件暂时保留现状（旧格式），等 3.2 统一重写
