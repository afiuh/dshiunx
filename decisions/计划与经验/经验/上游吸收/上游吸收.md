# 上游吸收

**父级**：[经验](../经验.md)

## 这个目录是什么

**研究资料区**，不是决策。每次上游（DSH）更新后，对"哪些更新值得吸收"的分析都放这里，作为修改决策的依据。

| 性质 | 说明 |
|---|---|
| 内容 | 候选清单、逐项分析、优劣对比、复查记录 |
| 不放什么 | 决策本身（决策在内核模块/插件模块） |
| 生命周期 | 一轮吸收完成后保留（作为决策的依据链），不删除 |
| 命名 | 按上游版本分目录：`rc3/`、`rc4/`…… |

## 规则

1. **分析必须落到决策**：每个"吸收"结论最终要改某个决策文件；只写分析不改决策 = 没完成
2. **判断必须引战略**：P1（最小内核）/ P6（自进化）/ P7（无版本门槛）是裁决依据，不是"上游更好"
3. **保留反例**：明确"不吸收"的项也要写清原因（例如版本管理违反 P7），避免下一轮重新讨论
4. **与路线分工**：路线（`计划与经验/路线/`）只写"做什么、什么顺序"；本目录写"研究出了什么"
5. **版本代码的剥离要防"牵一发动全身"**（2026-10-24 用户提醒）：
   - 我们**不要**版本管理代码：`engines.dsh` 判定、`updatable`、`listVersions`、`updateBundle`、version exemption、`compatibility-preflight` / `plugin-compatibility` / `profile-compatibility`
   - **但**这些代码与启动链路、安装流程、profile 解析深度耦合：直接删会断调用链，导致"版本检测不通过 / 启动失败"的报错，且报错位置往往不在删除点
   - **正确顺序**：先**旁路**（让判定恒为通过，不改调用点）→ 验证系统能跑 → 再逐个删除 → 每步测试
   - **判据**：任何"删了就跑不起来"的改动，说明还没到删除时机，回到旁路
   - **检查点**：删除前先 `grep` 调用链（例如 `compatibility-preflight` 在 `app-boot/index.ts` 的启动链上），列出所有消费者
