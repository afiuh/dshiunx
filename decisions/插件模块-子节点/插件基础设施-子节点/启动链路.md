# 启动链路

**父级**：[插件基础设施](../插件基础设施.md)

## 为什么需要

从宿主入口到插件树加载完成的整条链路：Context 创建 → Loader 安装 → profile patches → entries.yml 挂载 → 启动审计。

## 准备怎么实现

### 宏观想法

启动五步：boot → include → loader → entries → 审计——**每一步都可能失败，要能定位**。

```
boot() → mountRootInclude → loader → audit
```

**为什么五步**：启动失败要能说清是哪一步（配置/加载/审计），否则排错靠猜。


### 细节实现

1. **boot 五步**：
   - 创建 Context + diagnostics（启动日志收集）
   - 设置 `baseUrl`（配置目录）、提供 `dshHomePath`
   - `ctx.plugin(Loader)`
   - `prepare(ctx)`（宿主准备，失败 = host preparation failed）
   - `mountRootInclude(...)`（挂载 entries.yml）
   - `ctx.loader.await()` → `auditStartupEntries(...)`

2. **builtins 注册**：`cordis:include` + `cordis:group` 在 include 挂载前注册；`HostResolvedRootInclude` 用 `internal.import` 解析裸包名（`bareModuleBaseUrl`）。

3. **固定 id**：bootstrap include 的 id 固定为 `include`（启动诊断稳定，不随随机 id 变化）。

4. **必需项 vs 非必需项**：
   - `requiredStartupEntryIds` + bootstrap include = 必需项
   - 必需项失败 → 抛 `StartupError`（阻断启动）
   - 非必需项失败/缺失/pending → 只 `warn`，不阻断（成功兄弟继续运行）

5. **启动审计**：`inactiveEntries` 收集失败/缺失/pending 的 entry；`auditStartupEntries` 按必需性分级处理。

6. **错误包装**：`StartupError` 带配置路径 + 启动日志（warn/error）；其他错误按 `host preparation failed` / `plugin tree failed to load` 两阶段标注。

7. **`internal/update` 钩子**：捕获 `Fiber.update()` 丢弃的 restart promise，避免未处理 rejection（`index.ts:1221-1224`）。
8. **结算后的二次检查**（`index.ts:1234-1236`）：`await ctx.get('loader')?.await()` 之后**再查 `ctx.get('loader') === undefined`**——surface 可能在启动途中完成并销毁整棵树，此时 Loader 服务已随之消失，再读 `ctx.loader` 会抛 TypeError 覆盖"应用已按要求退出"的事实。
9. **失败清理**：catch 里先 `ctx.fiber.dispose()`（不覆盖原始 cause），再把 `StartupError` 补上配置路径与启动日志；其他错误按 stage 包装成 `${binName}: ${stage}: ${detail}${stack}`，并沿 `cause` 链找最深的 Error（`AggregateError` 展开每个错误）。
10. **diagnostics 的生命周期**：单独的 Context，比 root 活得更久（`finally` 才 dispose），用于保留异步清理阶段的错误日志（`index.ts:1208-1219`）。

## 与 DSH 对齐（2026-10-23 修正）

**之前的判断错了**：`owner = ctx.root` 是不必要的补偿。

查证 DSH：
- `agent-preset-registry` 在 patch 的 `- insert:`（**Include 的子 entry，不是 root**）
- `owner = ctx`（entry ctx）
- 服务查找是**全局 store（按 isolate 标签）**，不是 fiber 链——`reflect.ts` 的 `_getImpl` 用 `this.store[key]`

**回滚验证**：
- `owner = ctx` + `ctx.loader`（4 处 `ctx.get` 回滚）
- strict 0；`waiting for` / `cannot get property` 均为 0；启动 96 entries
- **D40 没有复现**——`owner = ctx` 就能看到宿主服务（isolate 标签相同）

**结论**：
- 与 DSH 一致：`owner = ctx` + `ctx.loader`
- `ctx.get('loader')!` 的 4 处修改已回滚
- D40 的 `owner = ctx.root` 补偿作废

## 启动日志修复

`logger-console` 原本在 `boot()` 之后挂载，导致 boot 期间的 logger 日志（HMR watching、preset 错误）丢失。改为在 `prepare` 回调里挂载（entries 挂载前），日志完整。

**这个修复暴露了 preset 的 loader 访问错误**——之前被静默吞掉。

## 启动前与进程级（不属于五步，但属于链路）

| 环节 | 实现 | 职责 |
|---|---|---|
| **环境加载** | `loadEnv` / `loadLayeredEnv`（`index.ts:121` / `:238`） | 读项目层与 Harness-home 层的 `.env`；两层都先解析再应用（一个被拒不会留下半应用）；`bootstrap-only` 变量在两个文件里都被拒绝 |
| **fail-loud** | `installFailLoud`（`index.ts:884`） | 安装 `unhandledRejection` / `uncaughtException` 处理：先写诊断再释放终端（`release`），释放有超时上限，handler 在释放期间保持安装，避免第二次 rejection 变成未捕获 |

**为什么写进链路**：这两件都在"插件树就绪"之前发生，失败时的表现与启动失败相同（进程退出 + 终端状态）。不写进来，排错时会以为是插件问题。

## 宿主入口（`bin/dx.ts`）的边界

| 入口管 | 不管 |
|---|---|
| 解析参数（`-p` / `--preset` / `--session` / `--model`…） | 任务怎么执行（agent-loop） |
| 调 `boot()` 并等待插件树 | 怎么呈现（TUI / headless） |
| 进程生命周期（心跳、信号、退出码） | 具体插件加载（loader） |

### 硬约束

1. **执行路径不依赖任何界面插件**：删掉 TUI，`-p` 仍能跑（核心战略 §5 判据 2「删掉任意插件，`dx` 仍能启动」）
2. **headless 必须独立**：`-p` 走 agent 直调，不经过 TUI
3. 界面插件只能读入口提供的上下文，**不能成为执行的前提**

### 当前实现的缺口（2026-10-24 发现）

| 现象 | 证据 |
|---|---|
| `-p` 不执行任务 | `bin/dx.ts` 只把任务写进 `DSHIUNX_TASK`；全项目 `grep` 无人读取 |
| 非 TTY 下进程不退出 | 退出交给 TUI 的 `onExit`（`6c40d6a`），TUI 检测非 TTY 后跳过 |
| 违反战略 | §5 判据 2（删 TUI 后执行链断裂）、§6（执行路径被界面绑架） |

**决策缺失**：`6c40d6a`（"dx keeps process alive; tui onExit exits"）提交 body 为空，`6cd6202` 只有技术清单——没有记录"执行路径怎么设计"，导致这个缺口从未被审查。

**待修**：入口补 headless 分支（照上游 `packages/bundle/headless`）。

### headless 路径（补法，参考 DSH）

**DSH 的做法**（`packages/bundle/headless`，包名 `@deepseek-ai/dsh-headless`）：

| 项 | 内容 |
|---|---|
| 定位 | **one-shot direct Agent driver**：不挂 Host / HTTP / browser 插件 |
| 形态 | 普通插件：`name = 'headless-runner'`，`inject = ['agentDefaultModel','agents','sessions']` |
| 依赖 | 除 inject 三项外，`--session-id` 路径还依赖 **`sessionQuery`**（`dsh-headless/src/index.ts:268-275`）；`sessionQuery` 依赖 base 的 `session-query-sqlite` backend（[会话](./运行时基础-子节点/会话.md)「查询服务」） |
| 输入 | `Config`：`task`（或 stdin）/ `sessionId` / `json` / `permissionMode` / `approvalPolicy` |
| 驱动 | 创建（或采用 `sessionId` 的）Agent → 驱动到 quiescence → flush Session |
| 输出 | stdout：最终 assistant 文本（或 `--json` 的 NDJSON）；stderr：provider reasoning |
| 退出 | `ctx.get('appExit')`——**launcher 必须提供**，插件自己不 `process.exit` |
| 失败 | `fail(io, error, json)`：结构化错误到 stderr，非零退出码 |

**参数契约（2026-10-24 补，之前写漏）**：

| 项 | 决策 | 为什么 |
|---|---|---|
| 解析层 | 必须挂 `headless-startup`（`packages/dsh-headless/src/startup.ts`，与上游逐字一致），runner `inject: [headlessStartup]`，config 用 `!!js ctx.headlessStartup.*` | `--json` 的**错误契约**（语法错误也输出 NDJSON）只能在 startup 层做；stdin/校验/help 也归它 |
| 入口职责 | `bin/dx.ts` 只把 `-p` 转成 positional（startup 不认 `-p`），并提供 `cmdlineArgs` / `appExit`（`provideCmdline`） | 入口不知道 JSON 契约，也不该知道 |
| 裁剪 | headless 模式禁用 `hmr` / `credentials` / `authorization` / `deepseek-account`；`sandbox-policy` 按 headless 配；`system-prompt.personaPrefix` 改 coding agent | 照上游 patch；一次性任务不用交互式凭证/HMR |
| 退出 | `appExit` = `process.exit`（现状）；上游是 `shutdown.shutdown`（先 dispose 再退） | 数据已 flush，清理是次要；**待补，不阻塞** |

**我们怎么补**：

1. **移植 `dsh-headless`**（新包，照上游 5 个文件：index / startup / startup-internals / runner-internals / json-stream）
2. **`bin/dx.ts` 提供 `ctx.appExit`**（`code => process.exit(code)` 的包装）
3. **按参数选执行者**：
   - 有 `-p` → 挂 `dsh-headless`，**不挂 TUI**
   - 无 `-p` → 挂 TUI（现状）
4. **入口只做选择**：删掉 `DSHIUNX_TASK` 死代码

**挂载位置（2026-10-24 修正，实测锁定）**：

headless 必须与 `agent-loop` **同 scope** 挂载——通过 bundle patch（`insert`）或 `loader.create`，**不能在 root 用 `ctx.plugin`**。

| 证据 | 值 |
|---|---|
| root 的 `agents` 实例 | factory 存在 |
| `agent-loop` 的 `agents` 实例 | 另一个对象，factory 存在 |
| headless 在 root 挂载后拿到的实例 | 第三个对象，`factory` 显示存在 |
| `agents.create()` | 用 `this.ctx` 重新 trace factory（`dsh-agent/index.ts:416-418`），最终 `requireFactory()` 抛 `no agent factory registered`（`:403`） |

**为什么**：服务按 isolate 标签分实例（[Service.md 决策 4](../../../../内核模块-子节点/依赖注入与生命周期-子节点/Service.md)、[Isolate.md](../../../../内核模块-子节点/嵌套与隔离-子节点/Isolate.md)）。headless 在 root 挂载，它的 `ctx` 与 `agent-loop` 的 scope 不同，拿到的 `agents` 实例不是注册 factory 的那个。

**上游做法**：`packages/bundle/headless/cordis.patch.yml` 用 `insert` 把 `headless-startup` + `headless-runner` 挂到 base bundle——与 `agent-loop` 同层。

**原决策的错误**：只写了"挂 headless"，没写"挂在哪一层"，默认成"boot 后 `ctx.plugin`（root）"，与服务的 scope 语义冲突。

**边界**：

| headless 管 | 不管 |
|---|---|
| 跑一个任务、输出结果、退出 | 交互、渲染、会话切换 |
| stdout/stderr 的输出契约 | 任务的语义（agent-loop） |
| 失败时的退出码 | 界面插件（完全不依赖） |

**为什么这样补而不是给 TUI 加参数**：
- 界面插件不能成为执行前提（§6）
- headless 是"执行"的一种形态，和 TUI 并列，不是 TUI 的模式
- 上游已证明可行（独立包 + `appExit` 契约）

## 执行约束（2026-10-24 headless 实施锁定）

headless 跑通（`dx -p "say hi"` → 回复 + exit 0）时锁定的三条执行约束：

| # | 约束 | 证据 |
|---|---|---|
| 1 | headless 条目必须在 entries include 树内（与 agent-loop 同层）；**不能 boot 后在 root 用 `ctx.loader.create`** | root 与 include 的 `agents` 实例 `same: false`；报 `no agent factory registered` |
| 2 | `disabled` **必须是 `!!js` 节点**；字符串形式走 `Boolean(string)`，非空即 true → 条目恒禁用 | `cordis-plugin-loader/src/config/entry.ts:93-96`（只有 `isJsExpr` 才求值） |
| 3 | `!!js` 求值域是 `with (ctx) { eval(expr) }`：`ctx` 属性优先，未命中走全局作用域——**`process` 可达**（已实测 + 上游 patch 用 `!!js process.env.DSH_PERMISSION_MODE`） | `cordis-plugin-loader/src/config/utils.ts:5-9` |

**入口分工**：`bin/dx.ts` 只把 `headless` / `task` 放进 `profileContext`；挂哪个执行形态由 entries 的 `disabled` 决定。

**验证**：

- `dx -p "reply with just: ok"` → stdout 有回复、退出码 0、**无 TTY 也能跑**
- `dx -p "..." --json` → NDJSON 事件流
- 删掉 TUI 包后 `dx -p` 仍能跑（§5 判据 2）

## 边界

| 启动链路管 | 不管 |
|---|---|
| 从入口到插件树就绪的**顺序与失败分级** | 单个插件能否加载（loader） |
| 配置路径、env、baseUrl 的确定 | profile patch 怎么组合（装配） |
| 必需项 / 非必需项的阻断策略 | 插件运行时的行为 |
| 启动日志的收集与错误包装 | 进程退出后的终端恢复细节（fail-loud 内部） |

**一句话**：启动链路回答"系统怎么从零到能跑，失败时怎么说清楚"，不回答"插件怎么工作"。
