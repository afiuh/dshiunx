# 插件装配

**父级**：[插件基础设施](../插件基础设施.md)

## 为什么需要

插件怎么组合成系统：profile、entries、按需加载、裁剪、预设。

## 准备怎么实现

### 宏观想法

插件装配：profile + bundles + entries（分层 + 索引）——**多产品/多发行版**复用同一套插件。

```
profile.yml → bundles → entries.yml
```

**为什么分层**：单一 entries 不能复用/多产品；分层 + 索引（catalog）兼顾简单和复用。

### 细节实现

1. **profile**：第一版一个 `profiles/default/`（历史决策）。
2. **entries.yml**：配置树，所有插件通过 Include 挂载（统一挂载）。
3. **按需加载**：`disabled` 条件（`!!js` 表达式）+ loader 的 `create` / `remove`。
   - **必须用 `!!js` 节点**：字符串形式走 `Boolean(string)`，非空即 true → 条目恒禁用（2026-10-24 实测）
   - 求值域：`ctx` 属性优先，未命中走全局作用域（`process` 可达）；入口可用 `profileContext` 或 `process.env` 传执行形态
   - **按执行形态选择挂载集合**：headless（`-p`）不挂 TUI 组，TUI 模式不挂 headless-runner；互斥由 `profileContext.headless` 决定（`!!js` 条件）
4. **裁剪**：不需要的插件直接删（entries 条目），不留 disabled。
5. **预设**：preset（Standard / PTC / Minimal / Creator）是“插件组合的预设”，通过 `agent-preset` 挂载。
6. **启动链路**：见 [启动链路](./启动链路.md)。

## 官方清单与装配代码分离（rc.3 吸收）

**变更**：上游把"安装自带的 bundle 清单"从 `app-boot` 拆到独立包 `util/official-bundles`。

| 内容 | rc.3 位置 | 性质 |
|---|---|---|
| 安装自带的 bundle 名称（选中 / 提供 / 按需安装 / 退役） | `util/official-bundles/bundles.ts` | 数据 |
| 默认 profile 模板（`PROFILE_TEMPLATES` / `DEFAULT_PROFILE_BUNDLES`） | 同上 | 数据 |
| 官方按需目录 | `catalog.generated.ts` | **生成物**（`gen-official-bundle-catalog`） |
| plugin-manager 保护 / 隐藏 / 排序 / 实验性标记的包名 | `plugin-manager.ts` | 数据 |
| 应用这些清单的代码（profile 解析、启动、装配） | `app-boot` | 逻辑 |

**为什么拆**：数据与应用分离。`plugin-manager` 只需要"清单"（保护哪些包、有哪些官方 bundle），不该因此依赖整个 `app-boot`（5,372 行的启动代码）。这符合 P1——减少不必要的耦合。

**我们的现状**：清单全在 `dsh-app-boot`（`profile.ts:179/213/223`、`official-bundles.ts`），`dsh-plugin-manager` 直接 import app-boot。

**吸收结论**：拆出独立清单包；`plugin-manager` 依赖清单，不依赖启动代码。

## 与 DSH 的差异：装配方式（详细对比）

### DSH：bundle / patch 分层

```
base bundle (cordis.patch.yml)
  → web-app bundle (patch)
    → preset patch (standard / ptc / minimal / cordis)
      → user patch (profile/cordis.patch.yml)
```

- 每层是 patch（`insert` / 覆盖 / `disabled`）
- 最终配置 = 所有 patch 叠加
- 可以 dump 出最终 entries

### 我们：单一 entries.yml

```
entries.yml（所有插件 + preset 配置）
```

- 一个文件，直接挂载
- 没有分层

### 对比

| 维度 | DSH（bundle/patch） | 我们（单一 entries.yml） |
|---|---|---|
| 配置集中度 | 分散（多文件） | **集中（一个文件）** |
| 分层 / 复用 | ✅ 可以组合 bundle | ❌ 复制整个文件 |
| 覆盖 / 裁剪 | ✅ patch 按 id 覆盖 | ⚠️ 手动改 |
| 调试 | ⚠️ 需要 dump 最终配置 | ✅ 直接看文件 |
| 多产品 | ✅ 同一 bundle 组合不同产品 | ❌ 每个产品复制 / 改 |
| 插件市场 | ✅ bundle 可发布 | ❌ 无 |
| 根级服务位置 | ✅ 天然正确（base 顶层） | ⚠️ preset registry 在 entry 层 |

### 判断

**短期（单产品）**：我们的简单，够用。
**长期（多产品 / 插件市场 / 自进化）**：DSH 的分层更合适。

**但两者可以结合**：用“生成”机制——

- 源：base / preset / user 分层
- 生成：`entries.yml`（单一文件）
- 好处：保留简单性 + 分层能力

### 改进方案：分层 + 集中索引（用户提出）

**思路**：采用 DSH 的分层（bundle/patch），但加一个“集中索引”文件——两者兼顾。

```
catalog.yml          ← 集中索引：所有插件（id / name / 类别 / 来源）
bundles/
├── base/            ← 基础层（运行时 + 工具）
├── web-app/         ← Web 层（未来）
└── presets/         ← preset 层（standard / ptc / minimal / creator）
profiles/
└── default/         ← 发行版：选择哪些 bundle
```

| 文件 | 职责 |
|---|---|
| `catalog.yml` | **索引**：有哪些插件、属于哪类、来源；不是最终配置 |
| `bundles/*` | **分层 patch**：每层插入/覆盖插件（DSH 式） |
| `profiles/*` | **发行版**：选择 bundle 组合（像 Arch 的不同发行版） |
| 生成器（可选） | `catalog + bundles + profile → entries.yml` |

**与 DSH 的差异**：DSH 只有 bundle/patch，没有集中索引；我们加 `catalog.yml`——可查、可组合、可生成。

**发行版类比**：
- Arch：内核 + 包管理，不同发行版（Manjaro / EndeavourOS）选择不同预装
- 我们：内核 + 插件，不同 profile 选择不同 bundle 组合

**可行性**：可行。`applyEntryPatches` 已支持 patch 叠加；`catalog.yml` 只是索引，不参与运行时；生成器可选（loader 也可以直接应用 patch）。

## 边界

| 装配管 | 不管 |
|---|---|
| 插件怎么组合成系统（层、顺序、覆盖） | 插件本身是什么（[插件规范](./插件规范.md)） |
| bundle / profile 的选择与生成 | 插件运行时的行为（各具体插件） |
| patch 的应用顺序与去重 | 单个插件的内部实现 |
| 生成物（`entries.yml` / `catalog.yml`） | 运行时加载（loader，见[内核模块-子节点/插件加载](../../内核模块-子节点/插件加载.md)） |

**一句话**：装配回答"哪些插件、按什么顺序、以什么配置进入系统"，不回答"插件怎么做"。

## 验证

- **层顺序决定覆盖**：`composeEntries(layers)` 用 `layers.flat()` 保序，后层的同 id patch 覆盖前层（`profile.ts:816-822`）
- **不改输入**：`structuredClone(layers.flat())`（`profile.ts:818`）——调用方的 patch 对象不被修改
- **从空开始**：`applyEntryPatches([], ...)`（`profile.ts:819`）——第一层也是 patch，没有"隐式基础配置"
- **生成物一致**：`npm run build:entries` 产出的 `entries.yml` 与手写版 `diff` 为 0（实施状态已记录）
- **索引不参与运行时**：`catalog.yml` 只由 `gen-catalog.mjs` 生成与读取，loader 不读它

**代码状态**：rc.2 的官方清单（`PROFILE_TEMPLATES` / `DEFAULT_PROFILE_BUNDLES` / `OPTIONAL_BUNDLES`）在 `dsh-app-boot`，未拆出独立清单包。待第 2 步拆分。

## 教训：转写 DSH 配置必须保留 `!!js`（2026-10-24）

`e5c5d1c` 从 DSH 的 `base/cordis.patch.yml` 转写 `entries.yml` 时，漏了 `bash-sandbox` 的 `!!js` 标签：

```yaml
# DSH 原版
disabled: !!js process.platform === 'win32'
# 转写后（错）
disabled: process.platform === 'win32'
```

**后果**：字符串恒真 → `disabled` 恒 true → 插件不加载 → 依赖它的服务（`shell`）缺失 → 下游工具（`tool-bash`）waiting。

**规则**：
1. 从 DSH 转写 YAML 时，`!!js` 标签必须原样保留
2. 转写后跑一次启动验证（`verify-presets` / `dx`），确认关键服务（`shell`/`sandbox`/`subprocess`）已提供
3. 不要只对照“条目 id 一致”，要对照“`!!js` 表达式也一致”
