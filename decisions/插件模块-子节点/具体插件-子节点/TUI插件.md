## 准备怎么实现（核心决策 + 为什么）

### 细节实现

1. TUI 是插件（`@dshiunx/tui`），通过 `tui` group 挂载
2. 状态管理用 Zustand（`tui-store`），不放在 TUI 插件内
3. TUI 只读状态 + 渲染，不修改业务（边界）
4. `dsh-tui`（20 万行）是参考源码，不启用

| 决策 | 选了什么 | 不选什么 | 为什么 |
|---|---|---|---|
| 形态 | `tui` group（`cordis:group`） | 单个大插件 | 一切皆插件（P2），可裁剪 |
| 状态 | `tui-store`（Zustand） | 放在 TUI 内 | 状态与渲染解耦（P4） |
| Chat | **重写屏幕**（`ChatView` + 组件分层） | 拆 7162 行单体 | 单体屏幕无法拆（D53） |
| 来源 | 参考 `dsh-tui`（20 万行） | 直接复用 | 保留功能不保留结构 |
| 优先级 | **先做**（界面最好做） | 战略优先 | 工程顺序，不是战略（D46 修正） |

## 背景与参考策略（来自 2026-10-23 盘点）

TUI 的来源是 `dsh-TUI` 项目（参考源码，20 万行，不参与运行），代码水平不高：

| 问题 | 数据 |
|---|---|
| 单文件膨胀 | `Chat.tsx` 7556 行、`PromptInput.tsx` 4000+ 行 |
| 状态堆叠 | 64 个 `useState`、35 个 `useEffect`、44 个 `useCallback` |
| 组件堆积 | 197 个组件合并进一个包 |
| 解耦后残留 | 14 个空回调、ChatStore 字段缺失、`AnyMessageList as any` 绕行 |

**策略（第 3 步用）**：
1. **参考功能，不参考结构**——功能保留，结构重新设计
2. **解耦后重新审视**——`packages/tui` 是从 Chat.tsx 抽出来的，不是干净插件
3. **不要照抄**——7556 行的 Chat.tsx 是反面教材
