## 为什么需要

TUI 是**一个 renderer 插件**（和 Web renderer 并列），不是系统界面。登录后的默认界面是 [Shell](./Shell插件.md)；TUI 通过 `tui` 命令打开，像在 Arch 里打开 `htop`——退出 TUI 回到 shell。

> 定位（2026-10-24 修正）：TUI 不承载系统，只承载对话。它注册 `tui` 命令，打开时接管终端，退出时交还 shell。

## 准备怎么实现（核心决策 + 为什么）

### 细节实现

1. TUI 是插件（`@dshiunx/tui`），通过 `tui` group 挂载
2. 状态管理用 Zustand（`tui-store`），不放在 TUI 插件内
3. TUI 只读状态 + 渲染，不修改业务（边界）
4. `dsh-tui`（20 万行）是参考源码，不启用

| 决策 | 选了什么 | 不选什么 | 为什么 |
|---|---|---|---|
| 形态 | `tui` group（`cordis:group`） | 单个大插件 | 一切皆插件（P2），可裁剪 |
| 状态 | `tui-store`（Zustand） | 放在 TUI 内 | 状态与渲染解耦（P4） |
| Chat | **重写屏幕**（`ChatView` + 组件分层） | 拆 7162 行单体 | 单体屏幕无法拆（D53） |
| 来源 | 参考 `dsh-tui`（20 万行） | 直接复用 | 保留功能不保留结构 |
| 优先级 | **先做**（界面最好做） | 战略优先 | 工程顺序，不是战略（D46 修正） |

## 已知问题：headless（`-p`）模式不执行任务

| 项 | 内容 |
|---|---|
| 现象 | 非 TTY 下 `dx -p "..."` 启动后挂起：任务不执行，进程不退出 |
| 根因 | `bin/dx.ts` 的 `-p` 只把任务写进 `DSHIUNX_TASK`；执行完全依赖 TUI 插件读它。非 TTY 时 TUI 打印 `non-interactive host detected` 后跳过，任务没人执行，`bin/dx.ts` 停在 `await new Promise(...)` 等 SIGINT/SIGTERM |
| 影响 | 无法用 `-p` 做 headless 验证（对话、工具执行链） |
| 归属 | **TUI 模块**（第 3 步大重构时处理：headless 路径应独立于 TUI） |
| 临时方案 | 用 tmux 提供 TTY：`tmux new -d 'node --import tsx bin/dx.ts -p "..."'`，再 `capture-pane` 看输出 |
| 发现 | 2026-10-24（执行器插件化验证时） |

**注意**：这不是 TUI 的 bug，是 `-p` 模式缺独立执行路径——`bin/dx.ts` 把"执行任务"和"呈现界面"绑在了 TUI 上。重构时应拆开。
