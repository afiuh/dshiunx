## 1. 三步计划

### 第 1 步：用新信息打磨决策网络

**目标**：让决策网络吸收 DSH rc.3 里对我们有用的功能优化，并据此修正已有决策。

| 子步 | 做什么 | 产出 | 验收 |
|---|---|---|---|
| **1.1 筛选** | 从 rc.3 的 6,360 文件变更里，筛出"功能优化"类变更；排除 locale / 测试 / 文档 / 网站 / 产品包袱（Web UI、账户、遥测、市场 UI） | `decisions/上游吸收/候选清单.md`（按模块分组，每条一句：改了什么、为什么可能有用） | 每条候选有源码路径；排除项写明理由 |
| **1.2 详细研究** | 每个候选：① 完整读上游实现 ② 对照我们的决策（现在怎么写的）③ 对照我们的源码（现在怎么实现的）④ 分析优劣（上游好在哪 / 我们的约束是什么） | `decisions/上游吸收/分析/<模块>.md`（每项：吸收 / 改造吸收 / 不吸收 + 理由 + 影响面） | 判断必须引 P1/P6/P7；不得只写"上游更好" |
| **1.3 优化决策网络** | 按分析结果改决策文件：新增 / 修改 / 删除；冲突项按核心战略裁决 | 更新的 `decisions/` | 决策与源码一致，或明确标"待改代码"；无 P7 违规 |
| **1.4 全局复查** | 用 `决策文件执行过程.md` 的三层验证抽查改动过的文件 | 复查记录 | 自洽 / 行为 / 差异三层无 ❌ |

**研究时的硬约束**：
- **P7 优先**：任何版本检查、版本管理、兼容性门槛一律不吸收（`engines.dsh`、`updatable`、`listVersions`、`updateBundle`、version exemption）
- **P1 最小内核**：能被插件实现的能力不进内核（例如 plugin-market 只能作为插件）
- **P6 自进化**：优先吸收"让系统更能自我改造"的结构（执行器插件化就是典型）
- **产品包袱不吸收**：Web UI、账户、遥测、客户端适配

**已知的高价值候选**（1.1 的起点，需 1.2 逐项确认）：

| 候选 | 位置 | 初判 |
|---|---|---|
| 工具执行器插件化（`ToolExecutor` + native / ptc） | `core/tools/src/executor.ts`、`core/tool-executor-*` | 吸收（P6 典型） |
| batch 调度（exclusive 屏障 / 有界滚动池 / 启动前重分类） | `core/tools/src/batch.ts` | 吸收 |
| 执行流水线（pre/post 决策、取消、结果结算） | `core/tools/src/pipeline.ts` | 吸收 |
| JSON Schema 子集（共享给 outputs / PTC / subagent / workflow） | `core/tools/src/json-schema.ts` | 吸收 |
| agent 生命周期统一（`initializeAgent`） | `core/agent-loop/src/index.ts` | 吸收 |
| 模型选择持久化投影（默认 effort 不落盘） | `core/agent/src/model-selection.ts` | 吸收 |
| token 计量可重建缓存 | `llm/token-meter/src/measurement-projection.ts` | 吸收 |
| HTTP 抓取（同源重定向 / 匿名 / 代理） | `web/web-fetch-http/src/provider.ts` | 吸收 |
| plugin-market（索引 / 搜索 / 详情 / 仓库缓存） | `boot/plugin-market/` | 作为插件，不进内核 |
| 插件版本管理（`versions.ts` / `updatable` / `updateBundle`） | `boot/plugin-manager/` | **不吸收**（P7） |
| 兼容性判定（`engines.dsh` / exemption / preflight） | `boot/app-boot/`、`boot/plugin-manager/` | **不吸收**（P7） |

### 第 2 步：决策指导代码优化

**目标**：按第 1 步定稿的决策改代码；用改代码得到的经验反过来修正决策。

| 子步 | 做什么 | 验收 |
|---|---|---|
| 2.1 | 按模块列"决策 → 代码缺口"清单（决策说要，代码没有；或代码做了，决策没写） | 清单每条可定位 |
| 2.2 | 逐模块改代码，每模块一提交（commit 引用决策路径） | 测试通过；`strict` 0 错误；依赖边界 0 违规 |
| 2.3 | 代码暴露的决策错误 → 立即改决策（同一提交或紧邻提交） | 决策与代码同步 |
| 2.4 | 全部改完后，测试 `dependencies` / `version` 字段能否删除（前提决定 1） | 可删 → 按 D33 删；不可删 → 记录原因，定新策略 |

### 第 3 步：TUI 模块（前两步完成后）

**目标**：TUI 不是 DSH 写的，代码水平差，需要专门方法。

| 子步 | 做什么 |
|---|---|
| 3.1 | 研究"参考策略"：TUI 该借鉴什么、重写什么、哪些直接废弃 |
| 3.2 | 按新策略写 TUI 决策 |
| 3.3 | 按决策实现 |

**为什么放最后**：TUI 与 DSH 模块的代码质量、设计来源都不同，用同一套"对照上游"方法会失效；且 TUI 不是核心战略的主线（P2 里界面只是插件之一）。
