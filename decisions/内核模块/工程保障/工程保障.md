**父级**：[内核模块](../内核模块.md)

## 准备怎么实现

### 宏观想法

内核是 vendor 的代码，质量靠**工具链**保证：类型严格、依赖边界、测试、API 契约、差异登记。

```
类型（tsc strict）→ 依赖边界（脚本）→ 测试（24 个）→ API 契约（文档）→ 差异（diff 登记）
```

### 细节实现

1. **类型**：`tsconfig.core.json` 开 `strict: true`，`npx tsc --noEmit` 检查
2. **依赖边界**：`scripts/` 检查内核不 import 插件（`kernel-no-plugins`）
3. **测试**：`tests/`（24 个：framework/loader/hmr/kernel）
4. **API 契约**：`API契约.md`（公共 API 清单）
5. **差异登记**：与 DSH 的 `diff` 记录（有意修改 vs 无差异）
6. **健康心跳**：`bin/dx.ts` 写 `/tmp/dshiunx-heartbeat`

## 历史判断验证（2026-10-23 新增）

**历史决策可能记录的是“当时的判断”，不是“事实”。**

| 问题 | 表现 | 处理 |
|---|---|---|
| **历史判断误导** | D40 记录“DSH 的 preset registry 在 root 层”，实际在 Include 里 | 查机制层（`reflect.get` 的查找方式），不只看位置 |
| **补偿不必要** | `owner = ctx.root` 是补偿，回滚后 D40 不复现 | 先确认 DSH 的做法，再决定是否补偿 |
| **数据清洗遗漏** | 插件模块的历史决策没清洗，导致沿用错误判断 | 清洗范围要覆盖所有模块（内核/插件/历史讨论） |

**规则**：
1. 历史决策引用前，先验证机制层（代码/DSH 源码）
2. 补偿前，先确认“不补偿是否真的不行”
3. 数据清洗要覆盖所有模块，不只当前正在做的模块
