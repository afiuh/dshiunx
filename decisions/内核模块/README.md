# 内核模块

**父级**：[核心战略](../核心战略.md)

## 这个模块负责什么

把内核做干净、做小、做稳：只保留不可插件化的机制，让上层的一切都能被插件替换。

## 这一级拆成哪几个子模块

> 分组：前 7 个是**运行时机制**（内核提供什么能力）；第 8 个是**工程保障**（怎么保证内核做对）。

| 子模块 | 负责什么 |
|---|---|
| [依赖注入与生命周期](./依赖注入与生命周期/README.md) | Context / Fiber / Effect / Service / Registry / Reflect：服务怎么注册、查找、随生命周期创建和销毁 |
| [事件系统](./事件系统/README.md) | waterfall / parallel / serial / bail：插件之间怎么通信 |
| [日志](./日志/README.md) | `ctx.logger`：级别、格式化、导出 |
| [时间与调度](./时间与调度/README.md) | `ctx.setTimeout` / `setInterval` / 防抖：生命周期与 HMR 的时间基础 |
| [插件加载](./插件加载/README.md) | loader / include / 配置校验：配置树怎么读、模块怎么 import、插件怎么实例化 |
| [嵌套与隔离](./嵌套与隔离/README.md) | group / isolate / scope / EntryTree：插件怎么套插件、服务怎么隔离、子 scope 怎么继承 root |
| [热更新](./热更新/热更新.md) | HMR：文件变更怎么检测、依赖图怎么分析、模块怎么替换、状态怎么保留 |
| [工程保障](./工程保障/README.md) | **非运行时机制**：类型严格性、依赖边界、测试策略、API 文档、差异登记 |

## 审查顺序（按审查价值，不是按实现依赖）

代码已存在（vendored 的 cordis / loader / hmr），本阶段是**审查已有代码、找优化点**，不是从零实现。

**审查价值 = 复杂度 × 被 bug 咬过的概率 × 改动影响面。**

| # | 子模块 | 复杂度 | 历史问题 | 影响面 |
|---|---|---|---|---|
| 1 | 插件加载 | 高（loader + entry + tree + include） | 依赖链、config 必填、base 路径 | 全局 |
| 2 | 嵌套与隔离 | 中（group / isolate / tree） | D40 scope 不可见 | 全局 |
| 3 | 热更新 | 高（依赖图 + reload） | 刚修完，可能有遗留 | 开发体验 |
| 4 | 依赖注入与生命周期 | 最高（fiber 754 行、reflect 418） | `ctx.get` strict、PENDING 服务 | 全局 |
| 5 | 事件系统 | 中（352 行） | 少 | 中 |
| 6 | 日志 | 低（271 行） | 少 | 低 |
| 7 | 时间与调度 | 低（1 文件） | 少 | 低 |
| 8 | 工程保障 | 持续项 | — | 全局（质量） |

实际顺序可以调整；重点是按“哪里最可能有问题”排，不是按依赖排。

## 审查方法：三向对照

每个模块的审查，不是“读代码找感觉”，而是三向对照：

| 对照 | 看什么 | 产出 |
|---|---|---|
| **决策 vs 我们的代码** | 决策写了代码没做 / 代码做了决策没写 / 两者冲突 | 缺口、隐式行为、待决策 |
| **我们的代码 vs DSH 成熟代码** | 我们改了什么、删了什么、简化了什么 | 修改点清单、是否引入问题 |
| **决策 vs DSH 代码/文档** | DSH 的实现是否更成熟、能否借鉴 | 优化点、可借鉴的设计 |

**对照源**：

- 我们的代码：`packages/cordis*`
- DSH 源码：`/mnt/data/AI自由工作区/AI参考源码/deepseek-harness/vendor/{cordis,loader,group,include,hmr,logger-console}`
- DSH 文档：`/mnt/data/AI自由工作区/AI参考源码/deepseek-harness/docs/cordis-api`、`docs/cordis-tutorial`

**注意**：DSH 里有版本/兼容性检测模块（`dsh-app-boot/compatibility-*`），对照时**不要引入**（P7）；但 DSH 的 `vendor/cordis` 是内核本体，是主要对照对象。

## 审查标准：内核不留技术债

内核是唯一不能自进化的部分，必须打磨到最优。审查产出**只有两类**：

1. **改**——代码与决策不一致、与 DSH 有未登记的差异、有隐式行为没写进决策
2. **设计前提**——确认是边界条件，记录在案（不是“待办”）

**没有“建议改”“以后再说”“低优先级”**。内核里的每一处差异，要么现在消除，要么明确写成设计前提。

## 审查阶段

| 阶段 | 做什么 | 产出 |
|---|---|---|
| **阶段一：静态审查（现在）** | 三向对照（决策 / 代码 / DSH），逐模块走完 | “改”和“设计前提” |
| **阶段二：动态验证（整体代码完成后）** | 压测：深层嵌套、高频 HMR、大量并发 entry、长会话 | 针对具体模块的修改 |

压力测试需要整体代码，留到阶段二；阶段一先把静态差异清零。

## 明确排除（DSH 有，但我们不要）

| DSH 模块 | 为什么排除 |
|---|---|
| `dsh-app-boot/compatibility-preflight` | 版本/兼容性预检，违反 P7 |
| `dsh-app-boot/plugin-compatibility` | 插件兼容性检查，违反 P7 |
| `dsh-app-boot/profile-compatibility` | profile 兼容性检查，违反 P7 |
| `dsh-app-boot/package-meta` / `official-bundles` | 包版本元数据 |
| 任何 `engines` / `peerDependencies` 版本约束 | 版本门槛，违反 P7 |

**注意区分**：`loader/internal.ts` 的 `version: 'v1' | 'v2'` 是 **Node ESM loader 的 API 形状适配**（选择正确的调用方式），不是“版本不对就拒绝运行”——保留。

## 这一级不回答的问题

- 每个子模块内部怎么实现 → 子模块自己的 `README.md`
- 插件有哪些类别、怎么装配 → [插件模块](../插件模块/README.md)

## 硬约束

- 内核不知道任何具体插件的存在
- 删掉任意插件，内核仍能启动
- 内核不得依赖产品假设（账户、遥测、市场、客户端）
- 插件加载**不做版本验证**：有功能就能接（见核心战略 P7）
- 内核准入判据见[核心战略 P1](../核心战略.md)
