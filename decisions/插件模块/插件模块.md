# 插件模块

**父级**：[核心战略](../核心战略.md)

## 这个模块负责什么

把插件体系做自由、可组合、可自进化。

## 这一级拆成两个子模块

| 子模块 | 负责什么 |
|---|---|
| [插件基础设施](./插件基础设施/插件基础设施.md) | 怎么管理插件：规范、分类、装配、演化、启动链路 |
| [具体插件](./具体插件/具体插件.md) | 具体搞哪些插件：智能体、工具、界面 |

## 明确排除（DSH 有，但我们不要）

与 [内核模块的排除清单](../内核模块/内核模块.md) 对称，插件层同样不做版本门槛：

| DSH 能力 | 为什么排除 |
|---|---|
| `app-boot` 的 `compatibility-preflight` / `plugin-compatibility` / `profile-compatibility` | 版本/兼容性检查，违反 P7 |
| `plugin-manager` 的 `engines.dsh` 判定、`incompatible-version` 拒绝、version exemption | 版本门槛，违反 P7 |
| `plugin-manager` 的 `updatable` / `listVersions` / `updateBundle` | 版本管理，服务于版本号而非结构契约 |
| 插件 manifest 的 `version` / `compatibleWith` / `engines` 字段 | P7 明令禁止 |

**判断依据**：[核心战略 §P7](../核心战略.md)——插件与内核只靠结构契约（`name` + `apply` + `inject` / `provide`），不看版本号。

**当前代码状态**：上述能力仍随 vendor 带进来，属于**待剥离遗留**，不是我们的设计。
剥离时保留结构校验（`not-bundle` / `ambiguous-install` / patch 可读性），只删版本判定。

**历史依据**：[D33 去包管理器化](../历史讨论/框架来源/包管理与依赖/去包管理器化.md)——发布元数据（version/peer/dependencies）导致旧版 404，已删过一遍；vendor 新模块又带回来了。

## 后续加插件

在 `具体插件/` 下对应类别加文件夹（比如 `具体插件/新类别/README.md`），不需要改本文件。
