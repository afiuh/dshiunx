## 为什么需要

插件不是从天上掉下来的——它得先"进得来"。父级 [插件演化](./插件演化.md) 拆出四件事：来源与安装、启停与版本、AI 写插件、热加载与回滚。本文只解决第一件：

- 用户/AI 说"装这个插件"，系统怎么把一个包变成 profile 里能跑的插件？
- 装失败了，profile 会不会被写坏？
- 装的是私有源/本地目录/GitHub 仓库，行为一样吗？

## 准备怎么实现

### 宏观想法

一次安装是**"快照 → 试装 → 校验 → 激活"**四段，任一段失败都回到快照：

```
installBundle(spec)
  ├─ 0. 前置：spec 解析 → 拒绝空/-开头 → HMR 下已安装则拒
  ├─ 1. 快照：package.json + pnpm-lock.yaml 读入内存
  ├─ 2. 试装：GitHub 预检 → registry 计划逐个 pnpm add（每次前恢复快照）
  │     └─ 失败 → 记录 pendingBuilds → 恢复快照 → 抛错
  ├─ 3. 校验：唯一新增依赖 → 必须是 bundle → 兼容性 → patch 可读
  └─ 4. 激活：写 profile bundles → reload（HMR 立即 / 无 HMR 报告 restart-required）
```

**为什么是"快照 + 恢复"而不是"事务"**：pnpm 是外部进程，它自己改 `package.json`、`pnpm-lock.yaml`、`node_modules`，没有事务接口。能可靠回滚的只有"安装前把文件读进内存、失败时原子写回"（`RESTORED_FILES`，`index.ts:81`）。`node_modules` 不恢复——下载的包留在磁盘上不伤害正确性，只是浪费空间；重新安装的代价比重下更大。

**为什么"装完再校验是不是 bundle"**：registry spec 在装之前可以用 `pnpm view` 读到 manifest，但 git/tarball spec 的包只有 pnpm 拉下来才知道。所以校验分两处：能预检的预检（避免下载 + 执行 build script），不能预检的装后校验并回滚。

### 细节实现

#### A. 主流程

1. **spec 只有四种形态，path 必须绝对**
   - 依据：`install-spec.ts:69-97`（`parseInstallSpec`）
   - 形态：`registry`（包名 + 可选 range）/ `path`（绝对目录）/ `tarball`（`.tgz`/`.tar.gz`）/ `git`（shorthand、git URL、托管仓库 URL）
   - 边界：相对路径直接拒绝——`install-spec.ts:78` 的理由是"Host 的工作目录对在浏览器里输入的人没有意义，相对 profile 解析会指到 profile 内部"
   - 为什么不用"什么都交给 pnpm 判断"：pnpm 对非法 spec 的报错不可分类（`ERR_PNPM_*` 之外还有 git 的 stderr），先自己解析才能给出 `invalid-spec` 这种可操作错误

2. **安装前 inspect：能读的 manifest 先读**
   - 依据：`index.ts:408-486`（`inspect`）、`operations.ts:626-641`（`viewProfilePackage`）
   - registry spec → `pnpm view <spec> name version description dsh --json`，在 profile 目录跑（继承 `.npmrc` 的 registry/proxy/认证）；`--config.fetch-retries=0` 让死源在 `inspectTimeoutMs` 内报错，而不是等 pnpm 自己重试
   - path spec → 直接读 `package.json`；git/tarball → 只回答形态和 `host`（包内容要等 fetch）
   - 边界：range 返回数组时取最后一个（`answer.at(-1)`，`index.ts:473`）——pnpm 对 range 按版本从旧到新返回
   - 不选：不调 registry HTTP API。理由：认证、代理、镜像配置都在 pnpm 侧，自己发请求会绕开用户的 `.npmrc`

3. **安装前预检：不兼容的包根本不下载**
   - 依据：`operations.ts:149-200`（`namedSpecs` + `namedSpecManifest`）、`operations.ts:335-352`（预检）
   - 只对"点名了包"的命令（`add`/`install`/`i`）预检；git/tarball 无法预读，留给装后校验
   - 为什么：不兼容版本一旦装上，pnpm 会执行它的 install script；预检把"下载 + 执行脚本"整个跳过（README 原话：*nothing is downloaded and no build script runs*）
   - 边界：预检读不到 manifest（网络/私有包）时**不阻断**，交给装后校验——预检是优化，不是安全边界

4. **pnpm 运行：service 模式捕获输出，CLI 模式继承终端**
   - 依据：`run-tree.ts:37-39`（`leadsOwnGroup`）、`operations.ts:360-364`（execa 参数）
   - service（管理器在进程内调用）：`stdout/stderr: 'pipe'`、`killDescendants: true`、`stdin: 'ignore'`、scrubbed 环境
   - CLI（`dsh plugin`）：`inherit` 三件套，保留认证变量和终端
   - 为什么分两种：service 要抓输出分类失败、要在取消时杀整棵进程树；CLI 是操作员在前台跑，要能 Ctrl-C、要能输密码

5. **装后校验四步，任一失败回滚**
   - 依据：`index.ts:612-627`
   - ① 对比 before/after `dependencies`，必须恰好新增一个包（否则 `ambiguous-install`）
   - ② 该包 `dsh.bundle.patch` 必须存在（否则 `not-bundle`）
   - ③ 兼容性检查（`engines.dsh` 优先，缺省回退 peer，见 §D）
   - ④ bundle patch 必须能被 `loadOverlayPatches` 读（读不出就回滚，避免写入一个启动必炸的 selection）
   - 为什么"恰好一个"：pnpm 可能因为 workspace/link 语义改动多个依赖；多于一个说明 spec 的意图不明确，不能猜

6. **激活：先写 selection，再 reload**
   - 依据：`index.ts:637-649`（`configure` + `selectBundle` + `publishAndReload`）
   - HMR 存在：`hmr.runExclusive(...)` 串行化，改完立即 `reconcileProfile` 重组
   - HMR 不存在：只保存，结果报 `restart-required` + `restartReason: 'no-hmr'`
   - 边界：`enabled: false` 安装只装不选（`options.enabled !== false` 才 select）
   - 为什么 HMR 下要 `runExclusive`：管理器的写入和 HMR 自己的文件监听会并发改同一批文件，必须排进同一条队列

#### B. 分支

7. **多 registry：按计划逐个试，只对"可能换源解决"的失败继续**
   - 依据：`registry.ts:54-90`（`registryPlan`）、`registry.ts:92-98`（`attributeFailure`）、`index.ts:571-600`
   - 计划：`options.registry` → 配置的 `registry` → `fallbackRegistries`；去重；**不在配置集合里的 registry 单独问**（私有源不会掉进公共源）
   - 继续条件：`network` / `timeout` / `not-found` / `no-matching-version`（镜像未同步也表现为 not-found）
   - 停止条件：其他失败；或错误行点名了 git/tarball 的 `host`（`spec-host`，任何 registry 都替代不了）
   - 边界：每次换源前**恢复快照**（`index.ts:575`），否则上一次半成品会污染下一次
   - 不选：不并发问多个源。理由：pnpm 的 lockfile 与 registry 绑定，并发会产生不确定的 lockfile

8. **HMR 下重复安装直接拒，升级 = 先删再装**
   - 依据：`index.ts:541-545`、上游 `docs/upgrade-guide/v0.2.1-alpha.2/plugin-install-over-installed/`
   - 条件：HMR 存在 且 spec 能解析出包名 且 该包已在 dependencies
   - 为什么：HMR 下旧版本插件还在跑，直接覆盖会让新旧模块映射混在一起；先 `removeBundle` 停止旧插件、清映射，再装新版才能干净启动
   - 边界：git/tarball spec 装前解析不出包名 → 不拦，交给 HMR 重组替换（上游 README 明确这条例外）

9. **GitHub 预检只拦网络问题，不拦认证**
   - 依据：`github-connection.ts:28-68`、`index.ts:555-569`
   - 只对 `github.com` / `*.github.com` 的 git spec 执行：`git -c credential.helper= ls-remote -- <repo> HEAD`
   - 禁用凭据交互：`GIT_TERMINAL_PROMPT=0`、`GIT_ASKPASS=''`、`SSH_ASKPASS_REQUIRE=never`
   - 只把 `network` / `timeout` 当失败（`failedAt: 'spec-host'`），认证/仓库不存在留给 pnpm（它会走 HTTPS→SSH 回退）
   - 为什么：预检的目的是"5 秒内告诉用户网络不通"，不是替代 pnpm 的认证协商

10. **build scripts 审批：从失败输出里捞，自己写进 pnpm-workspace.yaml**
    - 依据：`build-approval.ts:49-62`（`recordPendingBuilds`）、`build-approval.ts:75-81`（`approveBuilds`）
    - pnpm 非交互运行时不写 `allowBuilds`，只在输出里打 `Ignored build scripts: a, b`；管理器用正则捞出来，写入 `allowBuilds: <name>: "set this to true or false"`
    - 审批时校验"名字仍在 pending"，否则 `stale-approval`；拒绝 YAML anchor/alias
    - 边界：`pnpm-workspace.yaml` **故意不恢复**（`RESTORED_FILES` 只有两个文件）——审批记录要跨失败保留
    - 为什么不让 AI 直接改 `pnpm-workspace.yaml`：审批是"用户明确同意执行脚本"的凭证，必须由用户/工具显式触发，不能顺手写

#### C. 边界

11. **取消：三个阶段，`applying` 之后不可停**
    - 依据：`index.ts:104-113`（`InstallControl.phase`）、`index.ts:653-676`（`waitForInstall` / `cancelInstall`）
    - `installing` → 可取消，杀 pnpm、恢复快照，返回 `cancelled`
    - `applying` → 返回 `too-late`（bundle 正在被选中/加载，停下来会留下半激活状态）
    - 未知 id → `not-running`
    - 为什么保留 `waitForInstall`：客户端丢响应后要能拿回同一次安装的结果，不能重装

12. **四类超时，各管一段**
    - 依据：`index.ts:208-217`（Config schema）、`operations.ts:377-395`（idle 计时器）、`operations.ts:431-437`（drain 2s）
    - `inspectTimeoutMs`（20s）：单次 registry 查询
    - `githubConnectionTimeoutMs`（5s）：GitHub 预检
    - `idleTimeoutMs`（600s）：pnpm **静默**超时——不是总时长；只要有输出就一直跑
    - `lockWaitMs`（120s）：抢 profile 写锁
    - 边界：CLI 模式（inherit）没有 idle 上限——操作员在终端前，卡住可以自己 Ctrl-C

13. **进程树：run.json 记录 + 退出后等 5 秒**
    - 依据：`run-tree.ts:4-77`、`operations.ts:199-250`（`recordRun` / `activeRecordedRun`）
    - 每次 pnpm 运行前写 `.plugin-manager/run.json`（pid + grouped），结束后删除
    - 下一个操作拿到锁时若发现残留记录：等最多 5 秒（`TREE_WAIT_MS`），还活着就报错并点名 pid，**不运行 pnpm**
    - 为什么：文件锁只保护"持有锁的进程"，不保护"它启动的 pnpm 树"；lifecycle script 会活得比 pnpm 久（上游 issue #4981）
    - 边界：`grouped` 只在 POSIX + service 模式为真，探测用 `kill(-pid, 0)`

14. **输出有界：返回 16KB，完整日志落盘**
    - 依据：`index.ts:211`（`outputBytes: 16384`）、`operations.ts:308-315`（`append` 截尾）
    - 只保留尾部 N 字节（失败诊断在尾部），`logPath` 指向 `.plugin-manager/logs/operation-*/pnpm.log`
    - 为什么截尾不截头：pnpm 的错误码和真实原因在最后几行

#### D. 差异（与 DSH）

15. **与 DSH 一致，无本地修改**
    - 依据：`diff -rq packages/dsh-plugin-manager/src node_modules/@deepseek-ai/dsh-plugin-manager/src` 无输出
    - 兼容性判定顺序沿用上游：`engines.dsh` 优先，缺省才看 `peerDependencies`（`docs/upgrade-guide/v0.2.1-alpha.3/plugin-engines-dsh/`）；`workspace:` 出现在 `engines.dsh` 里视为不兼容
    - 记录字段叫 `requirements`（上游已从 `peers` 改名），键是 `engines.dsh` 或 peer 包名
