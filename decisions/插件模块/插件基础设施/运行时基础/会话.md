# 会话

**父级**：[运行时基础](./运行时基础.md)

## 为什么需要

智能体的每次思考、每次工具调用、每次用户输入都要留下痕迹——否则无法恢复、无法投影、无法压缩。会话是这些痕迹的载体。

## 准备怎么实现

### 宏观想法

```
写入：事件（event）→ 持久化（jsonl）
读取：事件流 → 投影（projection）→ 消费者（界面/压缩/统计）
```

- **事件是唯一真源**：状态由事件推导，不单独存"当前状态"
- **投影是按需计算**：界面要什么就投影什么，投影可重建
- **持久化是追加**：jsonl 追加写，崩溃后能恢复到最后一个完整事件

### 边界

| 会话负责 | 不负责 |
|---|---|
| 事件的定义与追加 | 事件怎么产生（智能体/工具/用户） |
| 投影的注册与计算 | 投影怎么展示（界面） |
| 持久化与恢复 | 压缩策略（压缩是使用方） |
| 存储抽象（本地/远程） | 具体存储后端（子实现） |

### 投影的所有权与读取分离（rc.3 结构改进）

**变更**：新增 `ProjectionHandle<S>`——effect 拥有的注册，加上一个**独立于注册**的 reader。

| 成员 | 语义 | 为什么 |
|---|---|---|
| `stateOf(session)` | 用该 handle 的**原始 unit** 折叠 Session 已提交事件，返回当前游标处的状态 | 读取不依赖全局 drive；注销后仍能算 |
| `dispose()` | 从全局 drive 与快照注销，**但不使 reader 失效** | 省资源，但保留"偶尔读一次"的能力 |

**为什么需要**：消费者分两种——
- **订阅者**：要持续跟随更新（界面、统计）
- **查询者**：只要某个时刻的状态（工具、一次性诊断）

让查询者为了读一次而长期订阅，是资源浪费；让订阅者失去读取能力，又会让注销变危险。`ProjectionHandle` 把两者分开。

**另一处收紧**：`ProjectionDefinition.includeInSummary?: boolean`（默认 `true`）——声明该投影是否进入 Session summary。运行时 key 集合跟随这个字段，客户端视图类型跟随 `SessionProjectionSummaryExcluded` 标记。

**我们的现状**：`dsh-session-projection` 有 `ProjectionDefinition`，没有 `ProjectionHandle`。

### 验证

- 杀掉进程后重启，会话恢复到最后一个完整事件
- 投影可从事件流完整重建（删掉投影缓存不影响正确性）
- 新增一种投影不需要改会话核心
