# 插件规范

**父级**：[插件基础设施](../插件基础设施.md)

## 为什么需要

一个插件必须是什么样：manifest、生命周期契约、服务契约、配置 schema、隔离边界、自进化条件。

## 准备怎么实现

### 宏观想法

插件规范：形态 / manifest / 生命周期 / 服务契约 / 隔离 / 自进化——**让插件可加载、可替换、可热更**。

```
插件 → 规范检查 → 可加载
```

**为什么规范**：没有规范，插件可能泄漏副作用/状态，HMR 就不安全。

### 细节实现
## 设计原则

**插件规范不是独立设计的，它是内核契约的“使用说明”。** 每一条规则都必须能追溯到内核模块的某个决策；不是拍脑袋定的。

## 规范条目 → 内核依据

| 插件规范 | 依据的内核决策 |
|---|---|
| ESM 入口 | 热更新：只有 ESM 进 `loadCache`，才能被 reload |
| 静态 `import` | 热更新：依赖图靠 `job.linked` 收集 |
| 副作用用 `ctx.effect` 清理 | 依赖注入与生命周期：Fiber.effect LIFO，dispose 时执行 |
| 状态外置（storage/session） | 热更新：fiber 重建会丢模块级状态 |
| 入口通过 `entry.options.name` 声明 | 插件加载：loader 按 name 解析入口 |
| `Config` schema（Standard Schema） | 插件加载：apply 前验证、默认值补齐 |
| `inject` 声明 | 依赖注入：Registry 用 inject 决定何时启动 |
| 用 `ctx.timeout` / `interval` / `debounce` | 时间与调度：绑定 fiber effect，自动清理 |
| 用 `ctx.logger(name)` | 日志：命名 logger、级别过滤 |
| 事件命名（保留 `internal/` 前缀） | 事件系统：`internal/dispatch` 诊断 |
| `isolate` 的 label 用法 | 嵌套与隔离：LocalRealm / GlobalRealm |

## 1. 插件形态

三种形态都合法：

| 形态 | 写法 | 适用 |
|---|---|---|
| 函数插件 | `export function apply(ctx, config)` | 无服务、纯逻辑 |
| 类插件 | `export class Plugin extends Service` | 提供服务的插件 |
| 对象插件 | `export default { name, apply(ctx, config) }` | **推荐**：有 name、可读性好 |

## 1.1 执行器也是插件

`ToolExecutor` 不是内核的一部分，它是一个**提供执行能力的插件**：

| 项 | 规则 |
|---|---|
| 注册 | `ctx.tools.setExecutor(executor)`，返回 disposer，随 fiber 卸载 |
| 作用域 | 每个 scope 只能一个执行器；重复注册抛错 |
| 生命周期 | 执行器卸载后，在途调用等结算；后续调用明确失败（不静默换执行器） |
| 形态 | 与普通插件相同（函数 / 类 / 对象），只是它 `provide` 的是执行能力而非工具 |
| 数量 | 同一部署可以有多个执行器实现（原生 / PTC / 远程），由装配决定哪个生效 |

**为什么写进规范**：执行方式属于"插件能提供什么"，不是内核特权。这条是 P2（一切皆插件）在工具层的落点。

## 2. manifest 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 插件名，用于日志 / 诊断 |
| `apply` | ✅ | 入口（函数 / 对象形态） |
| `inject` | ❌ | 依赖的服务（数组或 name → config 映射） |
| `provide` | ❌ | 提供的服务名（类插件） |
| `Config` | ❌ | Standard Schema（配置验证） |

**禁止**：`version`、`compatibleWith`、`engines`——P7 无版本门槛。

## 3. 生命周期契约

| 阶段 | 规则 |
|---|---|
| 启动 | `apply(ctx, config)`；所有副作用通过 `ctx.effect` 注册清理 |
| 卸载 | 由 fiber 自动管理；插件不手动 dispose |
| 更新 | config 变化 → fiber 重建（volatile 字段除外） |
| 禁止 | 模块级可变状态（reload 会丢失） |

## 4. 服务契约

| 项 | 规则 |
|---|---|
| 类插件 | `super(ctx, name)` 构造即注册；随 fiber 注销 |
| 函数插件 | `ctx.provide(name, value)` 手动注册 |
| 服务名 | isolate scope 内唯一 |
| 可选能力 | 用符号（`init` / `check` / `invoke` / `config`） |

## 5. 隔离机制全景

worker 只是**进程级隔离**的一种，不是唯一。现有机制分三层：

### 进程内（已有）

| 机制 | 隔离什么 | 粒度 | 实现 |
|---|---|---|---|
| **fiber** | 生命周期 / effect / 状态 | 插件实例 | 每个 `ctx.plugin()` 一个 fiber，dispose 不影响其他 |
| **isolate（LocalRealm）** | 服务实例 | entry | `isolate: { name: true }` |
| **isolate（GlobalRealm）** | 服务实例 | 同 label | `isolate: { name: 'label' }` |
| **scope（group/preset）** | 服务可见性 | 子树 | 全局 store（按 isolate 标签，D40 修正） |
| **intercept** | 服务配置 | entry | `intercept: { name: config }` |

### 进程级（部分有 / 规划）

| 机制 | 隔离什么 | 现状 |
|---|---|---|
| **sandbox** | 子进程权限（文件 / 网络 / 系统调用） | 有 `dsh-sandbox-policy`（dshiunx 未装 sandbox-local，`danger-full-access`） |
| **子进程** | OS 命令 / 终端 | 有 `dsh-subprocess-local`（不是插件隔离） |
| **worker** | 故障 / 崩溃 / CPU / 内存 | 规划（AI 生成插件的隔离层） |

### 模块级（已有）

| 机制 | 隔离什么 | 实现 |
|---|---|---|
| **loadCache / require.cache** | 模块版本 | HMR 清缓存 + 重新 import |
| **entry 树** | 配置 / id | group 子树、`父:子` id |

### 隔离方式的选择（不是全量 worker）

| 插件类型 | 用哪层隔离 | 理由 |
|---|---|---|
| 可信插件 | fiber + isolate（in-process） | 无 RPC 开销 |
| AI 生成 / 第三方 | worker（进程级） | 故障隔离，工具级调用可接受 7µs |
| 高频事件插件 | fiber（in-process，仅可信） | RPC 开销不可接受 |
| 需要文件/网络限制的插件 | sandbox | 权限隔离 |

**结论**：worker 是“故障隔离”的补充，不是替代。fiber/isolate 解决“状态/服务隔离”，sandbox 解决“权限隔离”，worker 解决“崩溃/资源隔离”。

## 5.1.1 native 模块约束

| 规则 | 理由 |
|---|---|
| 插件不得直接 `import` native 模块 | 依赖服务接口，隔离 native 变更 |
| native 能力必须封装成服务 | 服务契约稳定，实现可替换 |
| 有状态插件必须支持 `serialize/restore` | 句柄/状态可迁移（HMR 状态迁移） |

## 5.1.2 隔离分级与动态策略

### 分级维度

| 维度 | 取值 | 影响 |
|---|---|---|
| **trust** | trusted / untrusted | 默认隔离级别 |
| **isolation** | none / fiber / worker / sandbox | 实际隔离方式 |
| **frequency** | high / low | 高频事件不适合 worker（RPC 开销） |
| **resource** | cpu / memory / native | 资源型适合 worker |

### 判定优先级（高 → 低）

1. **entry 显式配置**：`entries.yml` 的 `isolation: worker`
2. **插件 manifest**：`isolation: 'worker' | 'none'`
3. **trust 默认**：AI 生成 / 第三方 → **in-process + 风险控制**（加载前测试 / 运行时监控 / 回滚）；worker 只在“纯执行器 / 故障隔离”时用
4. **运行时策略**：`isolationPolicy` 服务（可配置）

### 动态调整

| 方向 | 触发 | 行为 |
|---|---|---|
| **升级** | 崩溃 N 次 / CPU 超阈值 / 内存超阈值 | 自动从 none 升到 worker（仅当插件是纯执行器/可远程） |
| **降级** | 不自动（避免抖动） | 由配置显式降级 |
| **特殊对待** | 白名单 / 黑名单 | 强制 none / 强制 worker |

### 接口（规划）

- `Plugin.Base.isolation?: 'none' | 'worker' | 'sandbox'`
- `EntryOptions.isolation?: ...`
- `ctx.plugin(plugin, config, { isolation })`
- `WorkerHost` 按判定结果选择加载方式

**原则**：默认按 trust 分级；任何一级都可以被显式配置覆盖；动态调整只升不降，避免抖动。

## 5.2 插件形态开放（修正）

**插件不限于 in-process。** 作为一个开放框架，插件可以运行在任意位置。

### 四种形态

| 形态 | ctx 语义 | 隔离级别 | 适用 |
|---|---|---|---|
| **in-process** | 完整同步 ctx（`get` / `provide` / `emit` / `effect`） | fiber + isolate | 大多数插件、官方插件、高频事件 |
| **worker** | 异步 RPC（ctx 代理或显式 `rpc`） | 进程级（故障隔离） | AI 生成、第三方、纯执行器 |
| **子进程** | 消息协议（stdio / IPC） | 进程级 | 需要独立运行时、崩溃隔离 |
| **远程** | HTTP / WebSocket | 网络级 | 分布式、多端（未来） |

### 统一抽象

插件协议不是“必须用 ctx”，而是：

- **manifest**：name / inject / provide / Config / isolation
- **生命周期**：load / reload / dispose
- **消息**：请求 / 响应 / 事件（形态不同，传输不同）

`ctx` 只是 **in-process 形态**的便利接口；worker/子进程/远程形态用 `rpc` 或消息协议。

### 形态选择

由 **isolation 分级**决定（trust / frequency / resource），不是硬编码：

```
entry.isolation 显式 → 用它
manifest.isolation → 用它
trust 默认 → AI 生成走 worker；官方走 in-process
```

### 修正说明

之前“同步 ctx 语义决定插件必须 in-process”**只适用于 in-process 形态**，不是所有插件。开放框架允许插件选择自己的形态：

- 需要同步 ctx 的插件 → in-process
- 需要故障隔离的插件 → worker（接受异步 RPC）
- 需要独立运行时的插件 → 子进程
- 需要跨端的插件 → 远程

**代价**：不同形态的插件不能直接共享服务（跨进程要 RPC）。这是形态选择的代价，不是框架的限制。

### worker 的定位（修正后）

| 问题 | 回答 |
|---|---|
| worker 是“AI 插件的默认隔离层”吗？ | ❌ 不是（修正前是，已作废） |
| worker 还需要实现吗？ | ✅ 作为**可选形态**保留，按需实现 |
| 内核模块的完整性依赖 worker 吗？ | ❌ 不依赖——in-process + watchdog + 加载前测试已覆盖核心风险 |
| 什么时候实现？ | 有明确需求时：纯执行器插件、故障隔离、未来远程插件 |

**结论**：worker 从“必须”降为“可选”。核心风险（死循环/崩溃）用 in-process + watchdog + 加载前测试解决；worker 是“开放框架的一种形态”，不是内核的必需组件。

## 6. 自进化检查

满足以下条件的插件**可热更**：

1. ESM 入口
2. 静态 `import`（不用动态 `import()`）
3. 副作用用 `ctx.effect` 清理
4. 状态外置（storage / session）
5. 入口通过 `entry.options.name` 声明

不满足的插件标记为“不可自进化”，不假装能热更。

## 边界

| 规范管 | 不管 |
|---|---|
| 插件的**形状**：形态 / manifest / 生命周期 / 服务契约 | 插件**做什么**（具体插件节点） |
| 可加载、可替换、可热更的**最低条件** | 插件之间怎么组合（插件装配） |
| 每条规则对应的**内核依据** | 内核契约本身（内核模块） |
| 隔离的**分级维度**（trust / isolation / frequency / resource） | 具体隔离实现（sandbox / worker 实现） |

**一句话**：规范回答"什么样的东西算插件"，不回答"这个插件好不好用"。

## 验证

- **加载条件**：函数，或带 `apply` 方法的对象（`registry.ts:8-9` 的 `isApplicable`；`:319` 的拒绝信息）。`name` 不是加载条件——缺省时从函数名推导（`:325`）
- **热更条件是行为结果，不是标记**：不满足五条件的插件不会进入 `loadCache`，文件变更不会触发它的 reload（HMR 按文件依赖图判断，没有"不可热更"标记机制）
- 执行器通过 `ctx.tools.setExecutor()` 注册；同 scope 重复注册抛错（`tools/index.ts:328`）
- 插件 manifest 里出现 `version` / `compatibleWith` / `engines` → 违反 P7
- 每条规范条目都能指到对应的内核决策（上表可查）
