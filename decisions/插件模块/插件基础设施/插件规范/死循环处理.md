## 设计原则

**接受意外，但不接受“后台悄悄死循环”。**

- 不自动杀（避免误伤合法的长循环）
- 先警告（让用户知情）
- 拉到前台（让用户判断）
- 提供修复插件（用户主动处理）

## 关键技术约束

**in-process 死循环会卡住主进程，主进程内的 TUI 也无法响应**——所以警告**必须来自主进程之外**。

Node 无法中断同步死循环（in-process），只能：
- 杀进程（watchdog 发信号）
- 或 worker terminate（仅 worker 插件）

## 归属：watchdog 是独立插件，不是内核

| 部分 | 归属 | 说明 |
|---|---|---|
| **心跳** | 内核（工程保障） | 主进程定期写 SharedArrayBuffer / 心跳文件（一行代码） |
| **watchdog** | **插件模块（独立插件）** | 独立进程，监控心跳、告警、提供操作 |

watchdog 不需要 ctx（它是监控者，不是被监控者），所以按插件形态属于“子进程/worker 插件”，放在插件模块。

## 架构：主进程 + Watchdog

```
主进程（cordis + TUI + 插件）
  ├── 心跳：每 100ms 更新 SharedArrayBuffer（或心跳文件）
  └── 插件可能死循环

Watchdog（独立 worker 或子进程）
  ├── 监控心跳（超 2s 无更新）
  ├── 直接写 stderr："主进程卡住 N 秒；最后活动：插件 X"
  └── 提供操作：等待 / 杀进程 / 重启
```

**为什么 Watchdog 必须独立**：主进程卡住时，主进程内的任何代码（包括 TUI）都跑不了。只有独立进程能检测和告警。

## 警告内容

| 信息 | 来源 |
|---|---|
| 卡住时长 | watchdog 计时 |
| 最后执行的插件 | 主进程心跳里带上 `ctx.fiber` 的当前插件名 |
| 建议操作 | “等待 / 杀掉 / 重启” |

## 修复插件（plugin-doctor）

用户确认后启动，提供：

| 能力 | 说明 |
|---|---|
| 查看卡住的 fiber | 哪个插件、什么状态 |
| 强制 dispose | 卸载卡住的插件（如果主进程还能响应） |
| 回滚 | `git revert` 到上一个版本 |
| 热修复 | 改代码 + reload（如果主进程可用） |

## 与“自动卸载”的区别

| | 自动卸载 | 透明化 + 前台 |
|---|---|---|
| 误伤合法长循环 | 会 | 不会（用户判断） |
| 用户知情 | 否 | 是 |
| 控制权 | 系统 | 用户 |
| 修复能力 | 无 | 修复插件 |

## 实现顺序

1. 心跳机制（主进程 → SharedArrayBuffer）
2. Watchdog（独立 worker/子进程，监控 + stderr 告警）
3. TUI 前台化（主进程恢复后，显示“刚才卡住 N 秒”）
4. plugin-doctor 插件（查看/卸载/回滚/热修）

## 残余风险

- Watchdog 只能“告警 + 杀进程”，不能“中断死循环”
- 杀进程会丢会话（session 持久化可恢复）
- 极端情况下（watchdog 也挂了）只能手动处理
