## 为什么单独讨论

AI 生成的插件与人工插件有本质差异：
- 没有“安装审批”环节（DSH 有人工把关，我们没有）
- 代码可能包含死循环、内存泄漏、权限越界
- 生成速度快，错误也快

而插件是 **in-process**（同步 ctx 的要求），所以风险会直接影响主进程。

## 风险类型

| 风险 | 例子 | 影响 | 能否隔离 |
|---|---|---|---|
| **崩溃** | 语法/运行时异常 | fiber FAILED | ✅ fiber 隔离（不影响其他插件） |
| **死循环** | `while(true)` | 事件循环卡住，整个进程无响应 | ❌ 同进程无法隔离 |
| **内存爆炸** | 无限数组 | OOM | ⚠️ 可设上限 |
| **权限越界** | 读 `/etc/shadow`、发网络请求 | 安全 | ✅ sandbox（限制子进程） |
| **依赖污染** | 引入恶意 npm 包 | 供应链 | ✅ 依赖白名单 |
| **热更失败** | 新代码有问题 | reload 后不稳定 | ✅ git 回滚 |

## 四阶段控制

### 1. 生成时（约束）

| 手段 | 内容 |
|---|---|
| **插件规范** | ESM / 静态 import / effect 清理 / 状态外置 |
| **模板/脚手架** | AI 按模板写，减少结构错误 |
| **依赖白名单** | 只能 import 允许的包（内核 + 官方插件） |
| **静态检查** | `tsc --noEmit` + lint，不过不进入下一步 |

### 2. 加载前（验证）

**关键：在 worker 里跑冒烟测试（隔离环境，不怕死循环）。**

```
AI 生成插件
  → 类型检查（tsc）
  → 依赖检查（白名单）
  → worker 内冒烟测试（加载 + 调用一次）
  → 通过 → in-process 加载
  → 失败 → 拒绝，AI 修复
```

**注意**：worker 在这里是**测试沙箱**，不是运行时隔离。测试通过后插件仍在主进程运行（保持同步 ctx）。

### 3. 运行时（监控）

| 监控 | 手段 | 动作 |
|---|---|---|
| **fiber 状态** | `FiberState.FAILED` | 记录 + 计数 |
| **事件循环延迟** | `monitorEventLoopDelay` | 超阈值（如 1s）→ 告警 |
| **内存** | `process.memoryUsage()` | 超阈值 → 告警/卸载 |
| **崩溃计数** | 同一插件连续 FAILED N 次 | 自动 `disabled`，写入 entries |

**事件循环监控示例**：

```ts
import { monitorEventLoopDelay } from 'node:perf_hooks'
const h = monitorEventLoopDelay({ resolution: 20 })
h.enable()
setInterval(() => {
  if (h.max > 1000) {
    ctx.emit('health/blocked', h.max)
    h.reset()
  }
}, 5000)
```

### 4. 事后（恢复）

| 手段 | 内容 |
|---|---|
| **git 回滚** | 插件代码 + entries.yml 每步提交，出问题 `git revert` |
| **审计日志** | 谁写的、何时加载、崩溃记录 |
| **禁用/删除** | `disabled: true` 或删除 entry |

## 关键判断

**死循环是同进程无法隔离的**——这是 in-process 的固有代价。

应对：
1. **加载前 worker 测试**（把死循环挡在加载前）
2. **运行时事件循环监控**（发现卡顿 → 告警）
3. **接受残余风险**：极端情况下只能重启进程（session 可恢复）

## 与 DSH 的对比

| | DSH | dshiunx |
|---|---|---|
| 插件来源 | 官方 + 市场（人工安装） | 官方 + AI 自动生成 |
| 把关环节 | 安装审批 | **生成时约束 + 加载前测试** |
| 运行时 | in-process | in-process（同） |
| 死循环风险 | 有（靠人工审查） | 有（靠自动化验证 + 监控） |

**结论**：dshiunx 用“自动化验证”替代 DSH 的“人工审批”，但保留 in-process（同步 ctx）。
