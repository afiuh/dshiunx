# 原生执行

**父级**：[执行器](./执行器.md)

## 为什么需要

默认执行方式：模型看到每个工具的定义，直接调用；执行器按批调度。

没有它，系统必须依赖 PTC 才能执行工具——而 PTC 需要生成 SDK、启动运行时，代价高。

## 准备怎么实现

### 宏观想法

```
一批调用 → 按调用顺序扫描
  ├─ exclusive 调用 → 形成屏障（前面的等完，后面的等它）
  └─ 其他调用 → 有界滚动池（并发上限内补位）
→ 结果按模型调用顺序结算（不是完成顺序）
```

**为什么结果要按模型顺序**：模型看到的 tool_result 顺序必须与它发出的调用顺序一致，否则后续推理会错位。执行可以乱序，结算不能乱序。

### 细节实现

1. **批级调度**：一次处理一个 assistant step 的全部调用；exclusive 调用是屏障，parallel 调用进有界池
2. **启动前重分类**：调用进入池之前再判定一次能否并行（工具可能在准备阶段改变并发语义）
3. **并发上限**：默认 10，可由批输入覆盖；PTC 子调用另有独立上限
4. **取消**：abort 时为**尚未启动**的调用生成合成错误结果，保证 replay 时调用与结果一一对应
5. **终止性失败**：调度器自身失败 → 排空已启动调用后 reject，由 step 记录保守恢复结果
6. **结果结算**：按模型调用顺序输出 `ToolBatchResult`，附带额外上下文

### 边界

| 情况 | 行为 |
|---|---|
| 批内无 exclusive | 全部进池，按上限并发 |
| 有 exclusive | 屏障切分批次，屏障两侧不重叠 |
| 取消 | 已启动的等结算，未启动的给合成结果 |
| 单个工具抛错 | 该调用返回错误结果，不终止整批（除非工具声明终止） |
| 执行器卸载 | 在途调用等结算，之后 `ctx.tools` 拒绝执行 |

### 验证

- 三个并行工具的总耗时 ≈ 最慢那个（不是三者之和）
- 中间插一个 exclusive，它前后的调用不重叠
- 取消后 replay，调用与结果数量一致
