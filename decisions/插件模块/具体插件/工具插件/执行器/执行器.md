# 执行器

**父级**：[工具插件](../工具插件.md)

## 为什么需要

工具被模型调用后，谁来决定"怎么执行"？如果写死在 `ctx.tools` 里，执行方式就不可替换——并行度、PTC、远程执行都成了内核的事，违反 P1（最小内核）与 P6（自进化）。

执行器把这个决定变成插件。

## 准备怎么实现

### 宏观想法

```
模型调用 → ctx.tools（定义与分发）→ ToolExecutor（插件）→ 实际执行
```

- `ctx.tools` 只管：工具定义注册、作用域可见性、调用分发
- `ToolExecutor` 管：一批调用怎么执行、并发多少、结果怎么结算
- 执行器通过 `provide` 注册，同一时刻一个 scope 内只有一个生效

**为什么是"整批"而不是"单个调用"**：执行策略本质是批级决策——哪些能并行、哪些必须串行、失败后是否继续。单个调用无法表达"exclusive 屏障"。上游 `ToolBatchInput` / `ToolBatchResult` 就是按批设计的。

### 边界

| 执行器负责 | 执行器不负责 |
|---|---|
| 批内调度（并行 / 串行 / 屏障） | 工具的定义与 schema |
| 并发上限 | 工具的可见性（preset 决定） |
| 取消传播、结果结算 | 工具内部逻辑 |
| 提供给模型的工具描述形态 | 系统提示的其余部分 |

### 子节点

| 子节点 | 负责什么 |
|---|---|
| [原生执行](./原生执行.md) | 直接执行每个调用，默认方式 |
| [PTC执行](./PTC执行.md) | 只暴露 `run_code`，工具通过生成的 SDK 调用 |

### 验证

- 同一批工具定义，在两种执行器下都能完成调用
- 执行器卸载后 `ctx.tools` 仍能列出定义（只是无法执行）
- 换执行器不需要重启会话
