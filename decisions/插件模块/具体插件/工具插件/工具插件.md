# 工具插件

**父级**：[具体插件](../具体插件.md)

## 为什么需要

给智能体用的能力：文件、命令、网络、子代理、调度、工作流。

工具插件要回答两个不同的问题，它们不该混在一个实现里：

1. **有哪些工具**（能力清单）——文件读写、bash、web……
2. **工具怎么被执行**（执行方式）——并行、串行、PTC、远程

## 准备怎么实现

### 宏观想法

工具插件拆成两个正交的维度：

```
工具插件
├── 执行器/      ← 怎么执行：原生（直接）/ PTC（工具即代码）
└── 具体工具/    ← 有哪些：文件 / 命令 / 协作 / 能力 / 检视
```

**为什么拆开**：同一个工具集，换一种执行方式（原生 ↔ PTC ↔ 未来的远程执行），工具本身不该改一行代码。这来自 rc.3 的上游结构（`ToolExecutor` 接口 + `tool-executor-native` / `tool-executor-ptc` 两个实现包），也符合 P2（一切皆插件）与 P6（自进化）。

### 边界

| 属于本节点 | 不属于本节点 |
|---|---|
| 工具插件的整体分工与边界 | `ctx.tools` 服务本身（内核） |
| 执行器与工具的关系 | `ToolExecutor` 接口的字段定义（内核契约） |
| 具体工具的分类与约束 | 单个工具的内部实现（子节点） |

### 子节点

| 子节点 | 负责什么 |
|---|---|
| [执行器](./执行器.md) | 工具怎么被调度与执行；实现 `ToolExecutor` 并注册 |
| [具体工具](./具体工具.md) | 有哪些工具；每个工具职责单一、只依赖服务 |

### 验证

- 换执行器（原生 ↔ PTC）不改任何具体工具的代码
- 删除任一具体工具，其余工具与执行器仍能工作
- 执行器与具体工具都只依赖 `ctx.tools` 契约，互不 import
