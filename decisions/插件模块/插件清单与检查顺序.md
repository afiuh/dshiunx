## 3. 检查顺序（按检查价值）

**检查价值 = 影响面 × 复杂度 × 历史问题。**

| # | 批次 | 包含 | 理由 |
|---|---|---|---|
| **1** | **启动链路** | `dsh-app-boot` → loader → entries.yml | 启动失败影响一切 |
| **2** | **运行时核心** | agent / agent-loop / llm / session / storage / tools | 核心功能，问题最多 |
| **3** | **工具插件** | tool-fs / tool-bash / tool-web / subagent / subprocess | 用户直接使用 |
| **4** | **界面插件** | tui / tui-protocol / tui-status / tui-store / tui-controller | 已部分检查（空回调/类型） |
| **5** | **清理** | dsh-tui（参考）/ tui-* 空壳 / 未启用包 | 减少维护面 |

## 4. 参考基准与检查策略（不同插件不同策略）

| 类别 | 参考基准 | 检查策略 |
|---|---|---|
| **运行时核心**（agent / agent-loop / llm / session / system-prompt） | **DSH 本身**（官方打磨得好） | 对照 DSH 的智能体循环、提示词结构；**不自己发明**，差异必须登记 |
| **工具插件**（tool-fs / tool-bash / tool-web） | DSH 本身 | 对照 DSH 实现，差异登记 |
| **界面插件**（tui / tui-*） | **dsh-TUI（参考），但结构乱** | **参考功能，不参考结构**；解耦后重新审视 |
| **装配**（app-boot） | DSH 本身 | 对照 app-boot 流程 |

### 4.1 TUI 的特殊性

TUI 的来源是 `dsh-TUI` 项目（参考源码，20 万行，不参与运行），它的代码水平不高：

| 问题 | 数据 |
|---|---|
| 单文件膨胀 | `Chat.tsx` 7556 行、`PromptInput.tsx` 4000+ 行 |
| 状态堆叠 | 64 个 `useState`、35 个 `useEffect`、44 个 `useCallback` |
| 组件堆积 | 197 个组件合并进一个包 |
| 解耦后残留 | 14 个空回调、ChatStore 字段缺失、`AnyMessageList as any` 绕行 |

**TUI 的检查策略**：

1. **参考功能，不参考结构**——dsh-TUI 的功能要保留，但结构要重新设计
2. **解耦后重新审视**——`packages/tui` 是从 Chat.tsx 抽出来的，不是“干净的插件”，要检查：
   - 14 个空回调（还没接）
   - ChatStore 字段缺失（`statusFields` / `approvalSnapshot` / `questionSnapshot` / `failureHintRowId`）
   - 文件组织（index.tsx 487 行渲染树是否该拆）
   - `AnyMessageList as any` 的类型绕行
3. **不要照抄**——dsh-TUI 的 7556 行 Chat.tsx 是反面教材，不是模板

### 4.2 智能体的特殊性

智能体（agent / agent-loop / system-prompt / persona / preset）以 **DSH 本身**为基准：

- DSH 的智能体循环经过产品验证，不要自己发明
- 提示词结构（persona / preset / instructions）对照 DSH，差异登记
- 改智能体循环 = 高风险，必须有测试 + 回滚

## 4.3 智能体插件对比（2026-10-23）

**包级别**：7 个智能体包与 DSH **完全一致**（`dsh-agent` / `agent-loop` / `system-prompt` / `agent-preset` / `agent-preset-registry` / `persona` / `agent-instructions`）。

**配置级别**：preset 有偏差。

| 差异 | DSH | 我们 | 判断 |
|---|---|---|---|
| `tool-pwsh` | standard preset 有 | 没有 | ✅ 合理（Arch 不需要 Windows shell） |
| `tool-schedule` | standard preset 里 | **宿主层**（entries.yml:277） | ⚠️ 所有 preset 共享，**Minimal 可能多了 tool-schedule** |
| `tool-schedule` 配置 | 无 | 无 | 配置本身一致 |

**决策 vs DSH 设计**：

| 决策 | 我们的决定 | DSH 实际 | 差异 |
|---|---|---|---|
| `personaPrefix` | `''` | `''`（默认） | ✅ 一致 |
| `includeHarnessIdentity` | `true`（显式） | `true`（默认） | ✅ 行为一致 |
| `includeRuntimeContext` | `true`（显式） | `true`（默认） | ✅ 行为一致 |
| `agent-instructions` maxBytes | 65536 | 65536 | ✅ 一致 |
| 四模式定义 | Standard/PTC/Minimal/Creator | 同 | ✅ 一致 |
| `tool-pwsh` | 不装 | standard 有 | ✅ 正常特化（Arch） |
| `tool-schedule` | 宿主层 | standard preset | ✅ **已修正**（移到 standard/ptc/creator preset） |

**结论**：智能体决策与 DSH 一致；`tool-schedule` 的位置已修正（宿主层 → standard/ptc/creator preset）。

**待确认**：宿主层的工具插件是否会泄漏到 Minimal（DSH 的 Minimal 只有 bash + readImage + compaction）。

**修正方向**：
- 把 `tool-schedule` 移到 standard/ptc/creator preset（像 DSH），或者确认 Minimal 是否需要它
- 检查宿主层其他工具插件是否也泄漏到 Minimal

## 5. 检查方法（三向对照）

| 对照 | 看什么 |
|---|---|
| **决策 vs 代码** | 决策写了代码没做 / 代码做了决策没写 / 冲突 |
| **代码 vs DSH** | 改了什么、删了什么、简化了什么（差异登记） |
| **代码 vs 测试** | 有没有测试覆盖；没有的补 |

## 6. 第一批：启动链路（具体检查项）

1. `dsh-app-boot` 的 `boot()` 流程：配置读取 → loader 创建 → entries 加载
2. `entries.yml` 的 86 个启用项：是否有冗余、是否有未使用的
3. 启动失败的错误处理：单个 entry 失败是否隔离
4. 心跳机制：`bin/dx.ts` 的 heartbeat 是否影响启动
5. 启动日志：logger-console 挂载后，启动日志是否完整
