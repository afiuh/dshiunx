# 具体插件

**父级**：[插件模块](../插件模块.md)

## 为什么需要

基础设施提供规则和地基，具体插件提供**能力**——系统能做什么，由这里决定。

## 准备怎么实现

### 宏观想法

按"提供什么能力"分三类，对应 P2 的三种角色：

```
具体插件
├── 智能体插件/   怎么想：循环、提示词、预设、子代理
├── 工具插件/     能做什么：执行器 + 具体工具
└── TUI插件/      怎么看：界面（本轮不做）
```

**为什么只有三类**：会话、模型、网络、运行时支撑都归基础设施（被用）；剩下的才是"在用它们做事"的插件。

### 边界

| 属于具体插件 | 不属于 |
|---|---|
| 决定系统行为的逻辑 | 通用服务（基础设施） |
| 模型可见的能力 | 资源管理（运行时支撑） |
| 呈现与交互 | 事件存储（会话） |

**硬约束**：具体插件只依赖基础设施的服务契约，不 import 其他具体插件。

### 子节点

| 子节点 | 负责什么 | 状态 |
|---|---|---|
| [智能体插件](./具体插件/智能体插件.md) | 循环、提示词、预设、子代理 | 旧格式，待按 rc.3 重写 |
| [工具插件](./具体插件/工具插件.md) | 执行器（原生 / PTC）+ 具体工具 | ✅ 已按 rc.3 演化 |
| [TUI插件](./具体插件/TUI插件.md) | 界面 | 本轮不做（第 3 步） |

### 验证

- 删掉任一类具体插件，系统仍能启动（只是少了对应能力）
- 三类之间不互相 import
- 新增一类具体插件不需要改基础设施
