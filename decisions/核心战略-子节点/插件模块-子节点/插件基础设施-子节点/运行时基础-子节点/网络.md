# 网络

**父级**：[运行时基础](../运行时基础.md)

## 为什么需要

工具要抓网页、要搜索；未来可能有浏览器、下载器。联网能力不该写死在某个工具里。

## 准备怎么实现

### 宏观想法

```
工具（web_fetch / web_search）→ ctx.web（服务）→ provider（fetch / search）
                                              ↓
                                     能力探测（ready?）
```

- **服务与工具分离**：`ctx.web` 提供能力，`tool-web` 把它包装成模型可调用的工具
- **provider 可替换**：抓取（HTTP）与搜索（各家 API）各自注册
- **能力探测**：provider 不可认证时，工具对模型不可见（而不是调用时报错）

### 边界

| 网络负责 | 不负责 |
|---|---|
| HTTP 抓取（重定向、大小/时间限制、编码） | 内容怎么给模型看（工具/呈现） |
| 搜索 provider 的调用与结果归一 | 搜索策略（工具） |
| 代理、证书、认证配置 | 用户审批（工具执行链） |
| 能力探测（`searchReady` / `fetchReady`） | 工具可见性（preset） |

### 能力探测与工具可见性（rc.3 吸收）

**新增**：`ctx.web.searchReady(llmProvider)` / `fetchReady(llmProvider)`。

| 项 | 语义 |
|---|---|
| 问什么 | 该 provider 能否为这个 chat route 认证 |
| 怎么问 | 只调 provider 的 `ready()`；没有 `ready()` 视为就绪 |
| 副作用 | **不发网络请求** |
| 选择失败 | 返回 `true`（因为 `search()`/`fetch()` 会报结构化 `WebError`） |
| 返回 false | 仅当 provider 明确说"无法认证" |

**工具侧**（`tool-web`）：模型 step 在 `searchReady()` / `fetchReady()` 返回 false 时**不 admit** `web_search` / `web_fetch`——工具对模型不可见，而不是让模型调用后失败。

**为什么**：模型看不到必然失败的工具，就不会浪费一轮调用；错误留给真正的执行路径。

### SSRF 防护：**不跟随上游删除**

上游 rc.3 删掉了 `web-fetch-http/src/network.ts`（301 行：DNS 解析 + 地址固定，防 SSRF），没有移到别处。

**我们不吸收这个删除**，理由：

| 风险 | 说明 |
|---|---|
| 模型被诱导访问内网 | 抓取 URL 来自模型输出，可能指向 `127.0.0.1` / `192.168.x.x` / 云元数据 `169.254.169.254` |
| 重解析绕过 | 只校验一次 DNS 不够——连接时重新解析可能落到私有地址 |

我们的 `network.ts` 做法（保留）：
- 一次 DNS 答案集**全部**验证
- 验证后的地址通过自定义 lookup **固定**给 Undici
- 连接时不会重新解析

**同时吸收的部分**：同源重定向、无浏览器 cookie、无环境凭据、时间/大小限制（这些与 SSRF 防护不冲突，是简化 + 收敛）。

### 验证

- 换搜索 provider 不改 `tool-web`
- provider 不可用时，工具不出现在模型可见列表里
- 抓取只跟随同源重定向，不携带浏览器 cookie

**代码状态**：rc.2 无 `searchReady` / `fetchReady`；`tool-web` 不会按 ready 动态可见。待第 2 步补。
