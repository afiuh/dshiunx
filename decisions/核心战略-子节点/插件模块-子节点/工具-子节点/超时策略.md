# 超时策略

**父级**：[工具](../工具.md)

## 要做什么

给每个声明了 `timeoutMs` 的工具调用装一个 deadline，超时返回 `TOOL_TIMEOUT`，不放弃工具本身的 promise。

## 为什么要做

一个卡住的工具会拖死整个循环；超时让系统能继续。但**不能**在超时后直接丢弃工具 promise——那会让会话回放时调用与结果对不上。

## 怎么做

### 代码事实（2026-11-07 验证）

`packages/dsh-tool-call-timeout-policy/`（1 个源文件，81 行）：

- 插件名：`timeout-policy`
- 注入：`tools`
- 监听：`ctx.on('tools/execute', async (exec, next) => ...)`
- 常量：`TOOL_TIMEOUT = 'TOOL_TIMEOUT'`

### 执行逻辑（代码验证）

```
取 exec.name 对应的工具定义
  → 没有 timeoutMs：不装 deadline，直接 next()
  → 有 timeoutMs：
      1. 临时替换 exec.signal（带 deadline 的 signal）
      2. 委托 next()
      3. 恢复上游 signal
      4. 只有本 wrapper 的 timer 先到时，才替换结果为 TOOL_TIMEOUT
```

- **协作式**：工具必须声明 `timeoutMs` 并遵守 `exec.signal`
- **不放弃 promise**：等待工具结算，只替换结果
- **嵌套安全**：`timeoutOf` 限定到本插件，避免把外层 wrapper 的 deadline 误判成自己的

### 超时结果（代码验证）

```ts
{
  content: [{ type: 'text', text: 'Error: tool call timed out after 300000ms' }],
  isError: true,
  error: { message, info: { name: 'ToolTimeoutError', code: 'TOOL_TIMEOUT' } },
}
```

## 边界

- **只中止调用，不杀进程**（进程由 subprocess 管）
- **不做重试**（模型决定）
- **工具不声明 timeoutMs 就不装 deadline**

## 如何验证自己做对了

- 一个声明 `timeoutMs: 1000` 的慢工具，1 秒后返回 `TOOL_TIMEOUT`
- 工具结算后，结果被替换（不是丢弃）
- 外层 wrapper 的 deadline 不会被误判为本次超时
- `grep -n "TOOL_TIMEOUT\|tools/execute" packages/dsh-tool-call-timeout-policy/src/index.ts` 能看到实现
- 人看：`apply` 是否只有"取 timeout → 换 signal → 委托 → 恢复 → 替换结果"
