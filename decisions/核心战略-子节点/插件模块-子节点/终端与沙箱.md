# 终端与沙箱

**父级**：[插件模块](../插件模块.md)

## 要做什么

提供子进程、PTY 终端、沙箱策略——让 Agent 能跑命令、开终端，同时有边界。

## 为什么要做

Agent 要能执行命令，但执行环境必须有边界：超时、进程组管理、沙箱策略。这些能力不该写死在工具里。

## 怎么做

### 代码事实（2026-11-07 验证）

| 包 | 职责 | 源码 |
|---|---|---|
| `dsh-subprocess` | 子进程 seam（`ctx.subprocess`） | `src/index.ts`、`control.ts`、`types.ts` |
| `dsh-subprocess-local` | 本地实现 | — |
| `dsh-terminal` | 持久 PTY 会话 seam（`ctx.terminal`） | `src/index.ts`、`types.ts` |
| `dsh-terminal-bash` | Bash PTY 后端 | — |
| `dsh-pwsh-local` | PowerShell（未装配） | — |
| `dsh-win32-process` | Win32 进程/Job Object | — |
| `dsh-sandbox` | 抽象沙箱 seam（`ctx.sandbox`） | `src/index.ts`、`diagnostics.ts`、`escalation.ts`、`roots.ts` |
| `dsh-sandbox-policy` | 每次调用的沙箱策略 | `src/index.ts`、`session-mode.ts` |

### 沙箱决策（归档原话）

> 用户（2026-10-22，D6）：
> "你参考一下pi的架构吧，我觉得沙箱是可以作为后续的插件选择的，而不是最开始的构建选择。"

**决定**：第一版不装 `dsh-sandbox-local`（bwrap/landlock/Seatbelt/ACL），只装 `dsh-sandbox-policy`，配置 `danger-full-access`。

代码验证（entries.yml）：

```yaml
- id: sandbox-policy
  name: '@deepseek-ai/dsh-sandbox-policy'
  config:
    mode: danger-full-access
    workspaceRoot: /mnt/data/AI自由工作区/dshiunx
```

### 终端装配

```yaml
- id: subprocess
  name: '@deepseek-ai/dsh-subprocess-local'
- id: pty
  name: '@deepseek-ai/dsh-terminal'
- id: terminal-bash
  name: '@deepseek-ai/dsh-terminal-bash'
```

## 边界

- **不做审批弹窗**：dshiunx 的边界是沙箱策略和超时，不是"问用户"
- **不做 Windows 支持**：当前只装配 Linux 实现（`pwsh-local`、`win32-process` 未用）
- **沙箱不是内核**：它是插件，可以换实现
- **沙箱是逐位置画边界，不是开关**（归档 §6.1）：按路径/fd/资源分别决定

## 如何验证自己做对了

- 跑一条超长命令，超时后进程被清理（没有僵尸）
- 终端会话能持久（同一 PTY 多次命令）
- 换一个沙箱实现，工具不用改
- `grep -A3 "sandbox-policy" packages/bundle-arch/entries.yml` 能看到 `danger-full-access`
- 人看：`dsh-subprocess` 的接口是否只有"起进程 → 读输出 → 杀进程"
