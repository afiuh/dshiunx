# 插件机制的指导理念

**父级**：[插件模块](../插件模块.md)

## 要做什么

定义 dshiunx 插件机制的三条不可妥协的原则：

1. **同质**：除内核外，所有插件是同一性质的对象，没有"基础插件 / 预设插件 / 业务插件"的分层
2. **显式**：每个插件对人和模型都可见——能列出、能读描述、能看状态、能看配置
3. **可热启动**：任何插件（包括 Agent 循环、沙箱、压缩）都能在不重启进程的情况下重载

## 为什么要做

DSH 宣称"一切皆插件"，但实际分了三六九等：

| 插件 | 是插件 | UI 显式 | 模型可见 |
|---|---|---|---|
| `agent-loop` | 是 | ❌ | ❌ |
| `agent-preset` | 是 | 半显式（只读列表） | ❌ |
| `sandbox-policy` | 是 | ❌ | 只有一行模式文本 |
| `user-approval` | 是 | 仅弹窗时 | ❌ |
| `compaction` | 是 | ❌ | ❌ |
| `skill-filesystem` | 是 | ❌ | 只有 skill 列表 |
| `hmr` | 是 | ❌ | ❌ |

结果：**模型看到的世界是残缺的**。它知道有哪些工具，但不知道工具体系怎么搭起来；不知道沙箱规则从哪来；不知道压缩是谁做的；不知道 preset 为什么改不动。

> 用户（2026-11-08，讨论 DSH 插件哲学）：
> "dsh 虽然想实现一切皆插件，可是基础插件都没有显式地展示出来，比如智能体循环还有那些预设插件之类的。我们要实现的是除了内核部分之外所有插件都是一个性质，而且要显式，让智能体没有偏见地看待所有插件。插件的功能不同只会影响运行方式，不影响性质。而且所有插件都要可以热启动。"

## 怎么做

### 一个接口，没有例外

```ts
interface Plugin {
  id: string
  name: string
  version: string          // 只用于记录/复现，不参与加载判断
  description: string      // 一句话，给人和模型看
  config: unknown          // 当前生效配置（可读）
  state: 'loading' | 'running' | 'failed' | 'disabled'
  capabilities: { tools?: string[]; hooks?: string[]; services?: string[] }
  reload(): Promise<void>  // 热启动入口
}
```

内核只做四件事：**加载、列出、调用、重载**。它不认识 `preset`、`sandbox`、`agent-loop` 这些具体名字。

### 显式的两个面向

**人可见**：UI 的插件页列出全部插件（含 agent-loop、sandbox、compaction、hmr、远程），显示状态、配置、依赖、最近重载时间。

**模型可见**：给模型一个 `plugins` 能力：

```
plugins()        → 全部插件 + 状态 + 一句话描述
plugin(id)       → 该插件的描述 / 配置 / 能力 / 依赖
```

模型能回答"我为什么被沙箱限制""谁在压缩上下文""远程插件装在哪"——而不是对着黑箱猜。

### 无偏见

模型看到的是一张同质的表：

```
id            state     description
agent-loop    running   消息循环
bash          running   执行 shell
sandbox       running   文件/网络边界
compaction    running   上下文压缩
git-guard     running   拦截危险 git
```

没有"基础/业务/预设"的分层，只有功能不同的同质对象。

### 统一热启动

```ts
await plugins.reload(id)   // 任何插件，同一入口
```

包括 agent-loop 自己。DSH 做不到这一点，因为它把 agent-loop 和 preset 当启动时挂载的特殊对象；dshiunx 要求它们和普通工具插件走同一条重载路径。

### 内核边界（必须定死）

内核只保留四件事：

1. **插件注册表**：加载 / 卸载 / 重载 / 依赖解析
2. **消息循环的最小骨架**：输入 → 模型 → 工具 → 输出，具体策略由插件决定
3. **进程与 IO**：stdin/stdout、HTTP、文件系统原语
4. **事件总线**：插件间通信

其余全部是插件：循环策略、上下文管理、压缩、沙箱、审批、工具、skill、UI、远程。

### 热更新是默认，冻结是显式选择

自进化系统的默认是"改了立刻生效"。版本冻结只在调试/复现时显式开启：

- **默认**：改插件 → 下一次调用就用新的
- **调试**：开 snapshot 会话，锁定版本号
- **审计**：每条消息记录当时版本哈希，但不阻止后续变更

> 用户（2026-11-08）：
> "都自进化了行为还要保持一致吗"

DSH 的 preset revision retention 把"可复现"当成默认需求，代价是热启动失效、两套生命周期、重复注册（`Duplicate agent preset`）。

## 边界

- **插件不隐藏自己**：没有"内部插件"这一说，所有插件都可列出
- **插件不分等级**：agent-loop 和 git-guard 在注册表里是同一类对象
- **内核不特殊对待任何插件**：内核代码里不出现具体插件名（默认配置除外）
- **热重载不改变会话状态**：重载插件不丢会话，会话按 id 继续解析

## 如何验证自己做对了

- `plugins()` 返回的列表包含 agent-loop、sandbox、compaction、hmr、远程插件——一个不少
- 模型能准确回答"当前沙箱模式是什么、谁设置的"
- `plugins.reload('agent-loop')` 不重启进程，会话继续
- 改任意插件的配置，下一次工具调用就生效（不需要重启）
- 内核代码里 grep 不到 `preset`、`sandbox`、`compaction` 这些具体名字
