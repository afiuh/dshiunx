# 内核模块

**父级**：[核心战略](../核心战略.md)

## 要做什么

只保留不可插件化的机制：依赖注入、生命周期、服务注册、事件分发、插件加载。其余一切能力都从内核里赶出去。

## 为什么要做

内核越大，插件生态越难建立——每个能力进内核，就多一条"必须兼容"的约束。DSH 的偏差之一就是框架里塞了产品假设。

> 用户（2026-10-22，核心战略）：
> "最初的框架应该就像 Arch Linux 系统最初的模样一样简洁干净，其他的一切都可以插件化。"

**踩过的坑**：`packages/*/node_modules` 里的软链指向 pnpm store 的旧版本（cordis 4.0.5），覆盖了根 `node_modules` 的软链——删除 76 个包内 node_modules 才修好。

### 内核准入判据（三条必须同时满足）

1. 所有插件都依赖它（不是某类插件）
2. 与具体能力无关（不知道"文件""工具""界面"是什么）
3. 足够稳定（不能频繁变化，否则插件生态无法建立）

### 事件分发（代码验证）

`events.ts` 定义 5 种模式（不是 4 种）：

| 模式 | 语义 |
|---|---|
| `emit` | 同步执行监听器，不 await |
| `parallel` | 并发执行，全部 await 完 |
| `serial` | 顺序 await，任一返回非空即停 |
| `bail` | 顺序执行，遇到第一个同步 bail 值即停 |
| `waterfall` | 每个监听器可以改写参数/结果，链式传递 |

### 生命周期（代码验证）

`fiber.ts`：
- `ctx.effect(() => { ... return dispose })`：注册副作用，卸载时自动清理
- effect 可以返回单个 disposer、Promise、或 generator（多个 disposer 逐个注册）
- 嵌套 effect 有标签树（用于诊断）
- 父 fiber 销毁 → 子 fiber 级联销毁

### 依赖注入（代码验证）

`registry.ts`：
- `ctx.inject(deps, callback)`：依赖就绪时执行，依赖变化时重跑
- `@Inject` 装饰器：类/方法上声明依赖
- `ctx.provide(name, value)` / `ctx.get(name)`
- 服务查找走 `isolate` 映射（按 scope 标签），不是 fiber 链

### DSH 0.2.2 的内核修复（必须跟）

| 修复 | 为什么必须跟 |
|---|---|
| `cross-tree group member transfer` | 插件树跨树移动——P3（无限嵌套）直接依赖 |
| `Include refresh rejections` | Include 刷新被拒时要兜住，否则树状态不一致 |
| `entry ids with colon` | entries.yml 生成的 id 带冒号——loader 要接受 |

**dshiunx 的决策**：这三条是**内核契约**，不是产品功能，必须跟。当前 loader 是旧版（`write()` 未改 `commit(change)`），跟进时一并改。

### 明确不进内核

TUI、Agent 循环、工具、模型适配器、会话存储、布局、角色、预设——全部在 `packages/dsh-*` 里。

## 边界

- **内核不知道"插件"之外的概念**：不知道 session、tool、model、ui
- **内核不做策略**：审批、沙箱、重试、压缩——都是插件
- **内核不碰 UI**：连 TUI 都是插件

## 如何验证自己做对了

- `grep -r "session\|tool\|llm\|ui" packages/cordis/src` 应该为空（内核不认识业务概念）
- 删掉 `packages/dsh-*` 全部，`cordis` 仍能单独启动、加载一个空插件
- 加一个新插件不需要改内核代码
- 5 种事件分发都能在 `events.ts` 里找到实现
- 人看：内核 API 面（inject/provide/get/on/effect/plugin）是否小到能一次读完
