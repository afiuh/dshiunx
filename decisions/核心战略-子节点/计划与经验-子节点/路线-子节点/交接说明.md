## 2. 卡点：headless 的 `no agent factory registered`

### 现象

`bin/dx.ts -p "..."` → 启动 99 entries → 报 `dsh: no agent factory registered (load an agent-loop plugin)` → exit 1。

### 已锁定的证据

| 事实 | 值 |
|---|---|
| root / agent-loop / headless 拿到的 `agents` 实例 | **三个不同对象**（`same: false`） |
| 三者 `!!factory` | 都是 `true` |
| `dsh-agent` 的 `create()` | 与上游**逐字一致**：`const ownerCtx = this.ctx` → `requireFactory()` → `getTraceable(ownerCtx, target)` → `Reflect.apply(target.createAgent, ...)` |
| 报错点 | `requireFactory()` 的 `this.factory === undefined`（`dsh-agent/index.ts:403`） |

### 矛盾

调试显示 headless 实例的 `factory` 存在，但 `create()` 里 `requireFactory()` 说 undefined。

→ **说明 `create()` 的 `this` 不是调试看到的那个实例**（或 `run()` 里 `ctx.get('agents')` 拿到了另一个）。

### 已试（都失败）

1. `ctx.plugin(HeadlessRunner, { task })`（root 挂载）→ no factory
2. 加 `await ctx.get('loader')?.await()` 再挂 → no factory
3. `ctx.loader.create({ id, name, config: { task } })`（root include 树）→ no factory

### 下一步（按顺序）

1. **读 `getTraceable(ownerCtx, target)`**（`dsh-agent` 内）：它怎么把 factory 的 target 绑定到 receiver
2. **读 `requireFactory()` 的 `this` 来源**：`create()` 是服务方法，`this` 是服务实例——确认 headless 拿到的实例是否与 `agent-loop` 注册 factory 的实例相同
3. **对照上游的 `headless-startup`**（`dsh-headless/startup`）：
   - 上游 patch 里 `headless-runner` 有 `inject: [headlessStartup]` + `config.task: !!js ctx.headlessStartup.task`
   - **task 通过 provider 传，不是直接 config**
   - 我们直接传 `config: { task }`，可能让 `run()` 走了不同分支（或 `inject` 未就绪时提前执行）
4. **对照上游 `agent-loop` 的挂载位置**：上游 `bundles/base/cordis.patch.yml` 里**没有** `agent-loop`（grep 无结果）——它可能在别的 bundle（`packages/bundle/*`）。需要确认上游 agent-loop 到底挂在哪一层、有没有 isolate

### 一个关键线索

上游 headless patch 的注释：

> An ordinary provider plugin injects `cmdlineArgs`, parses the task positional, Session identity, permission and output options

即：**headless-startup 先解析 cmdline → 提供 `headlessStartup` provider → headless-runner 注入它**。

我们跳过了 startup，直接给 runner 传 config——这可能就是差异所在（runner 的 `inject` 只有 `agentDefaultModel/agents/sessions`，但上游 patch 额外加了 `inject: [headlessStartup]`）。
