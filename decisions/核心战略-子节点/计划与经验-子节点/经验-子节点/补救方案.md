# 决策网络补救方案（2026-10-23）

## 问题

**当前决策网络是“从代码反推的文档”，不是“先设计再实现的决策”。**

| | 应该 | 实际 |
|---|---|---|
| **顺序** | 先决策 → 无限细分 → 实现拆分 → 写代码 | 先 vendor 代码 → 反推文档 |
| **内容** | 为什么（选 A 不选 B） | 是什么（源码/配置/行为） |
| **粒度** | 实现拆分（resolve 算法 / scope 继承） | 包 / 子模块（嵌套与隔离） |
| **作用** | 指导实现（写代码前看） | 描述现状（写代码后补） |

**根因**：我们一直“先复刻代码，再补文档”——决策文件变成了代码的说明书，不是设计。

## 补救方案

### 1. 新标准：决策文件写“为什么”

```markdown
# 实现拆分名

## 要解决什么问题（用户视角）

## 决策（为什么）
- 选 A，不选 B，因为...

## 接口契约（输入/输出/错误）

## 边界条件

## 对应代码
```

**关键变化**：
- 从“负责什么 + 源码 + 决策（是什么）” → “问题 + 决策（为什么）+ 接口 + 边界”
- 每个决策必须写“不选什么、为什么”

### 2. 增量补救（不重构全部）

| 范围 | 做法 |
|---|---|
| **新决策**（以后写的） | 按新标准 |
| **旧决策**（67 个文件） | 标注“代码反推，待补决策理由” |
| **优先补** | 正在改的模块（智能体 / 插件） |
| **不重构** | 全部 67 个文件（成本太高，先增量） |

### 3. 流程修正（写入规则）

1. **新功能**：先写决策（实现拆分级）→ 再写代码
2. **决策错了**：改决策，不是改代码再补文档
3. **代码改动**：同步决策（已有规则）
4. **决策粒度**：拆分到“一个函数/一个算法”级

### 4. 决策网络的“实现拆分”粒度

| 现在的粒度 | 目标粒度 |
|---|---|
| `嵌套与隔离-子节点/嵌套与隔离.md`（12 条决策） | `EntryTree 存储` / `EntryTree 遍历` / `Group 递归` / `Isolate scope` / `Realm 生命周期`（5 个文件） |
| `插件分类.md`（6 类） | `分类规则` / `catalog 生成` / `边界判定`（3 个文件） |
| `智能体插件-子节点/agent.md` | `AgentService 接口` / `Agent 生命周期` / `Agent 所有权`（3 个文件） |

## 不做什么

- ❌ 不重构全部 67 个文件（先增量）
- ❌ 不删除现有决策（它们是“现状描述”，有用）
- ❌ 不停止当前工作（补救是渐进的）

## 执行顺序

1. **立即**：把本方案写入 `decisions/README.md`（规则）
2. **本轮**：给插件模块的决策文件加“待补决策理由”标注
3. **下一轮**：智能体插件按新标准重写（实现拆分级）
4. **以后**：新功能先决策后代码

## 教训

**先代码后决策 = 决策变成说明书。** 决策网络的价值在“写代码前看”，不是“写代码后补”。
