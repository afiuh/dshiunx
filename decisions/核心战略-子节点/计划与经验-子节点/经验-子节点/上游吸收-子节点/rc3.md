# rc3

**父级**：[上游吸收](../上游吸收.md)

## 为什么需要

每次上游更新（rc3、rc4…）的吸收是**独立的一轮**：候选不同、结论不同、落点不同。按版本分开，避免混在一起说不清"这条结论是哪次吸收的"。

## 准备怎么实现

### 宏观结构

```
上游吸收.md              ← 跨版本规则（怎么判、怎么落决策）
上游吸收-子节点/
├── rc3.md               ← 本轮：吸收了什么、不吸收什么
├── rc3-子节点/
│   ├── 候选清单.md
│   ├── 分析-工具机制.md
│   ├── 分析-智能体.md
│   ├── 分析-内核与运行时.md
│   └── 复查记录.md
└── （未来）rc4.md + rc4-子节点/
```

### 边界

| rc3 管 | 不管 |
|---|---|
| 本轮（rc.2 → rc.3）的候选与结论 | 跨版本通用规则（[上游吸收](../上游吸收.md)） |
| 每条结论落到哪个决策节点 | 决策本身（在 `插件模块-子节点/` / `内核模块-子节点/`） |
| 哪些明确不吸收及原因 | 代码实现（第 2 步） |

### 验证

- 每条候选有结论（吸收 / 改造吸收 / 不吸收）
- 每个"吸收"都能指到落点决策文件
- "不吸收"写明原因（如违反 P7）
- 候选清单与已落地的决策对得上，没有"说了没做"
