# 插件加载与嵌套

**父级**：[内核模块](../内核模块.md)

## 要做什么

从 `entries.yml` 读取条目，逐个创建插件；支持插件套插件（group），深度不设限，且每层都拥有完整 ctx 能力。

## 为什么要做

装配要和代码分离：换一套插件组合就是换一个 entries.yml，不用改入口代码。嵌套则是"能力组合"的基本方式——一个"科研工作流"插件内部可以是一棵完整的子树。

> 用户（2026-10-22）：
> "插件可以套插件（group → group → …），深度不设限；内核能力在任意层级都完整可用。"

## 怎么做

### 加载流程（代码事实）

```ts
const ctx = new Context()
await ctx.plugin(Loader)
for (const entry of entries) {
  await ctx.loader.create({ id: entry.id, name: entry.name, config: entry.config })
}
await ctx.loader.await()
```

- `entries.yml`：`{ id, name, config }` 列表（当前 **51 条**）
- `loader.create`：按 name 解析包、实例化、挂到 ctx
- `loader.await`：等所有插件就绪

### 嵌套

- `cordis-plugin-group`：一个插件内部再挂子插件
- 子插件的 ctx 与顶层同构：inject/provide/get/on 全都能用
- 服务查找走全局 store，不因嵌套深度丢失能力

### 装配与代码分离

```yaml
- id: llm
  name: '@deepseek-ai/dsh-llm'
- id: llm-deepseek
  name: '@deepseek-ai/dsh-llm-deepseek-api-key'
  config:
    apiKeyEnv: DEEPSEEK_API_KEY
```

换 provider、换工具、加压缩——都只改 YAML。

## 边界

- **不在内核里写死装配**：入口只做"读 YAML → create → await"
- **不做版本兼容层**：插件版本由 npm 管，内核不检查
- **不做依赖图解析**：加载顺序由 entries.yml 的顺序保证

## 如何验证自己做对了

- 改 entries.yml 加一条，重启后新插件生效，入口代码没改
- 删一条，对应能力消失，其余插件不受影响
- 嵌套三层 group，最深层插件能 `ctx.get('sessions')`
- 人看：`bin/headless.ts` 是否只有"读配置 → 加载 → 等就绪"三步
