# 依赖注入与生命周期

**父级**：[内核模块](../内核模块.md)

## 要做什么

提供 `ctx.inject` / `ctx.provide` / `ctx.get` 做服务查找，提供 fiber/effect/dispose 做生命周期管理——让插件能安全地拿依赖、安全地清理。

## 为什么要做

没有 DI，插件之间只能靠全局单例或 import 硬编码，无法替换、无法隔离。没有生命周期，插件卸载时资源泄漏，热更新会叠出多份实例。

> 用户（2026-10-22）：
> "内核职责清单（穷举）：依赖注入（ctx.inject / provide / get）、生命周期（fiber、effect、dispose）、服务注册与查找、事件分发、插件加载。"

## 怎么做

### 服务查找

- `ctx.provide(name, value)`：注册服务
- `ctx.get(name)`：查找服务，拿不到返回 undefined
- `ctx.inject(deps, callback)`：依赖就绪时执行回调，依赖变化时重跑

### 生命周期

- 每个插件有自己的 fiber
- `ctx.effect(() => { ... return dispose })`：注册副作用，卸载时自动清理
- 卸载清理走 `ctx.effect` 返回的 disposer（没有 `dispose` 事件）
- 父 fiber 销毁 → 子 fiber 级联销毁（子 fiber 的 dispose 注册在父 fiber 的 effect 上）

### 隔离

- 服务查找是**全局 store（按 isolate 标签）**，不是 fiber 链——子 scope 不需要强制继承 root
- 这是 D40 修正（2026-10-23）：避免深层插件拿不到顶层服务

## 边界

- **不做依赖注入容器**（不需要装饰器、不需要 token）——就是字符串键 + 对象值
- **不做异步初始化链**：插件自己 await，内核只保证顺序
- **不做循环依赖检测**：靠约定（inject 只声明，不执行）

## 如何验证自己做对了

- 插件 A provide 服务，插件 B inject 后能拿到
- 卸载 A 后，B 的 inject 回调收到 undefined 或重跑
- 卸载父插件，子插件全部卸载，没有残留的 timer/listener
- 人看：`cordis` 的 DI 代码是否一屏能读完
