# 事件与服务

**父级**：[内核模块](../内核模块.md)

## 要做什么

提供统一的事件分发（emit / waterfall / parallel / serial / bail）和服务注册表——插件之间只通过事件和服务通信，不直接 import。

## 为什么要做

插件之间直接 import 会形成硬依赖：换一个实现就要改调用方。事件和服务是唯一的解耦手段——DSH 的 agent-loop、工具、会话全靠这个。

> 用户（2026-10-22）：
> "事件分发（waterfall / parallel / serial / bail）。"

## 怎么做

### 事件分发

| 模式 | 语义 |
|---|---|
| `emit` | 同步执行监听器，不 await |
| `waterfall` | 每个监听器可以改写参数/结果，链式传递（组合 `next`） |
| `parallel` | 并发执行，全部 await 完 |
| `serial` | 顺序 await，任一返回非空即停 |
| `bail` | 顺序执行，遇到第一个同步 bail 值即停 |

### 服务

- `ctx.provide(name, value)` 注册
- `ctx.get(name)` 查找
- 服务名是字符串（`sessions`、`agents`、`tools`、`llm`、`fs`、`subprocess`、`terminal`…）

### 事件命名

代码事实（2026-11-07 验证）：

| 域 | 事件 |
|---|---|
| agent | `agent/created`、`agent/disposed`、`agent/status`、`agent/error`、`agent/pre-step`、`agent/request`、`agent/request-error`、`agent/assistant-stream`、`agent/turn-stopping` |
| tools | `tools/pre-execute`、`tools/execute`、`tools/post-execute`、`tools/result`、`tools/change`、`tools/ptc-dispatch-log` |
| session | `session/event` |
| system-prompt | `system-prompt/assemble`、`system-prompt/change` |

## 边界

- **事件不持久化**：要持久化的状态走 session
- **服务不做版本**：同名服务只有一个实现（后注册覆盖或报错）
- **不做事件回放**：回放是 session 的事

## 如何验证自己做对了

- 插件 A 监听 `tools/execute` 能改写工具参数（waterfall）
- 插件 B 监听 `session/event` 能拿到所有会话事件
- 卸载插件后，它的监听器全部移除（没有幽灵回调）
- 人看：事件名是否按"域/动作"命名，能一眼看出谁发谁收
