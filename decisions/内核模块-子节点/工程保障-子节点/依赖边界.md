# 依赖边界

**父级**：[工程保障](../工程保障.md)

## 为什么需要

"内核不得依赖插件"不能只靠自觉。没有机械检查，一次 import 就能把内核和具体插件绑死，P1（最小内核）就名存实亡。

## 准备怎么实现

### 宏观想法

用 `dependency-cruiser` 做**路径级**约束：从 `packages/` 的路径前缀判断"内核"和"插件"，不靠包名或人工审查。

```
dependency-cruiser
  ├─ kernel-no-plugins    内核 → 插件：error（阻断）
  ├─ no-circular          循环依赖：warn
  └─ TUI 分层规则         渲染/UI/adapter 反向依赖：error
```

**为什么不用 ESLint 的 import 规则**：ESLint 只能看模块说明符，看不到"这个路径属于内核还是插件"；dependency-cruiser 按路径前缀匹配，正好对应 `packages/` 的物理布局。

### 细节实现

1. **内核范围**：`^packages/(cordis|cosmokit|schemastery)`——DI、事件、工具库、schema。
2. **插件范围**：`^packages/(dsh-|tui)`——所有具体能力（含 TUI）。
3. **`kernel-no-plugins`**：内核不得 import 插件；severity `error`（`.dependency-cruiser.cjs:5-9`）。
4. **`no-circular`**：全局循环依赖 warn；`index <-> plugin` 的类型循环显式 `ignore`（`.dependency-cruiser.cjs:12-24`）。
5. **TUI 分层规则**（当前冻结，仍生效）：
   - `tui-core-no-ui`：`src/ink`（渲染引擎）不得依赖 `components|screens`
   - `ui-no-backends`：UI 层不得依赖 `backends`
   - `adapter-no-ui`：adapter 不得依赖 UI
6. **违规处理**：`error` 级阻断（提交前/CI 跑）；`warn` 级只报告，不阻断。
7. **检查命令**：`scripts/deps.mjs`（封装 depcruise + 配置）。

### 边界

| 本节点负责 | 不负责 |
|---|---|
| 路径前缀的"内核/插件"划分 | 单个包内部的模块分层（由该包的决策管） |
| 违规级别（error/warn） | 运行时依赖注入的隔离（那是 `Isolate` / `Service`） |
| 新增规则的准入 | 重构以消除违规的具体做法 |

### 验证

- `kernel-no-plugins` 能拦住一次故意的内核 → 插件 import（临时加一行再撤销）
- `no-circular` 在出现环时报 warn
- TUI 冻结期间规则保持 error 级
