# 上游差异

**父级**：[工程保障](../工程保障.md)

## 为什么需要

我们是 DSH 的 vendor + 改造版。与上游的每一处差异都必须能回答"改了什么、为什么、影响面"——否则下次同步上游时，分不清是上游的 bug 还是我们的改动。

## 准备怎么实现

### 宏观想法

**差异就地登记在决策网络里**，不另建"差异清单"文件（避免双轨）：

```
模块决策文件（如 插件装配.md「与 DSH 的差异」）
  ├─ 改了什么
  ├─ 为什么（按 P1/P6/P7 裁决）
  └─ 影响面（哪些包/入口）
rc3 候选清单（上游吸收经验）
  ├─ 吸收 / 部分 / 不吸收 + 理由
  └─ 对应 commit
```

**为什么不用独立 diff 文件**：差异是决策的后果，脱离决策单独维护会过期；决策网络里就地记录，读决策就能看到差异。

### 细节实现

1. **登记规则**：任何与上游行为不同的改动，在所属模块决策里写「与 DSH 的差异」段：改了什么 / 为什么 / 影响面。
2. **裁决依据**：P1（最小内核）、P6（自进化）、P7（无版本门槛）；违反者一律不吸收（如版本检查、兼容性检查）。
3. **验证方法**：`diff -r packages/<我们的> 上游/packages/<对应>`；结构性差异看 `diff`，行为差异看测试。
4. **上游吸收**：`计划与经验-子节点/经验-子节点/上游吸收-子节点/rcN-子节点/候选清单.md`——每项有状态（吸收/部分/不吸收）+ 理由 + commit。
5. **同步成本**：差异越少，下次 rcN 同步越便宜；每吸收一项就缩小 diff。
6. **典型差异**：装配方式（bundles + catalog vs DSH 纯 bundle）、TUI（vendor 后冻结）、版本检查（删除，P7）。

### 边界

| 本节点负责 | 不负责 |
|---|---|
| 差异登记规则与位置 | 具体某项差异的技术实现（所属模块管） |
| 裁决依据（P1/P6/P7） | 上游更新的筛选（rcN 路线管） |
| diff 验证方法 | 自动同步工具（没有，手工 diff） |

### 验证

- 任一模块决策能回答"与上游差在哪、为什么"
- `rcN 候选清单` 的每一项都有状态 + 理由 + commit
- 删除某项差异后，对应决策同步更新（不留过期描述）
