# 类型检查

**父级**：[工程保障](../工程保障.md)

## 为什么需要

内核的接口（Service / Fiber / Context / Loader）一旦类型错了，所有插件的类型都会跟着错。需要一个**内核专属的严格检查**，不被 vendor 的历史代码拖累。

## 准备怎么实现

### 宏观想法

两个 tsconfig，分工明确：

```
tsconfig.json        全量：编译所有包（strict: false，兼容 vendor）
tsconfig.core.json   内核：extends 全量 + strict: true + noEmit，只 include 内核 9 包
```

**为什么不全量 strict**：vendor 的代码大量 `any`/隐式类型，全量 strict 会报几千个错，改不起也不该改（不是我们的代码）。内核是我们维护的，必须 strict。

### 细节实现

1. **`tsconfig.core.json`**：`extends: ./tsconfig.json`、`strict: true`、`noEmit: true`。
2. **include 范围（9 个包）**：`cordis`、`cordis-plugin-loader`、`cordis-plugin-group`、`cordis-plugin-include`、`cordis-plugin-hmr`、`cordis-plugin-timer`、`cosmokit`、`schemastery` + `types/**/*.d.ts`。
3. **验收**：`npx tsc -p tsconfig.core.json --noEmit` → **0 错误**（交付口径，不可跳过）。
4. **全量 `tsconfig.json`**：`strict: false`，负责编译/打包；`paths` 映射所有包（含新增的 `dsh-headless` / `dsh-session-query-sqlite`）。
5. **新增包时**：如果是内核包，加进 `tsconfig.core.json` 的 include；如果是插件包，只加 `paths`。
6. **为什么 core 用 `noEmit`**：检查与产物分离；产物由全量 tsconfig / tsx 负责。

### 边界

| 本节点负责 | 不负责 |
|---|---|
| 内核包的 strict 范围与基线 | 插件包的类型质量（各插件自己管） |
| core / 全量的分工 | 构建产物（`lib/`）的生成 |
| 0 错误的验收方式 | lint 规则（oxlint / eslint） |

### 验证

- `npx tsc -p tsconfig.core.json --noEmit` → 0 错误
- 内核包新增文件自动纳入（include 用 glob）
- 插件包不进 core include（不会因 vendor 代码报错）

## 参考什么

- `tsconfig.core.json`（strict + noEmit + 9 包 include）
- `tsconfig.json`（全量 + paths）
