# 测试策略

**父级**：[工程保障](../工程保障.md)

## 为什么需要

内核的行为（DI / 生命周期 / 事件 / loader / HMR）是全部插件的地基。地基错了，上层所有测试都不可信。测试要能**独立于具体插件**验证内核。

## 准备怎么实现

### 宏观想法

```
tests/
├─ kernel.test.ts          16 个：DI / 生命周期 / 事件 / Service / include / group / intercept
├─ framework.test.ts        3 个：框架层（状态机 / 调度）
├─ loader.test.ts           1 个：声明式配置加载
├─ hmr.test.ts              4 个：热更新（依赖图 / 重载 / 清理）
├─ infrastructure.test.ts   3 个：基础设施
└─ agent.test.ts            4 个：agent 注册表 / 生命周期
```

**为什么按模块分文件**：一个文件对应一类决策；新增决策时知道该往哪个文件加用例，不靠猜。

**为什么不做覆盖率数字**：覆盖率是行覆盖，不是行为覆盖。内核的关键是"决策写的行为都被验证"，不是"每行都跑到"。

### 细节实现

1. **kernel.test.ts（16 个）**：DI（inject/provide/get）、生命周期（fiber 状态 / effect LIFO / dispose）、事件（waterfall / parallel / once / prepend）、Service（check 谓词 / isolate）、include（配置加载 / patch）、group（disabled 级联）、intercept（配置合并）。
2. **framework.test.ts（3 个）**：状态机转换、调度、错误传播。
3. **loader.test.ts（1 个）**：按声明式配置加载插件（`entries.yml` 的 include 行为）。
4. **hmr.test.ts（4 个）**：依赖图、三集合、重载、清理。
5. **infrastructure.test.ts（3 个）**：基础设施服务（timer / logger 等）。
6. **agent.test.ts（4 个）**：agent 注册表、创建/销毁、announce。
7. **新增决策时**：决策文件的「验证」段写的行为，必须落到对应测试文件的一个用例；没有对应文件的，新建。
8. **交付口径**：`npx tsx --test tests/*.test.ts` → 31/31（当前基线）。

### 边界

| 本节点负责 | 不负责 |
|---|---|
| 内核/框架层的测试组织与基线 | 具体插件的行为测试（各插件自己的 tests/） |
| 新增决策的测试落点 | 性能/压力测试 |
| 测试命令与通过标准 | E2E（`scripts/test-env.mts` 那类） |

### 验证

- `npx tsx --test tests/*.test.ts` → 31/31
- 新增内核决策时，能在上表找到对应文件并加用例
- 测试不依赖真实网络 / 真实模型（fixtures 隔离）

## 参考什么

- `tests/`（6 个文件 / 31 个用例）
- `scripts/run-tests.mts`（启动完整树跑测试的入口）
