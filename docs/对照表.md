# DSH 分层对照表

## 1. base（核心运行时）

分类口径：**保留** = 进入 base 移植范围；**跳过** = 不移植，理由见 1.2。base 只覆盖模型运行时本身，不含桌面/Web 客户端、平台账户、通用存储与遥测。

逐条判定按三条顺序走：

1. 是否 agent 循环、模型调用、会话、工具执行所必需（缺了跑不起来）；
2. 是否只服务客户端展示、平台账户或产品化流程（插件市场、设置页、遥测、远程接入）；
3. 若被保留项引用，能否降级为「可选注入 / 环境变量 / 直接读写文件」。

前两条都指向「非运行时」才判跳过；第三条用来兜住边界情况，避免把有硬依赖的条目错跳。按此口径重判 96 项，结果：**保留 66 项、跳过 30 项**（分类见 1.1、1.2，依赖闭环见 1.3）。

复核记录：上一轮曾把 `web`、`web-fetch-http` 从跳过改为保留（`tool-web` 注入 `ctx.web`，且 `web-fetch-http` 是不依赖平台的本地 HTTP 抓取 provider，否则保留的 `tool-web` 无法装配），把 `plugin-manager`、`tool-plugin-manager` 从保留改为跳过（产品级插件安装/启停，依赖 `host-plugin-inventory`、`hmr` 等产品/客户端条目，且无 `profileContext` 时装配本就不启用）。本轮逐条重判未再改判，另补 1.3 依赖闭环核对、1.4 与 `entries.yml` 的对账；`credentials` 跳过已由 `apiKeyEnv: DEEPSEEK_API_KEY` 配置确认可行，仍留两处待确认（`mcp-resources` 的消费者、`attachment-local`/`spill-local` 是否走 `ctx.storage`）。

### 1.3 依赖闭环核对

保留项之间不能有悬空依赖；跳过项若被保留项引用，必须能降级。逐项核对如下（只列有跨条目依赖的）：

| 保留项 | 依赖 | 结论 |
|---|---|---|
| `tool-web` | `web`、`web-fetch-http`；搜索 provider | 前两项已保留；base 无搜索 provider，配 `search: false` |
| `tool-fs` | `fs-sandbox`、`fs-observation-policy` | 均已保留 |
| `tool-bash` | `bash-sandbox`、`shell-env`、`subprocess`、`sandbox-policy` | 均已保留 |
| `tool-jobs` | `jobs` | 保留 |
| `tool-skill` | `skill`、`skill-filesystem` | 保留 |
| `tool-subagent` / `tool-subagent-fork` | `subagent` + `subagent-spawn-in-process` / `subagent-fork-in-process` | 保留 |
| `tool-workflow` | `workflow-ptc`、`ptc-runtime`、`subagent` | 保留 |
| `command-compact`、`tool-result-pruner`、`image-offload` | `compaction-basic`、`token-meter` | 保留 |
| `spill-policy` | `spill-local` | 保留 |
| `session-persistence-jsonl` | `session`；直接写文件 | 不依赖 `storage` / `storage-json`，跳过存储层不影响持久化 |
| `llm-deepseek` | `llm`；可选 `settings` | `settings` 跳过，移植时去掉 `ctx.settings` 可选注入 |
| `mcp-resources` | 无（base 内没有 mcp client） | **待确认**：目前是无消费者的注册表；若 `tools` 不读其资源表，可一并跳过 |
| `attachment-local`、`spill-local` | 是否走 `ctx.storage` | **待确认**：若走 storage，则 `storage` 不能跳，需改为直接落盘 |

两处「待确认」（涉及 `mcp-resources`、`attachment-local`、`spill-local` 三项）是先验推断，移植时需按实现里的 import / 注入点核实；其余依赖已闭环。

### 1.4 与当前 entries.yml 的对账

仓库 `packages/bundle-arch/entries.yml` 第 1–315 行是运行时实际装配的宿主清单（83 条），与本表并非一一对应，执行本表时要一并处理：

- 本表判跳过、但宿主清单里仍挂着的 10 项：`storage`、`storage-domain`、`storage-json`、`settings`、`credentials`、`session-title`、`session-title-llm`、`config-editor`、`web-search-deepseek`、`web-deepseek-api`。需显式移除，否则 base 仍会带上存储、设置、会话标题与云端搜索。
- 另有 2 项虽在清单里但本就禁用：`plugin-manager`（`disabled: '!ctx.get(''profileContext'')'`）、`tool-plugin-manager`（`disabled: true`）；保留条目即可，不必删。
- 清单里有、本表未列为 base 的：`filesystem`（fs-local）、`pty`、`terminal-bash`、`persistent-bash`、`agent-preset-registry`、`tool-schedule`、`tool-subagent-model-selection`。终端/持久 shell 归第 2 节 sdk-minimal，`agent-preset-registry` 归第 3 节，其余属产品层；`sessions` 只是 `session-persistence-jsonl` 的条目 id，不算额外条目。
- 本表保留、清单里没有独立条目的：`permission`（权限预设，可能由 preset 段装配）。

### 1.5 装配约束

- `tool-web` 的 `web_fetch` 由 `web-fetch-http` 提供；base 没有搜索 provider，装配时给 `tool-web` 配 `search: false`，只启用 `web_fetch`。
- `tool-fs` 的 `fs` 由 `fs-sandbox` 提供，`tool-bash` 的 `shell` 由 `bash-sandbox` 提供，两者均已保留。
- `llm-deepseek` 的 host 在 `settings` 可用时会调用 `ctx.settings.configure(...)`；base 跳过 `settings`，移植时需去掉该可选注入，或补一个最小 settings 实现（不影响 adapter 注册）。
- `llm-deepseek` 的 key 走 `apiKeyEnv: DEEPSEEK_API_KEY`（`entries.yml` 即如此配置），因此跳过 `credentials` 不影响鉴权。
- `plugin-manager` / `tool-plugin-manager` 不在 base：base 由静态 profile 与 loader 装配条目，不提供运行时安装/启停；`dsh plugin` 子命令和设置页的插件管理属产品层，装配时不要保留这两个条目。
- `mcp-resources` 没有 mcp client 消费就是空转：要么补 client，要么从 base 清单移除（见 1.3）。
